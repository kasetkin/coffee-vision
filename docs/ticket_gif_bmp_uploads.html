Ticket OPS-18 · coffee-vision · the front's upload check and the public contract

The front accepts a GIF or a BMP again, canonicalizes it like any other photo, and the page and the contract name both

Since the OPS-15 cutover (2026-11-02) the front answers a GIF or a BMP with a 400, though the old single host decoded both and canonicalization (ML-19) still can. The refusal is one check in webapp/front/upload_check.py, which lets through only the formats the public contract names. This ticket adds GIF and BMP to the check, the contract and the page; a plain TIFF stays refused. On the way it makes the accepted formats one data file with one recogniser, read by the front, canonicalization and training alike, and lets no other format reach a decoder (D4, D11, D17). Written 2026-11-08; D1–D20 decided the same day; not planned, not implemented.

1. Summary

Today a GIF or a BMP sent to /analyze is refused at the front, before canonicalization, with "not a JPEG, PNG, WebP, HEIC/HEIF, AVIF, JPEG XL or camera RAW file". After this ticket the front's check accepts either by its signature, and canonicalization decodes it as it already can; an animated GIF is read as its first frame (D1). The page's picker, its format chips, llms.txt and openapi.json name GIF and BMP (D5). A plain TIFF is still refused (D2). The accepted formats become one data file, coffeecv/data/accepted_formats.csv (D11, D13–D15), and one recogniser in canonical.py tells a file's format from its first bytes and name (D17), for the front's check (D3) and for canonicalization, which then opens it with that row's decoder and no other (D4). Training's store reads the same file (D10). The work has five parts: the file and the recogniser; GIF and BMP through canonicalization, with tests; the front's check and the old loader on the file; the contract, the page and a test that holds them to the file (D12); a release of its own, verified on the domain (D9).

2. Background

Read from the code at 89d628a; Pillow's behaviour checked in the front's environment (Pillow 12.3.0).

  • Where GIF and BMP went. OPS-15 P1 (54b1b46, 2026-11-02) added the front's format check, webapp/front/upload_check.py. It accepts only the formats the public contract names, so "GIF, BMP and a plain TIFF are refused here, where the app's Pillow path decoded them" (the commit message; the plan's P1 entry, judgement call 1). The review left it so, and the owner closed OPS-15 knowing it (its Activity, 2026-11-02). No decision or ADR chose to drop them. The contract never named them.
  • Canonicalization already decodes both. coffeecv/canonical.py: _sniff sends anything that is not JPEG, PNG, JPEG XL, HEIF or a RAW extension to Pillow (line 93); that branch takes frame 0 (im.seek(0), line 210) and converts to RGBA when the image has transparency, else RGB (line 211); to_rec2020 lays transparent pixels over the fill grey (ML-19 D13, which absorbed ML-17). PHOTO_EXTENSIONS (line 303) lists .gif and .bmp.
  • Nothing tests it. tests/test_canonical.py canonicalizes no GIF or BMP, and dataset/ has neither. tests/test_front_upload_check.py asserts the opposite of this ticket: test_formats_the_contract_does_not_name (lines 99–102) checks that GIF and BMP are refused. Its accept test still decodes through photo_io.load_rgb_image, the path from before ML-19.
  • Where the contract names formats. webapp/static/llms.txt line 23, webapp/static/openapi.json (the photo part's description), the page's format chips and the inputs' accept lists (webapp/static/index.html; two inputs since OPS-17), the refusal message (_NOT_A_PHOTO in upload_check.py), and docs/inference_path.html, which says GIF and BMP are refused at the front.
  • The signatures. A GIF starts with GIF87a or GIF89a. A BMP starts with BM, and Pillow opens any file that does (BmpImagePlugin._accept); two bytes alone would let through many files that are not photos. The BMP info header's size, a 32-bit little-endian number at byte 14, is one of a few fixed values (12, 40, 52, 56, 64, 108, 124), so the check can read it too. All of this is inside the 64 bytes the check reads (HEAD_BYTES).
  • BMP is uncompressed, about 3 bytes a pixel, so the 40 MB cap lets in a BMP of about 13 megapixels; the 60-megapixel ceiling never binds. A BMP that Pillow writes from RGBA reads back as RGB; how a 32-bit BMP with an alpha mask from another tool decodes has not been tried.
  • The front's check is not the last word on decoders. Since ML-19 the front canonicalizes every upload (webapp/front/check_service.py), and an unreadable one is a 400 there (line 204), so what the check adds is keeping other formats away from a decoder on a public endpoint. But canonical.py calls Image.open with no formats= (lines 140 and 209), and Pillow 12.3.0, when a file passes one plugin's signature and then fails its parser, tries its other plugins in turn: 43 in all, TGA, PCX, PSD and EPS among them (Image._open_core). A file starting BM that is not a BMP would reach them. The same holds today for a file that passes the WebP or AVIF signature.
  • The dataset holds no GIF, BMP or TIFF: dataset/ has JPEG, HEIC, PNG and DNG only (2026-11-08), though PHOTO_EXTENSIONS lists .tif and .tiff. Intake (strip_metadata.PHOTO_EXTENSIONS) admits JPEG, PNG, HEIC/HEIF and RAW, and reports any other file as "not photos, left alone"; canonicalize_folder skips a file outside its list without a word.
  • The format knowledge is written several times, and it has drifted. upload_check.py tells HEIF and AVIF by the major or a compatible brand of the ftyp box, ten brands (_HEIF_BRANDS); canonical._sniff by the major brand only, eight (HEIF_BRANDS, no hevm, hevs, avif, avis). A HEIF with major brand hevm, or with heic among its compatible brands only, passes the front and then goes to Pillow's plain path, which cannot open it: a 400. RAW_EXTENSIONS has three copies (photo_io, canonical, upload_check), held equal by one test for two of them.

3. Before and after

Now

  • A GIF or a BMP upload gets a 400 at the front; canonicalization never sees it.
  • The page's picker hides GIF and BMP files, and the page, llms.txt and openapi.json name neither.
  • A test asserts that GIF and BMP are refused.

After

  • A GIF or a BMP passes the check, is canonicalized (an animated GIF as its first frame, D1), and is answered like any other photo.
  • The picker offers image/gif, image/bmp, .gif and .bmp; the page's format list, the refusal message, llms.txt and openapi.json name GIF and BMP, and llms.txt says an animated GIF is read as its first frame.
  • Tests hold the front to accepting both and canonicalization to decoding them: a still GIF, one with palette transparency, an animated one, and BMPs of 24 and 32 bits.
  • A plain TIFF is still refused (D2).

4. What does not change

  • Canonical photos. Canonicalization already decodes GIF and BMP. D4 narrows which decoders Pillow may try, which changes no accepted photo's pixels, so no re-canonicalization of the store and no retrain (ADR 0033).
  • The inference host and the models. They read canonical photos only.
  • The limits. 40 MB per upload and 60 megapixels, as for every other format.
  • A plain TIFF stays refused, for now (D2). Its signature is the one the TIFF-based RAW families share, which the check tells apart by extension; accepting it is a later ticket's question.

5. Risks

IDRiskEvidence and mitigation
R1A GIF holds at most 256 colours, usually dithered, and the models never saw one. dataset/ has no GIF. A GIF of beans may get a worse answer or be refused by the OOD guard. The answer is still the model's, so this costs nothing that a refusal does not. To measure it, the plan converts the four example photos (OPS-16) to GIF and compares their verdicts with the originals'. That is a record, not a gate (D6). A 24-bit BMP holds the photo's pixels exactly, so it carries no such risk.
R2OPS-17 changed the same lines of the page. OPS-17 (6789037, not yet on main) gives the page a second file input with its own accept list. This ticket's branch starts from main after OPS-17 merges and adds GIF and BMP to both lists.
R3A GIF's transparency or animation, or a BMP's alpha, decodes into something unexpected. The code path is read, not tested (section 2). New tests in tests/test_canonical.py: a palette GIF with a transparent index comes out over the fill grey; an animated GIF comes out as its first frame (D1); a 32-bit BMP with an alpha mask comes out as the test records, alpha over the fill grey or dropped.
R4BM is a weak signature. On its own it would let any file starting "BM" through to canonicalization, and from a failed BMP parse to Pillow's other decoders (section 2). D4 stops the second; the check also reads the info header's size, and a test feeds it a file that starts BM and is not a BMP.

7. Scope and acceptance

  • coffeecv/data/accepted_formats.csv: one row per accepted format (a row per RAW extension), with id, chip label, group, extensions, MIME types and decoder (D13–D15); GIF and BMP in it, no TIFF; in both releases' manifests.
  • One recogniser in canonical.py, one rule per row id, a test pairing rows and rules (D14, D17). GIF by GIF87a or GIF89a; BMP by BM and a known info-header size (R4); HEIF by major or compatible brand, the longer list (D18).
  • decode opens a file with its row's decoder only (Pillow with formats= that one format); a file that passes a rule and fails that decoder is Unreadable, never handed to another (D4, a test).
  • PHOTO_EXTENSIONS, every RAW_EXTENSIONS (canonical, upload_check, photo_io) and the refusal message come from the file (D10, D19, D20); canonicalize_folder reports a file that is not an accepted format and goes on (D16).
  • The front's check calls the recogniser (D3, D17). tests/test_front_upload_check.py: GIF and BMP accepted; a plain TIFF and a non-BMP file starting BM refused (D2, R4); a HEIF with a hevm major brand and one with heic as a compatible brand only accepted and decoded (D18); every accepted format decoded by canonical.decode, not photo_io (D7).
  • tests/test_canonical.py: a still GIF, a GIF with a transparent palette index, an animated GIF, a 24-bit BMP and a 32-bit BMP with an alpha mask canonicalize as D1 and ML-19 D13 say (R3).
  • llms.txt (with D1's first-frame note), openapi.json, the page's format chips (D5) and every accept list on the page name GIF and BMP; docs/inference_path.html says only a plain TIFF is refused.
  • A fast-tier test holds llms.txt, openapi.json, the page's chips and its accept lists to the file: every accepted format named, nothing else (D12).
  • The four example photos, converted to GIF, run through a local front and inference host; their verdicts are recorded beside the originals' (R1).
  • Live in a release of its own, after OPS-17's (D9), verified on the domain (--verify, per docs/agents/deploy.md): a GIF and a BMP sent with curl -F photo=@... each get a preview and a classification.

Out of scope

  • A plain TIFF (D2: refused for now).
  • Adding GIF or BMP photos to the dataset, or training on palette images (R1).
  • The page preparing a photo on the device (OPS-12, not merged).
  • Intake's own list, strip_metadata.PHOTO_EXTENSIONS (D10): it records what stripping is checked on.
