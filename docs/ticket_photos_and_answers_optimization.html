1. Summary

Stub. The question is what the page and the backend should pass to each other for one photo, and how many times the photo should travel. Nothing is proposed yet.

2. Background

Notes from OPS-6's web review, read at 214daa4; to be checked when the ticket is written.

  • Three uploads, three decodes. The page sends the original file to /preview, then to /crop, then to /classify. Each decodes it with load_rgb_image; /crop and /classify each run the segmenter (webapp/app.py, webapp/static/index.html).
  • Rough costs. The segmenter takes about 1.7–2 s on one thread for a 12–19 MP photo (analysis/ml2_p0/timing_devcontainer_t1.json). A curl from the devcontainer adds about 7 s of upload to /classify (deploy.md). Phone upload times are not measured.
  • Constraints. The app keeps no state between requests (webapp/app.py's docstring); the request log keeps no image bytes (docs/logging_plan.html); nginx allows one request in flight server-wide; a release ships its page and its backend together (ADR 0008).
  • Ideas raised, not assessed. Merge /preview and /crop into one answer (one upload fewer, but the photo shows only after the segmenter); hold the upload on the server for a short time under a token (fewer uploads, but server-side state and a privacy question); send the EXIF orientation so the page can show portrait photos upright.
