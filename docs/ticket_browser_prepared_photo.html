Ticket OPS-12 · coffee-vision · web page

The web page checks, turns, resizes, strips and re-encodes a photo on the visitor's device, and uploads that instead of the file

The owner asked that the page stop sending the visitor's file as it is: a file that is not an image should be refused before it is sent, a 200 MP photo or a RAW file should not travel at full size, and the photo's private metadata should not reach the server. The design was settled in one discussion with the owner on 2026-10-28 (D1–D19), and the plan's questions answered the same day (D20–D25). Planned in the plan; not implemented. Closed 2026-11-11 by the owner's decision that it will not be implemented (D26).

Owner request, 2026-10-28. As it is now, the visitor can select and upload any file, and it is parsed only on the server: a file that is not an image is reported only after the upload, an image can come in a very inefficient format such as BMP or DNG, and all the private information inside a photo goes to the server. A script should parse the file on the device; if it is a correct image, keep only the necessary part (the image and its orientation, perhaps the F-number and other metadata without private information), reduce the pixels (from 200 MP to at most 48 MP), encode them in an efficient modern format such as JXL with the metadata, show a first view in the browser and send that image to the server. The steps after it stay as now: the preview, the mask, the classification. TypeScript, not plain JavaScript.

1. Summary

Today the page posts the file the visitor picked to /analyze, and the server decodes it. After this ticket the page makes a prepared photo on the device and posts that; it falls back to the original file only when it cannot (D1). The page shows the local thumbnail at once, then redraws with the server's preview when it arrives (D6). The work splits into a WASM feasibility prototype on phones, a privacy and correctness harness, an evaluation that picks the JXL distance and proves the 90° turn harmless, the production page, and the deploy.

2. Background

Read from the code at 711d794 (main) and the design discussion of 2026-10-28.

  • A 200 MP photo fails on the site today. The web service keeps Pillow's decompression-bomb limit, 179 MP (commit 6185f45), and the Galaxy Z Fold8 Ultra's 200 MP photo is 16320×12240. Uploads are capped at 20 MB by nginx and Flask (MAX_UPLOAD_BYTES in webapp/app.py).
  • The server reads no metadata. load_rgb_image (coffeecv/photo_io.py) ignores EXIF, Orientation included, and the ICC profile; training reads photos through it too. The dataset's privacy rules are coffeecv/strip_metadata.py's deny list (DELETE_ARGS, DENY_GROUPS, DENY_TAGS, the GPS and serial-number pattern), checked by an exiftool audit (ADR 0013).
  • The models never saw a 90° turn. Spatial augmentation is a horizontal flip, a vertical flip and ±15° (params.yaml): the two flips make 180°, nothing makes 90°. Browsers apply Orientation when they decode, by default.
  • Resolution matters only down to a point. A classifier patch is 4–7 beans across and is stored at 448 px (patch_beans_min, patch_beans_max, patch_store_size), so a photo can shrink until its patches fall below 448 px, a bean pitch of about 64–112 px.
  • Browsers decode less than the server. No browser decodes RAW; Chrome and Firefox decode neither HEIC nor JXL (Safari decodes both). No browser encodes JXL or AVIF: canvas.toBlob gives JPEG, PNG and WebP. iOS Safari caps a canvas at about 16.7 MP, so a natively decoded photo above that cannot be read at full size through a canvas.
  • The page today (webapp/static/index.html) is one HTML file with an inline script, loads nothing from another origin, and accepts JPEG, PNG, WebP, HEIC, AVIF, JXL and ten RAW extensions. nginx sends no COOP or COEP header. The repo has no JavaScript toolchain.
  • Releases are built on the dev machine and copied to the VM (build() in scripts/deploy_webapp.sh), so a compiled page can be built there without Node on the VM.
  • This reverses part of OPS-7 D8 on purpose. D8 had the server send a JPEG thumbnail "so the browser never needs to decode HEIC/AVIF/JXL/RAW itself" (OPS-7; _preview_part in webapp/app.py). Here the browser decodes them. The server's thumbnail stays (D6). ADR 0023 (one upload, one streamed answer, nothing held) is unaffected.

3. Before and after

Now

  • The visitor's file goes to the server byte for byte, with its GPS, serial numbers and maker notes.
  • A file that is not an image is refused by the server, after the upload.
  • A RAW file or a 200 MP photo travels at full size; a 200 MP photo is refused.
  • Nothing is shown until the server's preview arrives.
  • The model sees the photo's stored pixels, unturned.

After

  • The server gets a prepared photo: upright, at most the cap, 8-bit, its ICC profile kept, lossy JXL, with the metadata the dataset's stripping would keep and nothing else.
  • A file that is not an image is refused on the device.
  • HEIC, JXL and RAW (DNG included) are decoded on the device, by the browser or by WASM.
  • The local thumbnail shows at once; the server's preview replaces it.
  • The original file is sent only when the page cannot prepare it, and the visitor is told.

4. What does not change

  • The endpoint and its answer. One upload to /analyze, the preview then the classification, nothing held (ADR 0023).
  • What the server accepts. Every format it decodes today, because the original file can still arrive (D1).
  • The models and training. load_rgb_image keeps ignoring Orientation and ICC; no retraining. Whether the prepared photo changes the model's answers is measured, not trained away (D17).
  • The server's limits. Pillow's limit and the 20 MB cap stay; an original file above them is refused as today.

5. Risks

IDRiskEvidence and mitigation
R1A phone runs out of memory or time on a large photo. A 48 MP RGBA buffer is 192 MB before the encoder's own memory; iOS kills a tab at roughly 1–1.5 GB. Plan P1 measures it on phones and sets the cap (D10); a failure falls back to the original file (D1).
R2A second lossy compression moves the model's answers. The models trained on the phones' own JPEG and HEIC. P3 measures the paired val/test effect per JXL distance (D17) before one is chosen (D5).
R3The 90° turn is input the models never trained on. Augmentation covers 180°, not 90° (§2). P3's turned arm measures it before shipping (D3).
R4The TypeScript deny list misses a private tag. The browser has no exiftool. P2 plants private tags in real photos of every format and runs strip_metadata's exiftool audit on the page's output in Chromium, Firefox and WebKit (D16).
R5A compromised JavaScript or WASM package. pnpm only, which runs no install script unless allowed by name (ADR 0038), a frozen lockfile, packages reviewed for build provenance and served from our own origin (D12).
R6The site and the CLI give different pixels for the same file. Accepted (D3, D5): the site classifies the prepared photo. coffeecv/infer.py's parity claim is reworded to say so.
R7A browser's native decoder turns or colour-converts the photo on its own, differently per browser. Turning, colour and resizing happen once, in our code (D9); P2's harness checks the result per browser engine.
R8The fallback still sends private metadata. Accepted (D1, D24), with a visible note (D14).

6. Decisions

IDQuestionOptionsOwner decision
D1Is privacy a guarantee or best effort? (a) The original file is never sent; a photo the page cannot prepare is refused. (b) Best effort: the original file is sent when the page cannot prepare one. (b), 2026-10-28: "best effort for now". Asked again after the prototype (plan Q5).
D2Which metadata does a prepared photo carry? (a) None. (b) A kept list, as KEPT_TAGS. (c) Everything the dataset's privacy stripping does not remove: its deny list, ported to TypeScript. (c), 2026-10-28: "any meta that is not stripped by privacy stripping code", over an allow list. The server ignores it for now; it may log some for debugging later, each field its own decision.
D3Which way up are the sent pixels? (a) Stored pixels, unturned, as training sees them. (b) Turned upright on the device. (b), 2026-10-28, with Orientation written as 1. Augmentation does not cover 90°, so before shipping the shipped recipe is evaluated on photos turned 90° (D17); the parity claim in coffeecv/infer.py is reworded.
D4Colour space? (a) Decode with no colour conversion and keep the ICC profile. (b) Convert to sRGB. (a), 2026-10-28: "keep color profile and ICC info". The pixel values stay those training reads; output is 8-bit, as load_rgb_image's.
D5How is the prepared photo encoded? (a) Lossless. (b) Lossy, high quality. (b), 2026-10-28: JXL, starting at distance 1.0. The final distance is chosen by the owner from P3: the crops compared by eye and the paired val/test metrics.
D6What does the page show, and what is it called? The image shown on the device before any answer, against the preview of OPS-7 D8. 2026-10-28: the first thing shown is the local thumbnail; it is always built, then redrawn with the server's preview when it arrives. The server's thumbnail stays in the preview. Both terms are in GLOSSARY.md.
D7Language and package manager? (a) TypeScript. (b) Rust to WASM. (c) Python in Pyodide. (a), 2026-10-28. Packages with pnpm, never npm, against supply-chain attacks (ADR 0038).
D8WASM or the browser's codecs only? (a) Browser codecs only: JPEG out, a cap of about 16 MP for iOS's canvas. (b) WASM codecs. (b), 2026-10-28: "we definitely will use WASM". WASM decoders for HEIC, JXL and RAW, DNG included; the browser's own decoder is tried first.
D9When is the native decoder used, and who resizes, turns and converts? (a) As below. (b) Leave them to the browser. (a), 2026-10-28: the native decoder only when it can hand over full-resolution pixels, else WASM (a large JPEG on iOS too); resizing with one fixed filter, turning and colour handling, each in one place in our code, never in createImageBitmap.
D10Resolution cap and time budget? A ceiling of 48 MP; the final cap is the least of 48 MP, what the slowest test phone prepares within budget, and what the pool's patch sizes need. 2026-10-28: "we will see numbers when we implement, any reasonable number is okay". Set in P1 (plan Q1); working budget about 5 s.
D11Threads in WASM? (a) COOP and COEP headers for SharedArrayBuffer, with a single-threaded fallback. (b) Single thread only. (a), 2026-10-28.
D12Where do the WASM codecs come from? (a) Published packages pinned by pnpm-lock.yaml. (b) Built here from C with Emscripten. (a), 2026-10-28, each package's build provenance reviewed; served from our own origin, never a CDN; each loaded only when a file needs it.
D13What are the two kinds of upload called? Prepared photo and original file. Adopted, 2026-10-28; in GLOSSARY.md. Every request line logs upload_kind: prepared or original.
D14How are non-images and fallbacks handled? A magic-byte check against the formats the server accepts; on a fallback, (a) silent or (b) a one-line note. The check, and (b), 2026-10-28; may change once the WASM work shows how often a fallback happens.
D15Where is the page built? (a) In deploy_webapp.sh's build(), into the release. (b) Compiled output committed. (a), 2026-10-28: TypeScript in webapp/page/, Node pinned, pnpm install --frozen-lockfile; compiled output never in git.
D16How is a prepared photo proved clean? Real photos of every format with private tags planted at test time, run through the TypeScript in headless browsers (Playwright), audited by strip_metadata's exiftool audit; Orientation, upright pixels and ICC bytes checked the same way. Adopted, 2026-10-28.
D17How are the JXL distance and the 90° turn evaluated? The shipped recipe's models at seeds 42, 123 and 7, unchanged; arms: original files, prepared photos at d = 0, 0.1, 0.5, 1.0, 1.5, 2.0, and d = 1.0 turned 90°; prepared by the shipping TypeScript in headless Chromium; paired val/test macro-F1 and per-class F1 (ADR 0002); a page of 100% crops for the owner's eyes. Adopted, 2026-10-28; d = 0.1 added by the owner ("if it is reasonable"), d = 0 by Claude as the reference that separates resizing and turning from compression. An arm that exceeds 20 MB is measured but cannot ship unless the limit changes.
D18Does the design get an ADR? (a) Now, proposed. (b) Not now. (b), 2026-10-28: "no ADR for now".
D19Order of work? Prototype on phones, privacy harness, evaluation, production page, the fallback asked again, deploy. Adopted, 2026-10-28; the plan.
D20The resolution cap (plan Q1)? The least of 48 MP, what the slowest phone prepares in budget, and what the pool needs. 48 MP, 2026-10-28: "48Mp for now, can be adjusted later."
D21How does the prototype reach the phones (plan Q2)? (a) The dev machine over HTTPS on the LAN, with a local CA (mkcert) the phones trust once. (b) An unlinked path on the live site. (a), 2026-10-28, as recommended.
D22Does RAW, DNG included, stay in the browser (plan Q3)? (a) Yes, where the phone can do it. (b) The original file. (a), 2026-10-28: "if possible, then yes". P1 shows where it is possible; elsewhere the original file.
D23JXL encoder effort (plan Q4)? A fixed effort, from P1's time and size per effort. 2026-10-28: "start with middle, then select after testing": effort 5 until P1's numbers pick one.
D24D1 asked again: when is a file refused rather than sent as the original file (plan Q5)? (a) Only a non-image. (b) Also any photo the page cannot prepare, making privacy a guarantee. (a), 2026-10-28: "if file is not an image". D1 and D14 stand.
D25The JXL distance (plan Q6)? Chosen from P3's paired results and crops. 2026-10-28: "start with d=0.5 and select after testing as planned": d = 0.5 from the prototype on, replacing D5's starting 1.0, until the owner picks from P3.
D26Implement this ticket? (a) yes, as planned (b) no: close it as not implemented (b), 2026-11-11: "write decision that this will not be implemented. And close ticket." Since it was written the server's front came to canonicalize every photo before the slow link (ML-19, ADR 0033; OPS-22, ADR 0036): turned upright, capped, re-encoded, without metadata; the visitor's file is still uploaded as it is. D1–D25 stand as the record of the design. ADR 0031 of this branch, pnpm, is renumbered 0038 (main's 0031 is another) and withdrawn; the four glossary terms it added are not merged.

7. Scope and acceptance

  • On the owner's test phones, a photo of every accepted format up to 200 MP becomes a prepared photo within the budget, or falls back with the note.
  • P2's harness is green in Chromium, Firefox and WebKit: no deny-listed tag survives, every tag the stripping keeps survives, Orientation is 1 and the pixels are upright, the ICC bytes are unchanged, a non-image is refused before upload.
  • P3's paired results are printed and the owner has chosen the distance and accepted the turn.
  • The page shows the local thumbnail, then the server's preview, then the classification; the request log has upload_kind.
  • The page is built from webapp/page/ with pnpm at deploy time and no compiled output is in git.
  • Deployed and verified live by docs/agents/deploy.md.

Out of scope

  • Training on prepared photos, or applying Orientation in load_rgb_image (D3 option c, not taken).
  • Raising the server's 20 MB or Pillow limit.
  • The server reading or logging any metadata field (D2).
  • Classifying on the device: the server still runs the models.
  • An ADR for the design (D18).
