1. Summary

Stub. A deploy installs the nginx site rendered from the release it deploys, but a rollback switches only the current and previous links, so the site stays the newest one. That holds while every release serves the same paths. OPS-7 changes the paths (/preview, /crop, /classify become /analyze), and from there a rollback runs the old app behind a site that does not route its endpoints. Nothing is proposed yet.

2. Background

Read at 6c45b78; to be checked when the ticket is written.

  • The site is rendered at deploy, not kept per release. render_production renders webapp/deploy/coffee-cv.nginx.conf.template from the deployed commit and installs it as /etc/nginx/conf.d/coffee-cv.conf when it changed; rollback_links swaps the links and restarts the service, with no nginx step (scripts/deploy_webapp.sh). The page already switches with the release, since nginx's root follows current.
  • The deploy's own rollback. A failed verify after a flip calls on_verify_failure, which rolls back the same way, and then verifies again.
  • Verify speaks one API. verify runs from the deploying checkout and posts to that checkout's endpoint, so after a rollback it checks the previous release with the new release's requests.
  • The rehearsal. scripts/rehearse_deploy_local.sh deploys origin/main~1, then origin/main, then rolls back and forward; it stubs nginx, so it never exercises the site. Across OPS-7 its rollback step cannot pass (OPS-7 D17).
  • Ideas raised, not assessed. Keep the rendered site inside each release and point nginx at current's copy (reload on every flip and rollback); or have the site route every path the kept releases serve; let verify read the release's own expected answer to pick its requests.
