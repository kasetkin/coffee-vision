Summary

coffee-cv-web.service runs gunicorn with WorkingDirectory=/home/alioth/coffee-vision and ExecStart=/home/alioth/coffee-vision-venv/bin/gunicorn. Training uses both of those paths too. Sweeps commit into that checkout after every fold, rewrite params.yaml, and are synced with git reset --hard. As a result, what production serves depends on the experiment's state at the moment the service last started. Because of this, and because both compete for the same 4 cores, the site has been switched off during every sweep. It has been off since 2026-09-20.

Evidence

Impact

  • No reproducible production state. A service restart mid-sweep, including an automatic Restart=on-failure, would import whatever coffeecv/ code and config the experiment has checked out at that moment.
  • Coupled environments. Installing or upgrading a package for training changes production. Pinning a package for the webapp can break training.
  • Downtime by design. The site gets switched off for every multi-day sweep (currently about 60 h).
  • Error-prone deploys. Deploys are an rsync into a working tree that is normally dirty, plus two manual steps (index.html copy, nginx re-render) that fail silently when skipped. There is no rollback.

Root cause

The VM was set up as a training box first. The webapp was later deployed with a single rsync into the same checkout, and the service was pointed at that checkout and venv to save setup work. Nothing afterwards separated them again.

Proposed fix

ADR 0008: the webapp serves immutable releases.

1. Python environment with uv

ADR 0007: uv manages every Python environment.

uv (by Astral) replaces pip and requirements*.txt for the webapp only. The training venv is not touched.

  • webapp/pyproject.toml lists what the 13 release modules import (R4), including torch and torchvision. Every version equals what pip freeze reports in the production venv today (torch 2.13.0+cpu, torchvision 0.28.0+cpu). Transitive packages such as werkzeug and jinja2 are held to the same freeze with constraint-dependencies. In the sketch below, ‹prod› marks a version to copy from that freeze.
  • opencv: declare exactly one of opencv-python and opencv-python-headless, since both install the same cv2/ package. The headless build has the same image processing without the libgl1 system dependency. Keep it only if the pre-cutover comparison is identical; otherwise use the build production has now.
  • torch and torchvision come from the PyTorch CPU index through [tool.uv.sources] (R3). environments restricts the lock to Linux x86_64, so uv does not try to find +cpu wheels for macOS or Windows.
  • timm keeps its current --no-deps behaviour through [[tool.uv.dependency-metadata]], which declares timm 1.0.29's requirements without huggingface_hub/safetensors. The service still never downloads anything.
  • Commit webapp/uv.lock. It records a hash for every artifact and uv verifies each one on install, which replaces --require-hashes. The deploy uses --locked, not --frozen: --frozen installs from the lock without checking that it still matches pyproject.toml, while --locked refuses when it does not.
  • required-version pins uv itself. uv is installed as one pinned binary at /usr/local/bin/uv on the VM, checked by sha256 against the checksum published with that uv release, and at the same version locally, where uv lock runs.
# webapp/pyproject.toml (sketch)

[tool.uv.sources]                    # without this, explicit = true means "never used"
torch = { index = "pytorch-cpu" }
torchvision = { index = "pytorch-cpu" }

[[tool.uv.dependency-metadata]]      # timm minus its download-only dependencies
name = "timm"

Each release gets its own .venv, built on the VM at the release's final path (R2):

export UV_CACHE_DIR=/opt/coffee-cv/uv-cache UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
export UV_PROJECT_ENVIRONMENT=/opt/coffee-cv/releases/$ID/.venv
cd /opt/coffee-cv/releases/$ID
uv sync --project webapp --locked --no-dev --compile-bytecode --python /usr/bin/python3.12
.venv/bin/python -m compileall -q coffeecv webapp
  • UV_LINK_MODE=copy gives every release its own copy of every package file (R7). On ext4 this is what uv does anyway after a failed clone; setting it explicitly records the choice and silences uv's fallback warning. Nothing is shared with the cache or with another release, so a rollback target cannot be changed by accident. The cost is about 1 GB per venv (torch alone is 750 MB, measured on the same versions locally), bounded by keeping only two releases (§4 step 8). The cache still saves the downloads: a deploy with an unchanged lock copies from it and needs no network.
  • --python /usr/bin/python3.12 and UV_PYTHON_DOWNLOADS=never keep the interpreter out of /home (R8) and identical to the one production runs today.
  • --compile-bytecode and compileall write the .pyc files the service is not allowed to write itself (R14).
  • Rolling back then restores code, model, frontend and packages together.
  • On the VM these commands never run directly in the SSH shell. They run inside a sandboxed, resource-capped transient unit (§6).

3. Remove the home-directory dependency

For inference, build the ResNet18 backbone with weights=None (a flag passed from coffeecv/infer.py:264). Training keeps ImageNet initialisation. load_model calls load_state_dict with its default strict=True (coffeecv/infer.py:265), so the checkpoint overwrites every parameter and BatchNorm buffer. The acceptance check is therefore bit-identical logits on a fixed image set, not merely close ones. After this change the release no longer needs ~/.cache. Together with R8, that is what lets ProtectHome=true work.

4. Deploy script: scripts/deploy_webapp.sh <git-ref> <model-name>

Runs locally and drives the VM over SSH. Also: --stage-only (steps 1–3, no flip), --rollback, --verify (step 7 alone), --bootstrap (creates /opt/coffee-cv, installs the pinned uv). Every VM step follows §6, so the script is safe to run while a sweep trains.

  1. Build from the ref, locally. Resolve <git-ref> to a commit sha, and refuse one that is not on main (R15). git archive <sha> the manifest's git-tracked paths: code, frontend, environment files, model sidecars including .pt.dvc, and models_pretrained/manifest.json. The working tree plays no part except as a source for the two untracked files:
    • models/<name>.pt, from the working tree or the local DVC cache (.dvc/cache/files/md5/<aa>/<rest>). Refuse if its md5 differs from the one in the ref's .pt.dvc.
    • For DINOv3, the backbone .pth. Refuse if its sha256 differs from the one in the ref's manifest.json.
    Write BUILD_INFO.json from the sha (write_build_info.py gains --ref and --model, since today it stamps the working tree's HEAD) and release.env.
  2. Stage in place. rsync to /opt/coffee-cv/releases/<id>/, the final path (R2), with --copy-dest pointing at the current release: unchanged files such as the 343 MB DINOv3 weights are copied on the VM instead of sent over the network again, and still end up as independent copies, like the venv. Build the venv there (§1), inside a capped unit (§6). Check the directory against the manifest, then write .complete last.
  3. Smoke-test inside the real sandbox. Render the unit template with RELEASE_DIR=/opt/coffee-cv/releases/<id>, PORT=8001, LOG_DIR=/var/log/coffee-cv/smoke into /run/systemd/system/coffee-cv-smoke.service (R13), plus a drop-in that adds only the resource limits from §6, so its sandboxing stays identical to production's. Then start it. Record time-to-ready, which must stay well under 30 s because gunicorn's --timeout also covers worker boot (R14). POST a known photo to /classify, /crop and /preview. Top-1 must match the expected result exactly, and scores and model_sha must agree, with scores allowed to differ by up to 1e-4 (R18). While a sweep is running, the timings are recorded but not gated, because the caps throttle the smoke on purpose; --verify gates them later. Stop the unit, then delete it, its drop-in and the smoke log directory.
  4. nginx. Render the nginx template. If the output differs from the installed file, back that file up, install the new one and run nginx -t; restore the backup if the test fails. This happens before the flip, so a bad config cannot leave a half-switched site.
  5. Flip. Point previous at the old target. Then ln -sfn releases/<id> current.new && mv -T current.new current, and reload nginx if its config changed.
  6. Restart coffee-cv-web, but only if it is enabled. While it is disabled (the owner's off switch, as now), the script stops after the flip and prints systemctl enable --now coffee-cv-web followed by deploy_webapp.sh --verify (R17).
  7. Verify. Backend, on 127.0.0.1:8000: GET / → 404, GET /classify → 405, and the startup journal line shows the expected model_sha and commit from BUILD_INFO.json. Public site (R6): GET https://$DOMAIN/ → 200 with a body whose sha256 equals the release's index.html, and one POST /classify of the known photo returns the expected top-1. Retry that once on 503, since nginx allows one request in flight. If any check fails, roll back automatically.
  8. Prune. Keep only current and previous, the one-command fallback. Delete every other release, including any without .complete. Run uv cache prune. A deploy therefore holds at most three releases, the new one being built plus the two kept, and two at rest. The release the running process uses is always one of the two kept.

Rollback: deploy_webapp.sh --rollback swaps current and previous, restarts, and runs step 7. The model (release.env) and the page (webapp/static) follow the symlink, so nothing outside the release has to change.

5. Service unit changes

One template renders both production and the smoke unit, so their hardening cannot drift apart (R13):

WorkingDirectory=$RELEASE_DIR
EnvironmentFile=$RELEASE_DIR/release.env     # the model travels with the release (R1)
Environment=PYTHONDONTWRITEBYTECODE=1 COFFEE_CV_LOG_DIR=$LOG_DIR
ExecStart=$RELEASE_DIR/.venv/bin/gunicorn -w 1 --worker-class sync \
    -b 127.0.0.1:$PORT --timeout 30 --no-control-socket webapp.app:app
ProtectHome=true          # was read-only; nothing under /home is needed any more
ReadWritePaths=/var/log/coffee-cv

Production renders RELEASE_DIR=/opt/coffee-cv/current, PORT=8000, LOG_DIR=/var/log/coffee-cv. systemd resolves current when the service starts. A running process stays on the release it started from until it is restarted, because coffeecv.config.REPO_ROOT is built with Path.resolve(). The nginx template changes root to /opt/coffee-cv/current/webapp/static (R12).

Releases are owned by alioth (the deploy user) with modes 0755/0644. ProtectSystem=strict already stops the service from writing to them. Optional hardening: run the service as a dedicated coffee-cv system user. Its benefit is that a compromised worker could no longer signal or ptrace the training jobs, which also run as alioth (R10). If adopted, the service user becomes a template variable separate from $APP_USER, and logrotate's su line and the ownership of /var/log/coffee-cv follow it.

6. Deploying while a sweep runs

Everything up to and including the flip can run while a sweep trains, including the running exp232–239. The service stays off until the owner turns it on (R17). That leaves four ways the deploy could reach the sweep: files, memory, CPU and disk. Each one is bounded by the kernel, not left to care:

ResourceGuaranteeHow
FilesNothing of the sweep's is ever written: ~/coffee-vision, ~/coffee-vision-venv, ~/sweep.log, ~/sweep_status.log, ~/.cache. Every VM step that runs code (uv sync, compileall, the pre-cutover comparison, the smoke) runs as a transient systemd unit with ProtectSystem=strict and ProtectHome=read-only (the smoke: true). Only /opt/coffee-cv is writable (plus /var/log/coffee-cv/smoke for the smoke). The other steps (mkdir, rsync, the symlink flip, rendering units) write fixed absolute paths under /opt/coffee-cv, /run/systemd/system and, at the flip, two files in /etc.
ProcessesNothing the sweep runs is signalled, restarted or reloaded. The sweep is not a systemd unit. daemon-reload and an nginx reload act only on their own units, and coffee-cv-web is not started while it is disabled.
MemoryAn overrun kills the deploy step, never the sweep. MemoryMax=3G and MemorySwapMax=0 on every unit, so the OOM killer acts only inside that unit's cgroup. The page cache from writing about 1.5 GB is charged to the unit as well, so it cannot push the sweep's cached training images out of memory. Preflight refuses to start unless MemAvailable is at least 5 GB.
CPUAt most 1 logical CPU for builds and 2 for the smoke, about 10 minutes in total. CPUQuota=100% / 200%: a hard cap that holds across cgroups, unlike nice, which only ranks threads inside one scheduling group. The sweep's 4 threads keep their 4 cores, and the deploy lands on their SMT siblings. That can slow the sweep for those minutes, but it does not change the sweep's results, which depend on the sweep's own thread count, and nothing here changes that.
DiskThe sweep cannot run out of space because of a deploy. Preflight refuses unless /opt has at least 10 GB free. On this VM's single disk it is the filesystem the sweep writes its checkpoints to.

Each code-running step on the VM looks like this, shown for the venv build:

sudo -n systemd-run --wait --pipe --collect --uid="$USER" --gid="$USER" \
    -p ProtectSystem=strict -p ProtectHome=read-only -p PrivateTmp=yes \
    -p ReadWritePaths=/opt/coffee-cv \
    -p CPUQuota=100% -p MemoryMax=3G -p MemorySwapMax=0 --nice=19 \
    --working-directory=/opt/coffee-cv/releases/$ID \
    -E UV_CACHE_DIR=/opt/coffee-cv/uv-cache -E UV_LINK_MODE=copy -E UV_PYTHON_DOWNLOADS=never \
    -E UV_PROJECT_ENVIRONMENT=/opt/coffee-cv/releases/$ID/.venv \
    /usr/local/bin/uv sync --project webapp --locked --no-dev --compile-bytecode --python /usr/bin/python3.12

The smoke gets the same limits through a drop-in, /run/systemd/system/coffee-cv-smoke.service.d/limits.conf, with CPUQuota=200%, MemoryMax=3G and MemorySwapMax=0. The pre-cutover comparison runs the old venv's interpreter with python -B, so reading that venv writes nothing into it.

Never run during a sweep

  • The current setup_server.sh. It pip-installs into ~/coffee-vision-venv, the venv the sweep runs from (setup_server.sh:58-60). It runs apt-get install nginx, which upgrades nginx whenever a newer version is available. And it runs systemctl enable --now coffee-cv-web (setup_server.sh:92), which would start the site against the owner's decision. Its /opt and uv steps move into deploy_webapp.sh --bootstrap, and the pip step is deleted, since the webapp no longer uses the training venv.
  • A second remote_launch.sh with its default paths. Its first action is rm -f ~/sweep.log ~/sweep_status.log (remote_launch.sh:37). That deletes the live sweep's log, and the second launch's exit code would then look like the sweep finishing. The deploy never calls it.
  • apt, reboots, and anything that writes under ~/coffee-vision*. That includes git commands that move the VM's checkout (merge, pull, checkout): §7's VM step runs only after the sweep has ended.

Proof after each run

Before its first VM step and after its last, the deploy records the sweep's PIDs (pgrep -f 'run_folds|train_baseline') and the size of ~/sweep.log, and prints both. The same PIDs still running and a log that kept growing show the run left the sweep alone. If the sweep finished on its own in between, its SWEEP_DONE_EXIT line says so.

Phases

  • A, during the sweep: --bootstrap, --stage-only, the pre-cutover comparison, then the full deploy up to the flip. That means the new unit rendered but left disabled, nginx root moved to the release (R12), and current flipped. The public site behaves exactly as it does now: the page loads and /classify answers 502.
  • B, whenever the owner chooses: systemctl enable --now coffee-cv-web, then deploy_webapp.sh --verify. This is safe for the sweep's files even mid-sweep. Its only cost is CPU while a request is being served: an idle site costs nothing. When both are busy, requests and the sweep share the CPU with no priority either way (out of scope).

7. Git history: bringing the VM's commits home

ADR 0009: simple merges only.

The sweep commits one experiment per fold into the VM's own main. A read-only fetch on 2026-09-27 found 3 commits the local repo does not have: exp232–234 (c6aedc4, 996eac6, 2959468), with exp235–239 still to come. They branch off 7cd4c7e. Locally, 680e6a9 on main and the 7 dino-integration commits were made after that point. OPS-1 itself never commits on the VM and never reads its checkout, so this section only keeps the training history in one piece. It does not block Phase A.

Only simple operations: fetch, merge (a fast-forward or one merge commit), temporary tmp/* branches, and stash for leftovers on the VM. No rebase, cherry-pick, reset --hard, amend or force-push. Those either rewrite commit hashes or discard work, and experiments/index.csv records the commit each run was trained on (exp234 → 996eac6, exp253 → 6bdfdb1). A rewritten hash leaves that record pointing at nothing, which is how 22 provenance commits were lost in early September.

# 0. Now, local, only if R15 = YES
git switch main
git merge --ff-only dino-integration             # main just moves forward 7 commits

# 1. After exp239 has finished (SWEEP_DONE_EXIT in ~/sweep_status.log), local
git fetch powervpsssh main:tmp/vm-sweep          # the VM's commits as a local branch
git switch -c tmp/merge-sweep main               # rehearse on a copy; main does not move yet
git merge -m "Merge exp232-239 (ResNet18 seeds 123/7) from the VM" tmp/vm-sweep
#   no conflict expected (rehearsed). If index.csv conflicts anyway: keep every row,
#   in exp order, then  git add experiments/index.csv && git commit --no-edit
#   run the checks below, then:
git switch main
git merge --ff-only tmp/merge-sweep              # main moves only now
git branch -d tmp/merge-sweep tmp/vm-sweep
git push origin main                             # with the owner's OK

# 2. The VM catches up: a fast-forward, nothing rewritten
git push powervpsssh main:tmp/from-local         # a branch the VM does not have checked out
#   then on the VM, in ~/coffee-vision:
git status --short                               # leftovers? diff them against the last commit
git merge --ff-only tmp/from-local               # if it refuses over leftovers: git stash push -u, retry
git branch -d tmp/from-local

Checks before main moves

  • git diff --stat main tmp/merge-sweep lists only files the sweep writes: experiments/, params.yaml, dvc.lock, outputs/. Nothing in coffeecv/ or webapp/.
  • experiments/index.csv has no conflict markers and has every row from both sides: exp232–239 and exp252–254.
  • Every git_commit in those rows resolves: git cat-file -e <sha>^{commit}.

If a check fails, git switch main, delete the scratch branch with git branch -D tmp/merge-sweep, and start again from the merge. main never moved.

Notes

  • Why no conflict: step 1 was rehearsed on 2026-09-27 in a throwaway worktree, merging the fetched exp232–234 into dino-integration, and it merged cleanly. experiments/index.csv is the only file both sides changed, but it is kept in experiment order: the VM's rows go between 231 and 240 and the local ones after 251, so the changes never touch. exp235–239 will land in the same gap. params.yaml, dvc.lock and outputs/*.json come from the VM unchanged, since nothing local changed them. params.yaml keeps the last fold's seed and held-out rig, as after every sweep (557ab27).
  • The VM step: it is a fast-forward because local main already contains every VM commit, and it replaces the old reset --hard sync recipe. --ff-only refuses if the VM made a commit we don't have; in that case, run step 1 again.
  • DVC: the merge brings dvc.lock, which points at the new fold checkpoints. The checkpoint files stay in the VM's DVC cache until the DVC remote is back and the VM runs dvc push. Until then, local dvc status reporting them as missing is expected.
  • If R15 is NO: skip step 0. After step 1, also run git switch dino-integration and git merge main, so the deploy branch gets the experiment records too.
  • Every future sweep: the VM starts equal to main, because step 2 of the previous round left it there. After the sweep, run steps 1–2 again. If local main did not move during the sweep, step 1's merge is a plain fast-forward with no merge commit.
  • During a sweep: only read-only fetches. git fetch powervpsssh main updates powervpsssh/main so results can be read locally, and changes nothing on the VM.
