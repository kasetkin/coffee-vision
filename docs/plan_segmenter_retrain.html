Implementation plan: XL0-v3 on the enlarged segmenter dataset

The order of work for ticket ML-6. There are five strands: append the photos, label the new positives, move the fine-tune's augmentation to Albumentations on the fly (D12), fine-tune and compare, and follow through. The append comes first. It is the only step that changes nothing about any model, and it ends the deploy refusal on its own. The first step that changes a number is the XL0-v3 fine-tune (P6). Everything runs on this host (the one ML-5 P8–P11 ran on), not on a remote machine (D9, owner 2026-10-12).

1. Phase order and why

P1 only appends to a file and reruns predictions that must come back identical. Nothing in it changes a model, and it unblocks deploys. P2 is optional (D2) and only measures. P3 and P5 are code and can run alongside P1 and P4. P4 is the owner's labelling. P6 is the first step that produces a new number, and the long one: about 7 h under Q4's recommendation. P7 and P8 end at the owner's choices. Predictions keep the pinned 4 threads of every seg_ml5_predict stage, so the v2 and v3 test masks are made the same way.

7. P5 — On-the-fly Albumentations in seg_finetune

StatusOpen not started
Blocked byD12, D16 (decided); D5 if (b)

The fine-tune stops reading an embedding cache. At the start of a run it loads every training photo and label once, verifies each photo's sha256 against the session's labels.csv, and resizes it to the encoder's frame with the serving code's own resize. It holds them in memory: about 1.5 GB for about 520 photos at 1024 px. Each sample is augmented when it is drawn, then encoded by the frozen encoder under no_grad, and the decoder takes its step. Nothing augmented is written anywhere. The validation photos are not augmented. They are encoded once per run and held in memory (about 0.25 GB), so checkpoint selection stays deterministic and cheap. Point prompts are still drawn from the error region of the augmented sample's box-only prediction, so no keypoint transform is needed.

  1. Test-first, in tests/test_seg_finetune.py:
    • a spatial transform moves the label with the photo (a forced horizontal flip equals np.fliplr on both);
    • a pixel transform leaves the label unchanged;
    • a warp's exposed border is 255 in the label, and the loss ignores it;
    • one seed gives one stream of batches, and another seed gives another;
    • no file is written during training apart from the model and its card.
  2. params.yaml: seg_ft.views gives way to seg_ft.augment, the Q5 pipeline as a list of {transform, arguments, p}. It is built by name from albumentations and seeded from the run's seed. The card records the pipeline and the albumentations version. NO_ALBUMENTATIONS_UPDATE=1 is set before the import, so neither training nor the tests touch the network. pyproject.toml pins albumentations==2.0.8, the MIT release, and not AlbumentationsX.
  3. Retire the custom code: VIEWS, the cache command and the memory-mapped cache reader. In dvc.yaml, seg_ml5_cache@pass1, @pass2, seg_ml5_finetune@xl0_v1 and @xl0_v2 become frozen: true, as ML-2's stages are. A comment names the last commit with the cache code. The seg_ml5_predict stages stay live.
  4. If D5 is (b): the score's negative term becomes the mean of the per-batch empty-or-tiny shares, each batch read from the dataset file by path. Test-first.
  5. ADR for D12, in /domain-modeling's format: segmenter fine-tunes augment on the fly through albumentations and store no augmented data. It binds later fine-tunes, and the ticket's D12 links it.
  6. Delete data/seg_cache_ml5/pass1 and pass2 once the freeze is committed (D13).
  7. Toy-scale run (CODING_STANDARDS.md, "Proving a change" and "Run the real entry point"): the stage's own command, python -m coffeecv.seg_finetune train, with 1–2 epochs on about 16 pass-2 photos at 8 threads, under a scratch name that is not committed.
