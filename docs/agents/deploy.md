# Deploying the webapp

Read before a deploy, a rollback, or a claim that something is live. Usage is in `scripts/deploy_webapp.sh`'s header (`--help`); the design is [ADR 0008](../adr/0008-webapp-serves-immutable-releases.md) and OPS-1.

- **The host is `webappremote`** (the script's default `HOST`; `APP_USER` is its SSH user), since the VM `powervpsssh` was shut down for good on 2026-10-12. nginx there serves TLS on port 12346 only (`PUBLIC_PORT`), behind a proxy that serves the domain on 80/443 and forwards to it; the live site is `https://<DOMAIN>/`. Until it is set up (`setup_server.sh`, the TLS files, then `--bootstrap`; `webapp/README.md`, "Deploying"), the site is down.
- **Only pushed commits deploy.** The script deploys commits on `origin/main`. Push when the owner asks: a plain `git push origin main` uses the devcontainer's key, `/workspace/.private_ssh/coffee-vision-devcontainer`, set as this clone's `core.sshCommand`. If a push fails with `Permission denied (publickey)`, that setting is missing: run `.devcontainer/link-private-ssh.sh`, which sets it (and links `~/.ssh` to `.private_ssh/`).
- **A model ships with its OOD probe** (`models/<name>.ood_probe.json`, [ADR 0016](../adr/0016-ood-guard-probe-at-fixed-half.md)), fitted to that checkpoint.
- **And with its LiteRT conversion** (`models/<name>.litert/`, the `litert_export` stage; [experiments.md](experiments.md), "Converting a candidate for serving"): the release serves it, not the `.pt`, and the build refuses a model without it in `dvc.lock` and the local DVC cache. The first release of a new model name uploads its ~780-820 MB in full (55 min to `webappremote` on 2026-10-17, about 14 MB/s): the upload reuses a file already on the host only at the same path, so a new name re-sends graphs byte-identical to the live release's (ML-8, 2026-10-20, where only `head.npz` differed).
- **The host's memory does not fit a smoke worker beside the live one** ([OPS-10](../ticket_deploy_memory_headroom.html)). The preflight asks for `MIN_MEM_GB` (5) of MemAvailable; beside the live GPU worker `webappremote` has about 3.6 GB (of 7.7 GB, 1 GB swap), and a worker costs about 3.3 GB of it, its GPU buffers as shared memory included (2026-10-20). Until OPS-10 is decided, deploys stop the live service by hand (the owner's choice in OPS-7): `sudo systemctl stop coffee-cv-web` on the host, then the deploy with `DEPLOY_SKIP_CHECK=1` if the full check passed on that commit; the full deploy restarts the service after the flip, and a failure before the flip needs `sudo systemctl start coffee-cv-web` by hand. Photo answers are down meanwhile, the page stays up. The script has no upload-only step (`--stage-only` runs the same preflight, then smokes), so a new model name's upload falls inside the outage. In ML-8 P8 the service was started again after the first minutes and the staged files sent with the script's own rsync command into the incomplete release directory, site up; the rerun's upload then took 4 s and every file's digest was checked, and the outage for `--stage-only`, `--compare` and the deploy was about 7 minutes. An upload-only step is OPS-10's to decide.
- **The gates hold the release to PyTorch, not bit for bit** ([ADR 0020](../adr/0020-converted-models-pass-d7-before-they-serve.md)): the smoke test checks the GPU proof in the worker's boot record, and `--compare` runs PyTorch here (the training environment, `TORCH_PY`) against the release on the host under D7's bars. `--compare` refuses unless this checkout's `coffeecv/` is the release's.
- **"Deployed" means verified on the live site**: `scripts/deploy_webapp.sh --verify` (needs `DOMAIN`) or a real request to the domain, not a successful restart. A restart succeeding once hid a service that crash-looped right after.
- **Latency**: quote the server-side `latency_ms` from the app's log, and for `/analyze` (OPS-7) `preview_ms` beside it, when its preview went out: on `webappremote`'s GPU `/analyze` took `latency_ms` 8.4-8.9 s with `preview_ms` 2.1 s (OPS-7 P5, 2026-10-18); `/classify` took about 7 s idle and 12.5 s during a sweep on the retired VM (OPS-1). A `curl` from this container adds about 7 s of upload and is not server latency.
- **Rehearse locally** with `scripts/rehearse_deploy_local.sh` before changing the deploy script itself.
- Rollback is `--rollback`, which switches the host to the `previous` release.
