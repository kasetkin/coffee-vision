# Deploying the webapp

Read before a deploy, a rollback, or a claim that something is live. Usage is in `scripts/deploy_webapp.sh`'s header (`--help`); the design is [ADR 0008](../adr/0008-webapp-serves-immutable-releases.md) and OPS-1, and since OPS-15 [ADR 0031](../adr/0031-the-front-and-the-inference-host.md).

- **Two hosts, one release** ([OPS-15](../ticket_front_and_inference_host.html), live 2026-11-02). **The front** is the proxy that serves the domain, `webproxy-deploy` (`FRONT_HOST`, as `coffee-deploy`; `webproxy` is the owner's root alias, never the deploy's): TLS, the page, the one-at-a-time gate, the 5 MB cap (10 MB from OPS-16's release, D8) and the upload check (`coffee-cv-front`, on `127.0.0.1:8100`), its site on `127.0.0.1:12347` behind the proxy's `stream {}` block. **The inference host** is `yappy`, `webappremote` (`HOST`; `APP_USER` is its SSH user): the app, behind nginx in plain HTTP on its tailnet address, port 12346, only. A deploy needs `DOMAIN`, `TLS_CERT` and `TLS_KEY`, the proxy's certificate files: `TLS_CERT=/opt/my-ssl/kasetkin.com-ssl-bundle/domain.cert.pem TLS_KEY=/opt/my-ssl/kasetkin.com-ssl-bundle/private.key.pem`. A fresh front is prepared once by the owner with `webapp/deploy/setup_front.sh`, a fresh inference host with `setup_server.sh` then `--bootstrap` (`webapp/README.md`, "Deploying").
- **Only pushed commits deploy.** The script deploys commits on `origin/main`. Push when the owner asks: a plain `git push origin main` uses the devcontainer's key, `/workspace/.private_ssh/coffee-vision-devcontainer`, set as this clone's `core.sshCommand`. If a push fails with `Permission denied (publickey)`, that setting is missing: run `.devcontainer/link-private-ssh.sh`, which sets it (and links `~/.ssh` to `.private_ssh/`).
- **A model ships with its OOD probe** (`models/<name>.ood_probe.json`, [ADR 0016](../adr/0016-ood-guard-probe-at-fixed-half.md)), fitted to that checkpoint.
- **And with its LiteRT conversion** (`models/<name>.litert/`, the `litert_export` stage; [experiments.md](experiments.md), "Converting a candidate for serving"): the release serves it, not the `.pt`, and the build refuses a model without it in `dvc.lock` and the local DVC cache. The first release of a new model name uploads its ~780-820 MB in full (55 min to `webappremote` on 2026-10-17, about 14 MB a minute; 13-15 MB a minute on 2026-10-29): the upload reuses a file already on the host only at the same path, so a new name re-sends graphs byte-identical to the live release's (ML-8, 2026-10-20, where only `head.npz` differed; ML-13, 2026-10-29, where 795 of 816 MB were identical). [OPS-13](../ticket_deploy_upload_by_content.html) proposes reuse by content; until then, ML-13's deploy copied the identical graphs on the host by hand (its Activity).
- **A deploy stops the live service** ([ADR 0026](../adr/0026-a-deploy-stops-the-live-service.md), the owner, 2026-10-20): the host's memory does not fit a second worker beside the live one ([OPS-10](../ticket_deploy_memory_headroom.html)); beside the live GPU worker `webappremote` has about 3.6 GB of MemAvailable (of 7.7 GB, 1 GB swap), and a worker costs about 3.3 GB of it, its GPU buffers as shared memory included (2026-10-20). The script does it (`make_room`): only once everything the release needs is on the host (every file uploaded and checked against its digest, the venv built, the release complete, the fixtures sent), it stops `coffee-cv-web` for the smoke, and for `--compare`'s run on the host, then requires `MIN_MEM_GB` (5); it refuses before stopping anything if stopping could not free that. `--stage-only` and `--compare` start the service again when their run is done, a full deploy restarts it on the new release after the flip, and any failure or interrupt before the flip starts the old release again. Photo answers are down meanwhile (say so before a deploy), the page stays up: for a full deploy the smoke, the flip and the restart (ML-8's full deploy step, reusing a staged release, took under 2 minutes end to end), and again for each `--stage-only` smoke and `--compare` run before it. A new model name's long upload runs with the site up. Keep `MIN_MEM_GB` at 5: a lower bar would let a smoke worker start beside the live one. If a deploy dies without its trap running (a killed shell, a lost link), check `systemctl is-active coffee-cv-web` on the host and start it by hand.
- **The gates hold the release to PyTorch, not bit for bit** ([ADR 0020](../adr/0020-converted-models-pass-d7-before-they-serve.md)): the smoke test checks the GPU proof in the worker's boot record, and `--compare` runs PyTorch here (the training environment, `TORCH_PY`) against the release on the host under D7's bars. `--compare` refuses unless this checkout's `coffeecv/` is the release's.
- **A new live model updates the docs that name it** in the release's change: `docs/status.md` (the live model, its numbers, the one it replaced) and `docs/inference_path.html` (its scope line, and any step the model changes; `CODING_STANDARDS.md`, "A serving change updates the serving path page").
- **"Deployed" means verified on the live site**: `scripts/deploy_webapp.sh --verify` (needs `DOMAIN`) or a real request to the domain, not a successful restart. A restart succeeding once hid a service that crash-looped right after. `--verify` checks both hosts: the front's `current` is the inference host's, the check service answers, the app's startup line names the release's commit and `model_sha`, and through the domain the page is the release's and `/analyze` answers both parts with the expected top-1. `PUBLIC_URL=` (set but empty) skips only the checks through the domain.
- **`systemctl reload nginx` succeeds even when the new config cannot bind**: it only signals the master, which logs `bind() ... (98: Address already in use)` to `/var/log/nginx/error.log` and keeps serving the old config. A change of a site's listen address needs `systemctl restart nginx`. OPS-15's first deploy moved `yappy`'s site from `0.0.0.0:12346` (TLS) to its tailnet address: the reload kept the old site, the host-local checks passed, and only the public `POST /analyze` showed it (a 301 to HTTPS from the old site), until a restart (2026-11-02). A deploy whose listen addresses do not change reloads cleanly; its public check would catch a stale site and revert.
- **The first two-host deploy** ran with `PUBLIC_URL=`, since the proxy's stream still sent the domain to `yappy`'s old port; then the owner pointed the stream's `server-coffee` upstream at `127.0.0.1:12347` and included `/etc/nginx/coffee-cv-stream.conf`, and `DOMAIN=... --verify` passed (2026-11-02). Measured then: a photo about 14 s end to end through the domain from this container, its preview line at about 9.8 s; the 5 MB cap's 413 in 0.1 s at the front; the check service's RSS at most 28 MB during a photo, with the proxy's `MemAvailable` no lower than 158 MB.
- **Latency**: quote the server-side `latency_ms` from the app's log, and for `/analyze` (OPS-7) `preview_ms` beside it, when its preview went out: on `webappremote`'s GPU `/analyze` took `latency_ms` 8.4-8.9 s with `preview_ms` 2.1 s (OPS-7 P5, 2026-10-18); `/classify` took about 7 s idle and 12.5 s during a sweep on the retired VM (OPS-1). A `curl` from this container adds about 7 s of upload and is not server latency.
- **Rehearse locally** with `scripts/rehearse_deploy_local.sh` before changing the deploy script itself.
- Rollback is `--rollback`, which switches both hosts to their `previous` release together, and refuses if either has none. **Until the second OPS-15 deploy the front has no `previous`**, so `--rollback` refuses; going back to the release from before OPS-15 (`d9212c6`, `yappy`'s `previous`) is by hand: on `yappy`, swap `current` and `previous`, copy `conf.d/coffee-cv.conf.pre-ops15` over `conf.d/coffee-cv.conf`, `nginx -t`, then **restart** nginx (the old site binds `0.0.0.0:12346`, which a reload cannot take from the tailnet address) and `coffee-cv-web`; the owner points the proxy's `server-coffee` upstream back at `yappy`'s port 12346.
