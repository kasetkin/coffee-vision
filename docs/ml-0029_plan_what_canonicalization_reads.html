Implementation plan: what canonicalization reads from an original

The order of work for ticket ML-29. Two strands, as the ticket has them. Part 1, read correctly (P1 to P6), comes first and ships in two releases: the standard-range colour declarations, which is the owner's darktable path (D6), then HDR main images once a tone-mapping operator is chosen. Part 2, use more (P7 to P11), is the gain-map experiment, offline until the owner adopts it. No phase of Part 1 changes a dataset photo; the first step that can change a model's number is P10's retrain.

  1. No new files from the owner. 2026-11-14: "I will not provide new exports from Darktable or new profiles. Work with data that you have or use the internet to get more info about PQ and HLG, get example photos if needed." Recorded as the ticket's D25. The five profiles not exported, and PQ and HLG in AVIF and HEIC, are made here: the darktable JPEG XL's own pixels re-encoded with the other declaration (imagecodecs.avif_encode and jpegxl_encode take primaries and transfer; pillow-heif has an x265 encoder, its coded tag on writing to be checked in P1), plus public samples (finding 5). What darktable itself writes for the five missing profiles stays unchecked; D5 reads every header declaration, so the answer does not change the work.
  2. Every change to canonical.py re-runs the store. It is a dependency of each canonicalize, segcrop and segmenter stage in dvc.yaml, so a change re-runs them all, as ML-28 did after its 12-bit fix and ML-25 after OPS-22. That re-run is the proof Part 1 needs: every output must come back byte-identical. To pay for it once per release, the new code is written in its own modules first (P1, P4, P7), which no stage depends on until P2, P5 and P11 wire them in.
  3. The front's colour path is the integer one (FRONT_SETTINGS, OPS-22 D4, ADR 0036): LittleCMS's optimized transform on the source's own 8- or 16-bit samples. A linear, PQ or HLG source at 8 bits through an integer lookup loses its shadows. Q1.
  4. The libraries are already there (R7). imagecodecs.avif_decode returns the 10-bit darktable AVIF as uint16 with white at 1023, where Pillow's plugin gives 8 bits; pillow-heif returns a HEIC's coded tag as nclx_profile; imagecodecs 2026.10.10 bundles libavif 1.4.2 and libultrahdr 2.0.2 (ultrahdr_decode gives linear float). No new dependency is expected; each use is checked in its phase, on the three machines' locks (ML-19 D41).
  5. Public HDR and gain-map samples exist. libavif's tests/data lists 35 such files, each with its licence in that folder's README: HDR main images (seine_hdr_rec2020.avif, colors_hdr_p3.avif), a standard-range image with a gain map as AVIF and as JPEG (seine_sdr_gainmap_srgb), an HDR main image with a gain map down to standard range (seine_hdr_gainmap_srgb.avif, the layout no dataset photo has), and Apple gain-map JPEGs. The same scene in several forms is a second test rig beside the darktable exports. Q4.
  6. Dataset intake compares a JPEG XL's pixels as canonical._decode_jxl reads them (strip_metadata.py, ML-28 D4), so intake follows the decoder: a float or newly read JPEG XL has to pass its pixel comparison too (D23). Folded into P2.

1. Phase order and why

The reader and the profile builder come first as a module nothing calls (P1), so they can be tested on all 22 exports without touching a DVC stage. P2 wires in the standard-range declarations, and its store re-run proves no dataset photo moved. HDR main images wait for the operator (P4, the owner's pick), because a tone curve chosen later would change those photos' canonical bytes twice. Part 2 starts only after the operator exists, since D11 uses the same one for gain maps, and runs entirely beside the store until P11.

3. P1 — the colour-declaration reader and the profile builder, not wired in

StatusIn progress 2026-11-14: the reader, the builder and their tests done; the 22 exports read as recorded; the files made here (D25) in progress
Blocked byNone

One new module, coffeecv/colour_declaration.py, with one small interface: a file's bytes and its accepted format in, its colour declaration out (the kind, the primaries and white point as xy, the curve), or the reason it cannot be converted. A second function turns a declaration into what the conversion needs: the curve undone in our own code, then a linear RGB profile with the declared primaries and white point (ic.cms_profile), so one builder serves every curve, PQ and HLG included (D20). Nothing calls it yet, so no DVC stage moves.

  1. The readers, in D4's order of precedence: an ICC profile; the coded tag of a HEIC's, HEIF's or AVIF's main image (its own colr boxes by item association, the reader of analysis/ml29/scan_dataset.py moved here) and of a PNG (cICP, then sRGB); a JPEG XL header, with jxl_header._customxy keeping the coordinates (D5); a JPEG's R03 (D8); a BMP's embedded ICC profile (D7). "Unspecified" is no declaration; PNG gAMA and cHRM and BMP endpoints are not read.
  2. The builder: sRGB, BT.709, linear, explicit gamma and DCI curves, any primaries and white point. PQ and HLG are recognised and marked HDR; their rendering is P4's and P5's.
  3. The test files (D25), in tmp/: the five profiles darktable did not export, and PQ and HLG as AVIF and HEIC, re-encoded from the darktable JPEG XLs' pixels; each read back from its bytes and added to analysis/ml29/README.md's table as made here, not by darktable. Whether pillow-heif writes a coded tag is checked; if not, HEIC keeps the owner's six files.
  4. Tests, test first, on small files made in code: each declaration kind, the precedence (an ICC profile beside a coded tag, a coded tag alone, "unspecified", R03), custom primaries, a reserved coded value as a refusal, the legacy fields ignored.
  5. Checks: on the owner's 22 exports and the files made here, the declaration read equals what analysis/ml29/README.md records; the builder's sRGB and Display P3 profiles convert within one 16-bit rounding step of LittleCMS's own sRGB and of the dataset's Display P3 ICC profile (R2); no file under coffeecv/ that a DVC stage depends on has changed.

4. P2 — standard-range declarations wired into decode

StatusIn progress 2026-11-14: code, tests and texts done; the store re-run running
Blocked byP1 Q1, Q2 answered

canonical.decode asks P1's module for the declaration and no longer falls back to sRGB on its own. A PQ or HLG declaration is refused in this phase with a message that says so; P5 lifts that. This is the phase that re-runs the store (finding 2).

  1. decode for every format: the declaration by precedence; a declaration that cannot be converted raises Unreadable naming it (ADR 0040). A photo with a usable ICC profile, or with no declaration, takes exactly today's path.
  2. JPEG XL: every standard-range header declaration (D5); float samples converted unclipped, values above white clipped for now, values outside the gamut clipped after the conversion (D21); an embedded ICC profile still refused, with its message (D22).
  3. AVIF decoded at its own depth (D9): imagecodecs.avif_decode, after checking it against Pillow's plugin on an 8-bit AVIF for orientation (irot, imir), transparency and the pixels; accepted_formats.csv's decoder column and ADR 0034's rule kept.
  4. The front: Q1's path for a built declaration; a 15 MP linear Rec.2020 upload timed and its memory read against the front's budget.
  5. Intake: strip_metadata's JPEG XL pixel comparison follows the new decode (finding 6).
  6. The texts: openapi.json, llms.txt, the refusal message and webapp/README.md say what is read; the tests that hold them updated. dvc.yaml's stages gain the new module as a dependency.
  7. Checks: the owner's standard-range exports and the files made in P1 each land within Q2's tolerance of the 8-bit sRGB export, the three misread today among them; every canonicalize and segcrop stage re-run with every output byte-identical (docs/agents/dvc.md first); scan_dataset.py's "read today as" column unchanged under the new rule; scripts/check.sh --full green.

6. P4 — tone-mapping research; the owner picks the operator stop

StatusOpen not started
Blocked byP1 Q4 answered; can run beside P2 and P3

D11 as a measurement, with the data in hand (D25). The result is a research note, analysis/ml29/research_tone_mapping.md, a prototype module coffeecv/tone_map.py that nothing calls, and a recommendation the owner accepts or changes.

  1. The primary sources read and cited by section: ITU-R BT.2100 (the PQ and HLG curves, HLG's system gamma), BT.2408 (reference white at 203 nits), BT.2390 (the roll-off for PQ), ISO 21496-1 and the Ultra HDR and Apple gain-map descriptions (for P7), and what libjxl, libavif and libultrahdr do when asked for a standard-range rendering.
  2. What darktable did: from the PQ and HLG JPEG XLs against the sRGB one of the same photo, the light level its standard white was written at and how much of the picture lies above it.
  3. The public samples (finding 5) fetched into tmp/, each file's licence line and URL recorded; none committed (Q4).
  4. Candidates, each a pure function on linear light: reference white to white with a clip; a BT.2390-style roll-off; a scale by the peak; one more if the sources name a better one. Each run on three sets: the darktable PQ and HLG files (JPEG XL, and the AVIF and HEIC of P1) against the sRGB export; the public same-scene HDR and standard-range pairs; a sample of dataset gain-map photos per camera, the map applied by a throwaway reader.
  5. The report: per candidate and set, the difference from the standard-range reference in 8-bit levels (mean, worst block), what happens in the bean region, side-by-side crops; the proposed operator and the proposed tolerance for HDR files (Q2).
  6. Stop for the owner: the operator and its tolerance, recorded as the ticket's next D-number.

9. P7 — the gain-map reader, not wired in

StatusOpen not started
Blocked byP4

A new module, coffeecv/gain_map.py: a file's bytes in, its gain map and what it means out (the map, its parameters, which way it leads), or none. Applying it gives linear light above white, which P4's operator brings back. It sits behind a setting that is off, so the store and the front do not change.

  1. The readers, ISO 21496-1 first (D14): the ISO form in a JPEG, in a HEIC's tmap item and in an AVIF; then Ultra HDR's hdrgm; then Apple's auxiliary image with its headroom. For each, the bundled library (libultrahdr, libavif) is tried before our own arithmetic, and kept only if it gives the unclipped linear result.
  2. Both directions: a map up from a standard-range main image (every dataset photo), and a map down from an HDR main image (the public sample), each ending in the same canonical photo form (D10).
  3. Tests, test first, on files made in code with ultrahdr_encode and on synthetic maps: a flat map is a pure brightness change; a zero map changes nothing; orientation follows the main image.
  4. Checks: on the 208 dataset files that carry both forms, the ISO result against the vendor map's, the differences reported (R5); the public samples read; the setting off, the store's bytes and the suite unchanged.
