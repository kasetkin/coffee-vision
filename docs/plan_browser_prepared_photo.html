Implementation plan: the web page prepares the photo on the device

The order of work for ticket OPS-12. Four strands: whether phones can do the work at all (WASM decode, resize, JXL encode), whether the result is clean (the privacy harness), whether the model minds (the paired evaluation), and the production page with its build and deploy. Feasibility comes first because its numbers set the cap every later phase uses; the first step that changes a number is P3's evaluation.

Built from a read of the code at 711d794 and the design discussion behind the ticket. 2 things the ticket does not cover turned up. They are folded in below, and the one that needs a decision is Q2 (§2).

  1. Cross-origin isolation needs a secure context. SharedArrayBuffer (D11) works only over HTTPS or on localhost, so a prototype served from the dev machine to a phone over the LAN gets no threads. Q2.
  2. Planted private tags cannot be committed. The pre-commit leak check refuses a file with GPS or an email address, so P2's fixtures are planted at test time into temporary copies, never stored.

1. Phase order and why

P1 decides whether WASM on a phone can prepare a 48 MP photo at all, and sets the cap (Q1) and the JXL effort (Q4) that P2–P4 use. P2 proves the output clean before any prepared photo is measured or served. P3 then measures what the prepared photo costs the model and is the only phase that changes a number. P4 builds the production page on the settings P3 chose; P5 is the owner's check on phones; P6 deploys.

3. P1 — WASM feasibility prototype and the pool's resolution check stop

StatusOpen not started
Blocked byNone Q2 answered

A throwaway page that does the whole preparation and reports its numbers, plus the toolchain the production page will keep. Nothing is uploaded; nothing in the live page changes.

  1. Toolchain in webapp/page/: package.json, pnpm-lock.yaml, Node pinned, TypeScript, one bundler; pnpm's install-script allow list empty unless a codec needs one, each such entry named (ADR 0038). Node and pnpm in the devcontainer. Compiled output ignored by git (D15).
  2. Codec packages for HEIC, JXL (decode and encode) and RAW, each reviewed for build provenance and recorded with version and source (D12); single- and multi-threaded builds (D11).
  3. The chain: native decode when full-resolution pixels are available, else WASM (D8, D9); turn by Orientation; resize to a given MP with one fixed filter; JXL encode at a given distance and given effort, starting at d = 0.5 and effort 5 (D23, D25). A readout of each step's time, the peak memory where the browser reports it, and the output's size.
  4. Pool resolution check (Python): for each pool photo, the bean pitch at full resolution and the smallest MP at which its smallest patch (patch_beans_min × pitch) stays at or above patch_store_size; the distribution, and the share of photos that would fall below at 12, 16, 24 and 48 MP.
  5. Serve the prototype to the phones as Q2 says; run it on a JPEG, HEIC and DNG of the dataset at 12, 24 and 48 MP, and the 200 MP photo, each at efforts 3–7, in Chromium and Safari on the dev machine first.
  6. Stop for the owner: run it on the test phones (the Fold8 Ultra, an older iPhone, a mid-range Android); the owner confirms or moves the 48 MP cap (D20), says whether RAW stays in the browser (D22) and picks the effort (D23).

4. P2 — Privacy and correctness harness

StatusOpen not started
Blocked byP1

D16: the exiftool audit stays the one guarantee; the TypeScript deny list is an implementation it checks.

  1. The TypeScript deny list, ported from coffeecv/strip_metadata.py (DELETE_ARGS, DENY_GROUPS, DENY_TAGS, the GPS and serial-number pattern): EXIF and XMP copied into the JXL less what it removes, the ICC profile kept as bytes, Orientation written as 1 (D2, D3, D4).
  2. Fixtures at test time: one real photo per format the server accepts, from the dataset or made from one, copied to a temporary directory and given GPS, serial numbers, owner fields, maker notes, C2PA and a thumbnail by exiftool; never committed.
  3. Playwright (installed with pnpm) runs the preparation in Chromium, Firefox and WebKit; Python checks each output with strip_metadata's audit and also: every tag the stripping keeps survives, Orientation is 1, the pixels match the source turned upright within JXL's error, the ICC bytes are equal, the output is 8-bit; a non-image is refused by the magic-byte check (D14).
  4. The harness in scripts/check.sh, in the tier that runs real-data tests.
  5. Checks: the harness green in all three engines; a planted tag deliberately left in makes it fail.

5. P3 — Paired evaluation of the JXL distance and the 90° turn stop

StatusOpen not started
Blocked byP2, Q1, Q4

D17, read under docs/agents/experiments.md and ADR 0002: the models do not change, only their input.

  1. The models: the recipe of the model in the live release, at seeds 42, 123 and 7. If it lacks one of them, stop and ask.
  2. Prepared val and test photos made by the shipping TypeScript in headless Chromium, at the cap (Q1) and effort (Q4), for each arm: d = 0, 0.1, 0.5, 1.0, 1.5, 2.0, and d = 1.0 turned 90° from upright. Each arm's file sizes recorded; an arm above 20 MB is measured but marked unshippable.
  3. Each seed's model classifies the original files and every arm through classify_one's path; code committed before the run, the changed path run at toy scale first.
  4. A page of 100% crops of about a dozen photos, the original beside each distance, for the owner's eyes.
  5. Stop for the owner: per seed, val and test macro-F1 for the original files and each arm, the paired deltas, their mean and range, per-class F1; the owner answers Q6.
