Implementation plan: the front's faster canonicalization

The order of work for ticket OPS-22. Three strands: the shared module learns a second set of settings without changing the store's (P1), the front uses them and re-encodes every upload (P2), and the deploy's checks and the docs follow the new path (P3), before a release the owner starts (P4). P1 changes no number; P2 is the first to change one, and only on the front.

  1. --verify's public /analyze expects the store's answer. It posts the smoke photo's original through the domain and compares its top-1 with the answer the staged app gave locally on canonical_fixtures' canonical photo, made with the store's settings (scripts/deploy_webapp.sh, canonical_fixtures and the public check). After P2 the domain's photo is the front's, so the two can differ. Q1; P3.
  2. A changed example answer rolls the release back, after the site went down. example_check.py fails a release whose example gets another country (OPS-16 D14), and a full deploy's failed verify reverts it, after the smoke and the flip have stopped photo answers. Under D5 the examples are the only check of the answers, so their answers on the front's photos are worth knowing before the deploy. Q2; P3.
  3. The pass-through lives in two places. canonical.canonicalize returns a canonical photo as it is, and so does check_service.canonicalize (is_canonical, logged as_sent). The store's tools, the fixtures and make_example_photos.py rely on the first; D3 removes only the second. P1, P2.
  4. A canonical upload is re-encoded from 16 bits. decode reads a canonical JPEG XL through _decode_jxl whole, at 16 bits, as Rec.2020; the integer path then converts Rec.2020 to Rec.2020. That is OPS-22 R3's 467 MB for the grinder example. P2 measures it under the front's MemoryMax=600M if this machine can hold a process to it, and P4 reads it on the front.
  5. libjxl's bytes on the front. ML-19 P1 found the front's files byte-identical to this machine's at efforts 3–7 (both AMD; analysis/ml19/p1/README.md), so expected answers computed here on the front's settings (Q1, Q2) describe the front's photos; P3 checks it once on the smoke photo.

1. Phase order and why

P1 adds the settings to the shared module with the store's as defaults: the store's tests, the golden file and a byte comparison against data/canonical/ prove it changes nothing. P2 is the first to change a number: the front's photos, in tests only. P3 makes the deploy check the front's path and writes the docs. P4 releases it, when the owner asks, since a deploy stops photo answers.

3. P1 — the settings in the shared module, the store's unchanged

StatusDone 2026-11-10, 16f73ef
Blocked byNone

One frozen dataclass, canonical.Settings: the colour path (float or integer), effort, quality, and the two thresholds (kept up to, capped to). STORE holds today's values (float, 7, 95, 60,000,000, 50,000,000) and is every function's default; FRONT holds D1's (integer, 3, 90, 18,000,000, 15,000,000). The module's constants stay as the store's, so header_problems' 60 MP limit, which the inference host applies, does not move.

  1. capped_size, _cap and decode take the thresholds from a Settings (D1: over 18 MP to at most 15 MP for the front); encode takes the colour path, effort and quality; canonicalize and its pass-through stay the store's (finding 3).
  2. The integer colour path (D4): for a source without transparency, LittleCMS's default (optimized) transform from the source's own integers, grey spread to RGB, its profile or sRGB, into Rec.2020 uint16, relative colorimetric, one call per rectangle libjxl asks for. A source with transparency keeps to_rec2020's float path, which lays it over the fill grey (ML-19 D13).
  3. Tests: STORE is the module's defaults; capped_size under both settings (18,000,000 kept, 18,000,001 capped to at most 15,000,000, the shape kept); the integer path within one 8-bit level of the float path's conversion, before the encode, for 8-bit, 16-bit, grey and tagged-P3 sources.
  4. Checks: ML-19 D8's tests and the golden file pass unchanged; ten originals from dataset/, a HEIC, a DNG and a 50 MP photo among them, canonicalized with the defaults are byte-identical to their files in data/canonical/ ("a rewrite is checked against the original").
