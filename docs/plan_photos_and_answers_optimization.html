Implementation plan: one upload per photo

The order of work for ticket OPS-7. Four strands: classify_one split into a segment step and a classify step; the /analyze endpoint with its streamed two-part answer; the deploy's smoke, verify and nginx site moved to it; and the page. Then the deploy. The split comes first because the endpoint is built from its two steps, and it is proved bit-identical before anything uses it. No phase changes a classification number.

Built from a read of the code at 6c45b78, not from the ticket alone. Eight things the ticket does not cover turned up. The owner settled the ones that needed a decision while planning (ticket D7–D17); the rest are folded in below.

  1. The segmentation /crop needs and the one /classify needs are reached through two different functions. bean_region_preview returns the full photo's mask, and segment_bean_region returns the cropped photo and its mask. Both call _segment, whose segment_and_crop result holds both. The decode happens inside patches_for_photo. P1 adds one segment step that returns everything both parts need. patches_for_photo keeps its signature, since ood_eval, export_litert, analysis/ml7_gpu/ and tests/test_seg_parity.py call it.
  2. The warm-up runs the segmenter twice, once in bean_region_preview and once in classify_one. After P1, a single classify_one call covers every graph, so ADR 0021 still holds and the boot gets about one segmenter pass shorter.
  3. The 400 has to be decided before streaming starts. P2 decodes and segments before it returns the response, so an unreadable photo is still a plain 400, and a segmenter crash is still the error handler's 500. Only the classification runs inside the stream. A ValueError from patch sampling, which today's classify_one also turns into "unmeasurable", now arrives as a classification part with verdict refused_unreadable, because the 200 has already gone out (R4).
  4. after_request runs before a streamed body (R2). P2 writes the log line from the stream's own finally, with the fields captured as it runs, so the stream ending and the client dropping out each produce one line. X-Request-Id is still set in after_request.
  5. nginx hides X-Accel-* response headers from whatever is in front of it by default. The app's X-Accel-Buffering: no would only reach our own nginx, never the nginx in front of the domain. P3 adds proxy_pass_header X-Accel-Buffering (ticket D11).
  6. The nginx site is not part of a release, so a rollback across this release takes the site down (ticket R8). Accepted in D10, with no undo (D16) and no rehearsal (D17). The fix is OPS-9.
  7. index.html is reached by internal redirect (index and try_files in location /). P3 sets no-cache in an exact location = /index.html, which both redirects land in, so / and every fallback path get the header.
  8. Places that name the old endpoints: webapp/app.py's docstring and its static_folder comment; infer.warm_up's docstring; photo_io.py's comment; release_probe.py (smoke and compare_smoke); the smoke and verify in scripts/deploy_webapp.sh, including the final "nothing serves /classify" message; the comment in fixtures.txt; the nginx template; tests/test_webapp_crop.py, tests/test_release_manifest.py (whose trace posts to all three) and tests/test_release_probe.py; webapp/README.md; deploy.md; and the TODO(crop editing) comment. Each moves in the phase that owns its file. analysis/ml7_gpu/baseline_stages.py groups the log by endpoint and simply sees /analyze as a new key, so it is left as is.

1. Phase order and why

P1 touches only coffeecv/infer.py and proves its answers unchanged. P2 builds /analyze from P1's two steps and removes the old routes. On this branch the page and the deploy tooling then lag behind until P3 and P4, which can run in either order after P2. Each phase's tests move with the code they test, so the suite is green at every phase's last commit. P4 stops for the owner to accept the page; P5 stops for the owner's go to deploy.

3. P1 — the segment step and the classify step

StatusOpen not started
Blocked byNone

coffeecv/infer.py only. Today classify_one calls patches_for_photo, which decodes, finds the bean region, measures the pitch and samples patches, and then runs the model and the OOD guard. After P1 it calls two steps, which /analyze will call one at a time with the preview sent in between (ticket R3).

  1. The segment step, segment_photo(path, cfg, skip_crop=False, segmenter=None). It returns a small dataclass: the decoded photo, its size, the full photo's bean mask (None on a fallback, on skip_crop and for a tray-heuristic model), the photo and mask to sample from, crop_info, the segmenter's diagnostics, and the decode and crop_detect timings. It calls _segment once and takes both masks from that one result. It covers the tray-heuristic branch (crop_to_bean_region) and skip_crop as patches_for_photo does today, and it raises load_rgb_image's ValueError / OSError unchanged.
  2. The classify step, classify_segmented(seg, cfg, class_ids, class_labels, classifier, ref, n_patches, seed_key, tta, probe, ood_method): the pitch, the sampling, the patches, the model and the OOD guard, which is the rest of today's patches_for_photo and classify_one. A ValueError from the sampling half gives "REFUSED (unmeasurable)", exactly as today.
  3. patches_for_photo becomes segment_photo plus the sampling half, with the same signature and the same returns. classify_one becomes segment_photo (a decode error gives "unmeasurable") plus classify_segmented. segment_bean_region stays, since the segcrop parity test calls it.
  4. warm_up runs classify_one only, and its docstring says why that covers every graph (finding 2).
  5. Checks: release_probe.py classify on the 13 fixtures (smoke and compare), CPU LiteRT, before and after the change, compared with compare-classify at no tolerance (bit for bit). On the same photos, segment_photo's full mask equals bean_region_preview's (checked before P2 deletes it). python -m coffeecv.infer on two photos prints the same before and after. tests/test_seg_parity.py and the full suite are green.

4. P2 — /analyze and its streamed answer

StatusOpen not started
Blocked byP1

webapp/app.py. One POST /analyze (D7), with the form fields photo and skip_crop as /classify takes them today. Its answer is application/x-ndjson, one JSON object per line (D2, D8).

  1. Before the response: "no photo uploaded" gives a 400 as today. The upload goes through _saved_upload into segment_photo, and the temporary file is deleted before streaming starts, since the decoded photo is in memory. A decode failure gives _log_decode_failure and a 400 JSON (R4). The preview line is built here too: the thumbnail as /preview made it (long side ≤ PREVIEW_MAX_DIM, JPEG quality 85, base64), the mask by _mask_png_b64, and box / cropped / needs_review / seg_fallback as /crop made them. For skip_crop, mask and box are null and cropped is false (D9).
  2. The stream (stream_with_context, header X-Accel-Buffering: no, D11) yields {"part": "preview", ...} and notes preview_ms (D13). It then runs classify_segmented, maps the entry with _entry_to_response (the body only, since the status has already gone out) and _log_classify_fields, and yields {"part": "classification", ...body}. An exception after the preview is logged as _log_unhandled logs one, and yields {"part": "error", "message": "Something went wrong -- try a different photo."} (R4).
  3. The log line (R2, finding 4): for a streamed answer, _log_request only sets X-Request-Id. The generator's finally writes the one line, with status 200, the whole latency_ms, preview_ms, the classify fields and skip_crop. It also writes how the answer ended (ticket D19): outcome is complete after the classification part, error after an error part, and client_gone when the generator is closed before it finishes (GeneratorExit); parts_sent counts the lines written. preview_ms, outcome and parts_sent join _JsonFormatter._FIELDS and the field list in _log_request. The rules don't change: no image bytes, no client IP.
  4. Remove the /preview, /crop and /classify routes (D5), and bean_region_preview along with its import once nothing calls it. The module docstring, the static_folder comment and photo_io.py's comment name /analyze.
  5. Tests: tests/test_webapp_crop.py becomes tests/test_webapp_analyze.py, keeping its mask checks on the preview part (the photo's mask scaled down, long side ≤ 1024, palette index 1 opaque, the Orientation tag ignored by the mask and the thumbnail alike, an empty mask falling back to no mask). New checks: exactly two lines, preview first; the classification part equals _entry_to_response(classify_one(...)) on the same photo; skip_crop=1 gives a preview with null mask and box, then a classification; an unreadable file gives a 400 JSON and no stream; no file gives a 400; a classify step that raises (mocked) gives an error line; one log line per request, with the classify fields, preview_ms ≤ latency_ms and skip_crop; outcome and parts_sent are complete/2 on a normal answer, error/2 on the mocked failure, and client_gone/1 when the test client's unbuffered response is closed after the preview line (D19). tests/test_release_manifest.py's trace posts /analyze.
  6. Checks: the full suite is green, including --full. On the local dev server (python -m webapp.app, COFFEE_CV_LITERT_ON_CPU=1), curl -N with a timestamp per line shows the preview line arriving before the classification ends (ticket scope, R1 on the dev server).

5. P3 — the deploy's smoke, verify, nginx site and docs

StatusOpen not started
Blocked byP2

Everything the deploy runs moves to /analyze. The deploy only ever talks to releases from this ticket on, so none of it speaks the old API (D10).

  1. release_probe.py smoke posts the smoke photo to /analyze once through the test client and emits its status, content type and two parts (preview, classification). compare_smoke compares the classification as it compares /classify today (verdict, top-1, SCORE_TOL). It compares the preview as it compares /crop today: the mask decoded with IoU ≥ MASK_IOU_MIN, the rest within 1e-3. The thumbnail is left out of that diff and checked on its own: it decodes as a JPEG of the same size as the local one, long side ≤ 1024. The module docstring follows.
  2. The smoke in scripts/deploy_webapp.sh: one curl to /analyze, its lines tagged for compare_smoke (SMOKE_ANALYZE with status and time, then one tagged line per part), SMOKE_LOG grepping "/analyze", and the summary lines reading the classification part.
  3. verify: the backend GET /analyze gives 405. The public POST /analyze (with the one retry on a 503) gives 200, two parts and top-1 as expected. With curl -N it reports the time to the preview and the time to the classification through the domain, failing on neither (D11). The messages that name /classify (the final "NOT enabled" message, on_verify_failure) name /analyze.
  4. The nginx template: one location = /analyze with the in-flight cap, client_max_body_size 20m, proxy_read_timeout 30s, proxy_pass, the two proxy_set_header lines and proxy_pass_header X-Accel-Buffering (finding 5), and proxy_buffer_size 1m with a comment on why (ticket D18, R9): with buffering off, nginx still reads up to that much from the backend ahead of the client, so the whole answer leaves the worker at once and a slow phone waits on nginx, not on gunicorn. The three old locations go. A location = /index.html with add_header Cache-Control "no-cache" (D5, finding 7). The comments on the cap follow. coffee_cv_minimal gains $upstream_bytes_received at the end of the line (D19), so a worker killed mid-answer shows as a 200 with a short answer; nothing parses that log, and webapp/README.md's log section names the field.
  5. fixtures.txt's comment says the smoke photo goes to /analyze. tests/test_release_probe.py runs compare_smoke on synthetic two-part answers: the mask cases it has today, plus a thumbnail of the wrong size, a missing part and an error part.
  6. Docs: webapp/README.md (the diagram, the endpoint section, the smoke and verify lines) and deploy.md name /analyze. deploy.md's latency line names preview_ms next to latency_ms.
  7. Checks: the full suite is green. bash -n scripts/deploy_webapp.sh. The smoke's own curl lines, run against the local dev server, are compared by compare_smoke with release_probe.py smoke's output from the same checkout, which exercises the real parser on both sides.
  8. The stream through two nginx servers (ticket D18, R1, R9). nginx is installed in the devcontainer for this check only (it is not there now; not added to the image). Our template, rendered with a throwaway self-signed certificate in place of the host's, sits in front of the dev server; a second nginx with a stock proxy_pass stands in for the proxy in front of the domain. Both pass nginx -t. Through both, curl -N with a timestamp per line shows the preview before the classification. With --limit-rate 20k it still does, and the request log's latency_ms minus preview_ms stays within the unthrottled run's spread over a few runs; without proxy_buffer_size 1m the same run shows that gap growing, which proves the check can fail. Nothing of this setup goes into the repo.

webapp/static/index.html. One button, one upload, and the answer read as it streams in. The overlay's drawing (renderOverlay, drawBeanRegion, "Show outline") is unchanged (OPS-6 D3, D4, D9, D14).

  1. Remove the Classify button. A pick posts the file to /analyze and reads res.body with a reader and a TextDecoder, splitting on newlines. On the preview part, the thumbnail goes into #preview as a data URL and the mask is decoded first, so the photo, the box and the bean region appear together. The classification part goes to render, and an error part to renderRefused. A stream that ends without a classification shows "Could not reach the server" (R4).
  2. A non-OK answer before the stream starts: a 503 shows "The server is busy with another photo -- try again in a few seconds." (D12). A 400 shows its error. A failed fetch shows "Could not reach the server".
  3. A rotating progress circle (CSS only) shows from the pick until the preview, then under the preview until the classification (D3). Choose Photo is disabled from the pick until the classification or a failure (D4). The upload token (OPS-6 D13) stays as a guard.
  4. "Use full photo instead" (D1) appears after a classification, unless that answer was skip_crop or seg_fallback. Pressing it clears the result, hides the overlay and the button, and keeps the preview with the circle under it, Choose Photo disabled (D14). It then posts the file with skip_crop=1. Its preview replaces the old one with the mask and box cleared (D9), and the button does not come back.
  5. The fallback note reads "No coffee beans found -- the whole photo is classified." (D14). The TODO(crop editing) comment names /analyze and says that an edited box is a second upload (ADR 0023).
  6. Checks: the page's script runs in the throwaway V8 harness OPS-6 P3 used (outside the repo), against recorded /analyze streams from the dev server. The cases: a tray photo, a negative that falls back, a HEIC, an unreadable file, a 503, an error part, a stream cut after the preview, and D1's button. Then by hand on the local dev server, as in OPS-6 P3, at desktop and phone widths: the same photos, plus the circle in both places and Choose Photo disabled in flight.

  1. Read the front nginx's config once, without changing it (ticket D18): it must not list X-Accel-Buffering in proxy_ignore_headers, nor application/x-ndjson (or *) in gzip_types, either of which holds the answer back until it ends. Report what it says at the stop below.

  3. Merge ops7-one-upload into main with a merge commit (ADR 0017) and push (deploy.md: only pushed commits deploy).
  4. DOMAIN=... scripts/deploy_webapp.sh <sha> <model> with the served model. The smoke passes on the host, the GPU is proven in the boot record (ADR 0020), and verify is green and reports when each part arrived through the domain (D11).
  5. Live (D6): the smoke photo and one frame-filling photo on a phone, through the domain. The preview shows with the circle under it before the classification. The page comes back Cache-Control: no-cache. The request log has one /analyze line per photo, with preview_ms and latency_ms and outcome complete; those server-side numbers are what gets quoted (deploy.md). nginx's access log ends those lines with $upstream_bytes_received (D19).
  6. Record the release, the commit and the live times in the ticket's Status and Activity; the owner closes the ticket.
