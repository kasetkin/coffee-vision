Owner request, 2026-10-07. Analyse the .claude folder for memories and docs, read the skills folder, see how the skills expect project memory to be stored, and plan how to reorganise the memory files for better integration with the skills. Committed memories become public, so memories and docs must not contain private information such as GPS, logins, IPs or domains.

1. Summary

Today every piece of project knowledge an agent has gathered (decisions, lessons, traps, procedures) lives in Claude's auto-memory, which is private and which none of the installed skills read. After this ticket, knowledge that any contributor's agent needs lives in the repo files the skills already read, and private memory keeps only what is personal: who the owner is, how the owner likes Claude to work, and the current focus. The work splits into ADRs (with links back from the tickets they came from), coding standards for review, an out-of-scope record of closed ideas, agent runbooks, pointers in CLAUDE.md, and slimming private memory.

2. Background

  • Where memory is. 39 files, about 170 KB, in .private_claude/projects/-workspace/memory/: the devcontainer bind-mounts .private_claude/ as Claude's config directory, and it is gitignored. Claude loads the index (MEMORY.md) every session and the files on demand. Memory is not versioned.
  • What the skills read (mattpocock-skills/skills/): CLAUDE.md and its Agent skills block; docs/agents/; GLOSSARY.md; docs/adr/ (tdd, diagnosing-bugs, domain-modeling, improve-codebase-architecture, to-spec, to-tickets); CODING_STANDARDS.md (code-review's Standards axis, retro); .out-of-scope/ (triage). None reads auto-memory. Before this ticket only GLOSSARY.md existed.
  • Memory drifts from the tickets. The ML-2 memory still says "in progress"; the ML-2 ticket says Closed on 2026-10-03. The logging memory points to a plan file under ~/.claude/plans/ that no longer exists. Several memories link to memories since deleted.
  • Memory carries sediment. Superseded recipes sit beside their replacements (a reset-based VM sync replaced by simple merges; a pip venv replaced by uv; an rsync data copy replaced by dvc push/pull).
  • What is private is D1. The leak check (coffeecv/leak_check.py) enforces it on every commit.

3. Before and after

Now

  • Decisions, lessons and procedures in private memory only.
  • Skills find no ADRs, standards or out-of-scope record; code-review checks the Fowler smell baseline alone.
  • A closed idea comes back unless the agent happens to read the right memory.
  • Status is written in memory and in tickets, and the two disagree.

After

  • Decisions that bind later work are ADRs in docs/adr/, linked both ways with their ticket's D-number.
  • Judgement rules in CODING_STANDARDS.md for review; closed ideas in .out-of-scope/; procedures and traps in docs/agents/.
  • CLAUDE.md points at each, in a few lines.
  • Status lives in tickets and plans only. Private memory holds the owner profile, how the owner likes Claude to work, and a current-focus line.

4. What does not change

  • Tickets and plans. They stay the source of truth for their own decisions; this ticket adds one ADR link to a D-entry and changes nothing else in them.
  • GLOSSARY.md. Domain terms only; /domain-modeling extends it when a term is resolved, not this ticket.
  • README.md, EXPERIMENTS_LOG.md and the existing docs. New files point at them rather than copy them.
  • Code. No behaviour changes.

5. Risks

IDRiskEvidence and mitigation
R1Private data is published. Memory holds personal details (D1 lists what counts). The pre-commit leak check refuses public IPs, emails, credentials and photo GPS; content is also read before it moves.
R2Knowledge is lost when memory is slimmed. Memory is not versioned. Migrated files are archived, not deleted (plan Q1), and the owner reviews what stays (P6 stops for it).
R3Stale content is published as current. See the sediment in §2. Each item is checked against the code, tickets and docs as it moves; superseded parts are dropped, not copied.
R4CLAUDE.md grows into a manual. It is loaded every turn. It gets navigation pointers only; rules go to the files it points at.
R5ADRs duplicate tickets. An ADR is one to three sentences: the decision, why, and a link to its ticket and D-number for the detail.

6. Decisions

IDQuestionOptionsOwner decision
D1What may be published? (a) Nothing from infrastructure (b) Only what identifies or exposes a person or a system (b), 2026-10-07. Private: public IP addresses, email addresses, credentials and logins, GPS and other identifying photo metadata. Fine to publish: SSH aliases, the DVC remote URL, the VM's user name and hostname, the live site's domain, Docker-internal addresses. ADR 0014.
D2Which issue tracker do the skills use? (a) HTML tickets in docs/ (b) GitHub Issues (a), 2026-10-07. Conventions in docs/agents/issue-tracker.md.
D3What does an ADR with no ticket name as its source? (a) An Origin line: owner decision, date, and the doc that records it, if any (b) Create a ticket for each (a), 2026-10-07.
D4Is the migration itself tracked? (a) As ticket OPS-2 with a plan (b) As plain commits (a), 2026-10-07.

7. Scope and acceptance

  • The leak check runs on every commit (pre-commit), push (check.sh) and deploy.
  • The skills config exists: CLAUDE.md's Agent skills block and docs/agents/.
  • Every memory file is accounted for: moved (to a named file), kept private, or archived as stale.
  • Every ADR born in a ticket is linked from that ticket's D-entry, and names it.
  • A fresh session answers the plan's probe questions from repo files.
  • No committed file fails the leak check.

Out of scope

  • New glossary terms (left to /domain-modeling).
  • Rewriting old tickets, plans or EXPERIMENTS_LOG.md.
  • Rewriting git history (D1 makes what is already committed acceptable).
  • Private data in PDFs under hardware/ and in commit author fields: the leak check does not read them.
