coffeecv.strip_metadata strips and checks several photos at once

The owner asked for the metadata stripper to use more than one core. Today it handles one photo at a time. For each photo it runs exiftool three times and decodes the full image twice, so a batch of 50 MP photos keeps one core busy while the others sit idle. Written; not planned, not implemented.

Owner request, 2026-10-28. A new ticket to make the stripping tool run on several threads: as far as the owner knows, it uses only one now.

1. Summary

Today python -m coffeecv.strip_metadata DIR... --manifest ... strips and checks the photos one after another, and a --dry-run checks them the same way. After this ticket, it works on several photos at once, up to a --jobs count. Each photo gets the same checks and the same manifest row as before. The rows and the report come out in the same order as before. The work splits into four parts:

  • a pool of workers that run strip_one;
  • a --jobs argument;
  • keeping the manifest and the report in the same order;
  • a check that a parallel run writes what a serial run writes.

2. Background

Read at e3202a5:

  • One photo at a time. main loops over photos_under(dirs) and calls strip_one(p, dry_run) on each photo in turn (coffeecv/strip_metadata.py, main). Nothing in the module starts a thread or a process, apart from exiftool's own subprocess.
  • The work per photo. strip_one does the following:
    • reads the tags (read_tags: one exiftool -j process);
    • hashes the file;
    • decodes the photo for the pixel digest (pixel_digest: load_rgb_image and Pillow's own decode, and for a HEIC every top-level and auxiliary image);
    • writes a stripped copy (a second exiftool process);
    • reads that copy's tags (a third);
    • decodes the copy again.
    Most of the time goes into image decoding and exiftool starting up, and the steps for one photo share nothing with those for another.
  • Each photo's work stays separate. A real strip writes its temporary copy beside the photo, under a name from tempfile.mkstemp, and moves it over the original with os.replace. A dry run writes its copy to the system temp folder. Two workers never touch the same file.
  • The manifest is written once, at the end. main collects the rows and calls append_manifest after the last photo. The photos stripped so far have already been replaced on disk by then. If the run is interrupted, they are stripped but have no row. A rerun finds them clean and records a row with the same hash on both sides, so it does not record the tags that were removed. This is the case today, and more photos in progress at once would make it more likely.
  • A precedent. coffeecv.find_duplicates already runs on a ProcessPoolExecutor with the spawn context and a --jobs argument (default os.cpu_count()).
  • An example batch. The batch of 2026-10-28 had 32 photos. Twelve were 50 MP or more (6144x8160 and 8160x6120 JPEGs, 5712x4284 HEICs), and each was decoded four times: the photo and the stripped copy, by load_rgb_image and by Pillow's own decode.

3. Before and after

Now

  • One photo at a time, on one core.
  • No way to choose the number of workers.
  • The manifest is appended once, after the last photo.

After

  • Up to --jobs photos at once.
  • The same checks and rows per photo. The manifest and the report are in photo order.
  • The manifest is written as D3 decides.

4. What does not change

  • What is stripped and checked. The deny list, the kept fields, the pixel, tag and audit checks, and the Samsung trailer cut stay as they are. Parallel and serial runs give the same rows.
  • The manifest's format. The same columns and header lines, and the same order: rows follow photos_under's sorted order, whatever order the workers finish in.
  • How a photo is replaced. The new file is written beside the photo, checked, then moved over the original with os.replace, so the cache file DVC links from the working tree is never written through.
  • The pre-commit leak check. coffeecv.leak_check reads image metadata on its own and is not part of this ticket.

5. Risks

IDRiskEvidence and mitigation
R1Memory runs out on large photos. A 50 MP photo decodes to about 150 MB of RGB, and the pixel check holds a photo and its copy, plus each HEIC auxiliary image. With one worker per core on 12 cores, that is a few GB at the peak. D2 sets the default worker count. A measurement on the 2026-10-28 batch decides it.
R2An interrupted run loses the rows of the photos it has already stripped. This already happens (§2). More photos in progress at once means more are lost when a run is interrupted. D3 decides whether to write each row as its photo is done.
R3The output changes order. Workers finish out of order. The progress lines may come out in that order, but the rows, the report and the exit code must not depend on it. A test compares a parallel run with a serial one on the same photos.
R4A worker fails and the photo has no row. An exception in a worker (an undecodable photo, for example) must end as a failing row for that photo, as a failed check does today, not as a lost row or an aborted run with photos half replaced.

6. Decisions

IDQuestionOptionsOwner decision
D1Threads or processes? (a) processes, a ProcessPoolExecutor with spawn, as find_duplicates uses (recommended: the image decoding and hashing run in Python and hold the GIL for part of the time); (b) threads, which are lighter, but only the exiftool subprocesses and part of the decoding would overlap. Open.
D2Default --jobs? (a) os.cpu_count(), as find_duplicates; (b) a cap set by measured peak memory (R1); (c) 1, so parallel runs happen only when asked for. Open.
D3When are manifest rows written? (a) at the end, as today; (b) each row as its photo is done, so an interrupted run keeps its records (R2). Rows would then be in completion order, unless they are sorted when the manifest is read or written. Open.

7. Scope and acceptance

  • A --jobs N argument. The strip and the dry run both work on up to N photos at once.
  • A parallel run and a serial run on the same photos give the same manifest rows (timestamps aside), the same report and the same exit code. This is checked on a mixed set of JPEG, HEIC, DNG and an already clean photo.
  • A worker that raises gives a failing row for its photo. The other photos are still handled.
  • The wall time and peak memory of a dry run on dataset/segmenter_positives (262 photos), before and after, are recorded in the ticket.
  • The module docstring describes --jobs and D3's manifest behaviour.

Out of scope

  • Photos above Pillow's decompression-bomb limit. A 200 MP photo of 2026-10-28 cannot be decoded by load_rgb_image, which the live site also uses for uploads. That is a separate decision.
  • Starting one long-lived exiftool process (-stay_open) per worker instead of one exiftool process per call.
