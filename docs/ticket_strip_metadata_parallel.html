coffeecv.strip_metadata strips and checks several photos at once

The owner asked for the metadata stripper to use more than one core. Today it handles one photo at a time. For each photo it runs exiftool three times and decodes the full image twice, so a batch of 50 MP photos keeps one core busy while the others sit idle. Owner request, 2026-10-28. A new ticket to make the stripping tool run on several threads: as far as the owner knows, it uses only one now.

1. Summary

Today python -m coffeecv.strip_metadata DIR... --manifest ... strips and checks the photos one after another, and a --dry-run checks them the same way. After this ticket, it works on several photos at once, up to a --jobs count. Each photo gets the same checks and the same manifest row as before. The rows and the report come out in the same order as before. The work splits into six parts:

  • a pool of workers that run strip_one, without torch (D1, D8);
  • a --jobs argument, its default set by free memory (D7, D12);
  • keeping the manifest, the progress lines and the report in the same order, with each row written as soon as it can be (D3, D9, D10);
  • a run that survives a failing photo and a Ctrl-C without losing rows (D4, D5, D6);
  • a ceiling on the memory one photo may need to decode (D13);
  • a check that a parallel run writes what a serial run writes, and measurements before and after (D11).

2. Background

Read at e3202a5:

  • One photo at a time. main loops over photos_under(dirs) and calls strip_one(p, dry_run) on each photo in turn (coffeecv/strip_metadata.py, main). Nothing in the module starts a thread or a process, apart from exiftool's own subprocess.
  • The work per photo. strip_one does the following:
    • reads the tags (read_tags: one exiftool -j process);
    • hashes the file;
    • decodes the photo for the pixel digest (pixel_digest: load_rgb_image and Pillow's own decode, and for a HEIC every top-level and auxiliary image);
    • writes a stripped copy (a second exiftool process);
    • reads that copy's tags (a third);
    • decodes the copy again.
    Most of the time goes into image decoding and exiftool starting up, and the steps for one photo share nothing with those for another.
  • Each photo's work stays separate. A real strip writes its temporary copy beside the photo, under a name from tempfile.mkstemp, and moves it over the original with os.replace. A dry run writes its copy to the system temp folder. Two workers never touch the same file.
  • The manifest is written once, at the end. main collects the rows and calls append_manifest after the last photo. The photos stripped so far have already been replaced on disk by then. If the run is interrupted, they are stripped but have no row. A rerun finds them clean and records a row with the same hash on both sides, so it does not record the tags that were removed. This is the case today, and more photos in progress at once would make it more likely.
  • A precedent. coffeecv.find_duplicates already runs on a ProcessPoolExecutor with the spawn context and a --jobs argument (default os.cpu_count()).
  • An example batch. The batch of 2026-10-28 had 32 photos. Twelve were 50 MP or more (6144x8160 and 8160x6120 JPEGs, 5712x4284 HEICs), and each was decoded four times: the photo and the stripped copy, by load_rgb_image and by Pillow's own decode.

Read again at 413f7b4 and measured on 2026-10-30, during the owner's review of the ticket:

  • An exception aborts the run today. strip_one turns a failed check into a failing row, but not an exception: a StripError from read_tags or _heif_meta, or a decode error, ends main before append_manifest, so every photo already replaced on disk is left without a row (D5).
  • The resume check aborts mid-run. A photo already in the manifest whose bytes are not its sha256_after makes main return 1 where the loop reaches it, after the photos before it have been stripped, and with no rows written (D6).
  • Every worker would import torch. strip_metadata takes load_rgb_image from coffeecv.dataset, which imports torch: 2.5–3.5 s and 323 MB per process. Importing coffeecv.photo_io instead costs 0.3 s and 40 MB. coffeecv.dataset is also what raises Pillow's pixel limit to 537 MP (6185f45), so the limit has to move with the import (D8).
  • The peak memory is in the decode. pixel_digest returns a hash, so a photo and its stripped copy are never decoded at the same time. The peak is inside load_rgb_image, which holds about three copies of the image at once: 1.9 GB above the imports for a 200 MP JPEG, about 10 bytes per pixel. Hashing the array's buffer instead of a tobytes() copy does not lower it.
  • Most photos to hand are already stripped. A dry run on a stripped photo returns early: one exiftool process and one pixel_digest, against three and two for a photo with tags to remove. Timing a full strip needs copies with private tags added back (D11).
  • Measured per photo (one dry run each, in its own process, on copies in /tmp; the full strip on a copy with the test suite's private tags added back):

    Decoding is 70–90% of each photo's time and each exiftool process 0.2–0.4 s, so a full strip takes 1.3–2 times the clean path. The parallel run makes no photo faster; it runs them side by side. From the mix in dataset/segmenter_positives, a serial run is estimated at about 4 min on the clean path and 7 min for a full strip; it can never be shorter than its slowest photo. The machine has 12 cores and 13 GB, about 8 GB of it free: 12 workers on 50 MP photos need about 7.7 GB without torch and about 11 GB with it.
  • Other decoders. The nomacs viewer decodes through Qt's QImageReader (libjpeg-turbo; HEIC through kimageformats and libheif), LibRaw and exiv2, at full size, with no scaled or tiled decode and Qt's allocation limit left as it is. These are the libraries Pillow, pillow-heif and rawpy already wrap. OpenCV 5 is installed but uses the same libjpeg-turbo and is not what training decodes; pyvips could stream a decode but is a new system dependency and also not training's decoder; a scaled decode (Pillow's draft, LibRaw's half size) cannot prove the pixels unchanged. The 200 MP photo needs no new library: Pillow decodes it in about 5 s under the dataset's 537 MP limit (D8).

3. Before and after

Now

  • One photo at a time, on one core.
  • No way to choose the number of workers.
  • The manifest is appended once, after the last photo.
  • An exception, a resume-check mismatch or a Ctrl-C ends the run with the rows of the photos already stripped unwritten.
  • No limit on the memory one photo may take, apart from Pillow's 537 MP.

After

  • Up to --jobs photos at once; by default as many as free memory allows (D12).
  • The same checks and rows per photo. The manifest, the progress lines and the report are in photo order.
  • Each manifest row is written as soon as its photo and every photo before it are done (D3).
  • An exception gives a failing row (D5); the resume check runs before any work (D6); a Ctrl-C writes every finished row (D4).
  • A photo that would need more memory than the budget fails before it is decoded (D13).

4. What does not change

  • What is stripped and checked. The deny list, the kept fields, the pixel, tag and audit checks, and the Samsung trailer cut stay as they are. Parallel and serial runs give the same rows. So does pixel_digest: a photo's pixel_sha256 is what it was before this ticket.
  • The manifest's format. The same columns and header lines, and the same order: rows follow photos_under's sorted order, whatever order the workers finish in. Only the header's started time changes, to the run's real start (D10).
  • How a photo is replaced. The new file is written beside the photo, checked, then moved over the original with os.replace, so the cache file DVC links from the working tree is never written through.
  • The pre-commit leak check. coffeecv.leak_check reads image metadata on its own and is not part of this ticket.

5. Risks

IDRiskEvidence and mitigation
R1Memory runs out on large photos. Corrected 2026-10-30: the pixel check never holds a photo and its copy at once (§2). The peak is one decode inside load_rgb_image, about 10 bytes per pixel: 0.5 GB for a 50 MP photo, 1.9 GB for a 200 MP one, plus 40 MB of imports per worker once torch is gone (D8). D12 sets the default worker count from free memory, and D13 fails a photo too big for the budget before it is decoded.
R2An interrupted run loses the rows of the photos it has already stripped. This already happens (§2). More photos in progress at once means more are lost when a run is interrupted. D3 writes each row once its photo and every earlier one are done. That still leaves the photos that finished behind a slower earlier one; D4 writes those too on a Ctrl-C.
R3The output changes order. Workers finish out of order. The progress lines may come out in that order, but the rows, the report and the exit code must not depend on it. A test compares a parallel run with a serial one on the same photos.
R4A worker fails and the photo has no row. An exception in a worker (an undecodable photo, for example) must end as a failing row for that photo, as a failed check does, not as a lost row or an aborted run with photos half replaced. Corrected 2026-10-30: today an exception aborts the whole run (§2), so D5 changes the serial run as well.
R5Several big photos run at once. D13 bounds one photo, not the sum: eight workers that each take a 200 MP photo would need about 16 GB. D12's default assumes about 1 GB per worker, which holds for the photos to hand (one 200 MP photo among the 263 in segmenter_positives). If a run does run out of memory, the fallback is admission by memory: a photo is submitted only while the estimates in flight, its own included, fit the budget (Out of scope).

6. Decisions

IDQuestionOptionsOwner decision
D1Threads or processes? (a) processes, a ProcessPoolExecutor with spawn, as find_duplicates uses (recommended: the image decoding and hashing run in Python and hold the GIL for part of the time); (b) threads, which are lighter, but only the exiftool subprocesses and part of the decoding would overlap. (a), 2026-10-30, as recommended: a ProcessPoolExecutor with spawn, as find_duplicates uses.
D2Default --jobs? (a) os.cpu_count(), as find_duplicates; (b) a cap set by measured peak memory (R1); (c) 1, so parallel runs happen only when asked for. (b), 2026-10-30, as recommended: --jobs is built with a provisional default of os.cpu_count(); the peak memory per worker is then measured on the 2026-10-28 batch (its 50 MP photos), and the owner sets the cap from that measurement. The cap is D12.
D3When are manifest rows written? (a) at the end, as today; (b) each row as its photo is done, so an interrupted run keeps its records (R2). Rows would then be in completion order, unless they are sorted when the manifest is read or written. (c) Each row as soon as its photo and every photo before it are done: results come back in submission order (as pool.map gives them), so the rows stay in photos_under's order, and an interrupted run loses only the rows of the photos still in progress. An exception in a worker is caught in the worker and becomes a failing row for its photo (R4). (c), 2026-10-30, as recommended. Refined by D4: with results taken in submission order, photos that finish behind a slower earlier one wait for it, so an interruption would lose their rows too.
D4What does a Ctrl-C do? (a) As D3 stands: the rows of the photos in progress, and of those finished behind a slower earlier one, are lost. (b) Workers ignore SIGINT. On the first Ctrl-C the main process cancels the photos not yet started, waits for the running ones, and writes every finished row in photo order, leaving gaps where photos never ran; a rerun appends the gaps, as reruns already append. A second Ctrl-C aborts at once. (b), 2026-10-30, as recommended. An interrupted run then loses no rows unless it is killed outright.
D5What does an exception do? A wrapper around strip_one catches Exception (not BaseException, so a Ctrl-C stays D4's) and makes it a failing row for its photo, e.g. error: StripError: ...; the run goes on. The same at --jobs 1, which changes today's serial run (§2). A failing row goes to the report and the exit code, never to the manifest, as today. 2026-10-30, as recommended.
D6When does the resume check run? Every photo already in the manifest is hashed in the main process before any work starts. A mismatch exits 1 with nothing changed. 2026-10-30, as recommended.
D7What does --jobs 1 do? (a) It runs in the main process, with no pool. (b) It runs a pool of one. (a), 2026-10-30, as recommended. It is the serial run the acceptance compares against: no spawn, a debugger works, and the existing tests that mock keep working. The parallel tests use real files, since a mock does not reach a spawned worker.
D8How do workers avoid torch, and which decoder and pixel limit do they use? Import load_rgb_image from coffeecv.photo_io. DATASET_MAX_PIXELS moves to photo_io, unassigned there, and dataset and strip_metadata each set Pillow's limit to it; photo_io itself must not, as the web service imports it and keeps Pillow's default (6185f45). Alternatives looked at (§2): leave torch in every worker; drop to Pillow's 179 MP; OpenCV, pyvips, or a scaled decode. 2026-10-30, as recommended, after the owner asked for the libraries that load big photos, nomacs's included, to be compared (§2): Pillow stays, without torch, at 537 MP.
D9In which order do the progress lines come? (a) In photo order, each printed when its row is written. (b) In completion order. (a), 2026-10-30, as recommended: the same output at any --jobs, matching the manifest. A slow photo holds back the lines after it.
D10How is the manifest written? A new manifest gets its header with the first good row, as today, so a run with no good row writes no file. The header's started is taken at the run's start (today it is taken after the loop). Each row is flushed as it is written, with no fsync. 2026-10-30, as recommended.
D11What does the acceptance measure? (a) A dry run on dataset/segmenter_positives only, which takes the clean path (§2). (b) That, and a dry run on a copy of the folder in /tmp with private tags added back, which takes the full-strip path; each serial and at the default --jobs. (b), 2026-10-30. Nothing under dataset/ is written.
D12The cap D2 asks for. (a) A fixed default the owner picks. (b) min(os.cpu_count(), available memory // 1 GB), read at the start. (c) A fixed default plus a check on each photo's size before it is submitted. (b), 2026-10-30, as recommended, with D13 added: about 8 workers on this machine. The 1 GB is from the measurement in §2.
D13How is a photo too big to decode caught? The main process reads each photo's dimensions from its header, decoding nothing, and estimates its decode memory: about 10 bytes per pixel (§2), with a factor per format (JPEG and PNG, HEIC, RAW from rawpy's sizes) measured in the plan. (a) A ceiling only: a photo whose estimate is above it fails before it is decoded; --jobs stays D12's. (b) The ceiling, plus admission by memory: a photo is submitted only while the estimates in flight, its own included, fit the budget. The ceiling is the memory available at the start minus 1 GB, or --max-memory. A photo above it gets a failing row, "too big: about N GB to decode, budget M GB": its original untouched, no manifest row, exit code 1. Not a skip with a warning, which would let a photo keep its private tags and the run pass. (a), 2026-10-30, with (b) kept as the fallback if a run runs out of memory (R5, Out of scope). The ceiling and the over-ceiling row as recommended.
D14P5's stop: is the default run's peak, measured against the free memory, acceptable? The default --jobs (6 workers here) peaked at 4.0 GB of the 6.8 GB available, about 0.6 GB a worker against D12's 1 GB (Activity, 2026-10-30). (a) Keep D12's 1 GB a worker; (b) a different per-worker budget; (c) open D13 (b), admission by memory. (a), 2026-10-30: 4 GB is fine, and 8 GB would be, with 10 GB of swap free. D13 (b) stays out of scope.
D15The default --jobs, raised (supersedes D12's formula). The owner asked for 10 workers by default instead of D12's 6 on this machine. Claude recommended keeping a memory term, so that a machine with less free does not start 10: min(os.cpu_count(), 10, (memory available + swap free) // 1 GB), read at the start; 10 here (12 cores, about 6.8 + 10 GB free). 2026-10-30, the owner: "raise default number of jobs from 6 to 10"; the formula as recommended.

7. Scope and acceptance

  • A --jobs N argument. The strip and the dry run both work on up to N photos at once.
  • A parallel run and a serial run on the same photos give the same manifest rows (timestamps aside), the same report and the same exit code. This is checked on a mixed set of JPEG, HEIC, DNG and an already clean photo.
  • A worker that raises gives a failing row for its photo. The other photos are still handled. The same at --jobs 1 (D5).
  • A manifest photo whose bytes are not its sha256_after ends the run with exit code 1 before any photo is touched (D6).
  • A Ctrl-C during a parallel strip leaves every photo replaced on disk with its manifest row (D4).
  • Importing coffeecv.strip_metadata does not import torch, the 200 MP photo still decodes, and the web service keeps Pillow's default limit (D8).
  • A photo above the memory ceiling gets a failing row before it is decoded, its original untouched (D13).
  • The wall time and peak memory, before and after, serial and at the default --jobs, of a dry run on dataset/segmenter_positives and of a dry run on a /tmp copy of it with private tags added back, are recorded in the ticket (D11).
  • The module docstring describes --jobs, --max-memory, D3's and D4's manifest behaviour and D13's ceiling.

Out of scope

  • Starting one long-lived exiftool process (-stay_open) per worker instead of one exiftool process per call.
  • Admission by memory (D13 (b)): the fallback if D13's ceiling and D12's default are not enough (R5).
  • Decoding an RGB JPEG or PNG once instead of twice in pixel_digest (load_rgb_image and Pillow's own decode give the same pixels). It would roughly halve a JPEG's decode time, but it changes the photo's pixel_sha256 against earlier manifest rows, against §4.
  • Fewer copies inside load_rgb_image, which would lower the peak (§2). Training and serving share that function.
