Ticket OPS-13 · coffee-vision · deploy

A deploy reuses any file the host already holds with the same content, so a file crosses the link once

The link to the web host is slow, about 14 MB a minute, and a release of a new model name sends its whole LiteRT export again, about 815 MB and an hour, although nearly all of it is already on the host. The owner asks for each file to be uploaded once where possible, reusing a file the host holds when its hash matches. Written 2026-10-29, during ML-13's deploy; decisions open, not planned, not implemented.

1. Summary

Today a deploy reuses a file already on the host only at the same path in an earlier release. A new model name is a new path, so its whole export is sent again, though most of its bytes are the same graphs the live release already serves. After this ticket, the deploy matches files by content: a file the host already holds with the same hash is copied there, not sent, and only what the host lacks crosses the link. Two parts: reuse from the releases on the host, and, per D1, reuse from the DVC store on the same host, which every model reaches first (ADR 0028).

2. Background

  • How the upload reuses today. scripts/deploy_webapp.sh uploads the staged release with rsync --copy-dest against the current release and the newest others on the host: a file found unchanged at the same relative path is copied on the host, and a changed one is sent as a delta. The copy is "a full copy, never a hard link -- each release stays independent". Only current and previous are kept (prune).
  • What a new model name costs. The export lives at models/<name>.litert/, so a new name matches nothing. docs/agents/deploy.md: "The first release of a new model name uploads its ~780-820 MB in full (55 min to webappremote on 2026-10-17)", and ML-8 found only head.npz differing (2026-10-20). ML-12's staged deploy took 66 min (2026-10-27).
  • How much is new, measured 2026-10-29 (XL0-v5's export against ML-13's, by md5): encoder.tflite (452.0 MB) and dino_b8.tflite (343.0 MB) identical, and convert.json; decoder.tflite (20.6 MB), head.npz (62 KB), manifest.json and check.json differ. 795 of 816 MB is already on the host in the live release.
  • The link. ML-13's DVC push ran at 13-15 MB a minute to the same host (2026-10-29).
  • The DVC store already sends each object once. It is content-addressed by md5: ML-13's push sent the new decoder (its object dated 2026-10-29) and not the encoder or DINOv3 graphs, whose objects have been there since 2026-10-15. Every model reaches it before a deploy (ADR 0028, docs/agents/dvc.md). Today only the deploy sends the same bytes again.
  • The DVC store and the releases share a disk. dvcnewremote and webappremote are both yappy (docs/agents/dvc.md); 90 GB free on its one filesystem (2026-10-29). The store is /home/sun/dvc-store, owned by sun, and /home/sun is mode 700, so the deploy's user, coffee-deploy, cannot read it today.
  • The digests a release is checked against. release_manifest.py lists the DVC files (the export, the checkpoint) by the md5 in dvc.lock and the .dvc pointers, and the pinned files by sha256. After the upload, and again when a staged release is reused, every file is checked on the host against its digest: md5 for a 32-character digest, sha256 otherwise; check_staged_listing then requires the release to hold exactly the manifest's files.

3. Before and after

Now

  • A file is reused only at the same path in a release on the host.
  • A new model name sends its whole export, about 815 MB, about an hour.
  • Bytes the DVC push already put on the host are sent again by the deploy.
  • DVC files are checked on the host by md5.

After

  • A file is reused wherever the host holds the same content (D1's sources), at any path.
  • A new model name sends only what the host lacks: about 21 MB for ML-13's export, under 2 minutes.
  • With D1 (b) or (c), a file the DVC push sent is not sent again.
  • A reused file is accepted only when its hash on the host matches (D2); otherwise it is sent.

4. What does not change

  • Releases stay independent (ADR 0008). A reused file is copied into the new release, never hard-linked, as --copy-dest does today, unless D3 says otherwise.
  • What runs is checked before it runs. Every file of the release is checked on the host against the manifest, and the release holds exactly the manifest's files, before the smoke, --compare and the flip.
  • The DVC store is not written by a deploy. It stays the archive (ADR 0028); the deploy only reads it.
  • The order of a deploy: only pushed commits on origin/main, the live service stopped only once everything is on the host (ADR 0026), the smoke, --compare, the flip.

5. Risks

IDRiskEvidence and mitigation
R1A reused copy on the host is damaged (a disk error in an old release or the store). The same check as an uploaded file: its hash computed on the host after the copy, against the manifest; a mismatch sends the file instead. A file that fails twice stops the deploy.
R2Two different files with the same hash. By accident, negligible for md5 or sha256 at this scale. On purpose, md5 collisions are cheap to make; sha256's are not known. Only someone who can already write to the host could plant one. D2 decides the hash.
R3The deploy's user reads the DVC store (D1 (b), (c)). /home/sun is mode 700 today. Read access for coffee-deploy only (a group, or the store moved out of /home/sun), never write; set up once on the host, recorded in webapp/README.md's host setup.
R4The DVC remote moves off the web host. The store path then holds nothing for the deploy, which falls back to the releases, then the upload: slower, never wrong. The deploy reads the store at a configured path on the web host; it does not assume the DVC remote's URL.
R5A change to the deploy script breaks a live deploy. scripts/rehearse_deploy_local.sh before it is used (docs/agents/deploy.md), and the first real use is a --stage-only run.

6. Decisions

IDQuestionOptionsOwner decision
D1Where may a deploy take a file from instead of sending it? (a) The releases on the host (current, previous), matched by content. Saves 795 of 816 MB for ML-13's export; the decoder and head are still sent. (b) The DVC store on the host, matched by the md5 it is named by: everything the DVC push sent, so model files cross the link once. Needs R3's read access. (c) Both, in that order, then the upload. Recommended: (c). (a) alone is the smaller change and takes most of the gain; (b) is what makes it "once". Open.
D2Which hash decides that a file on the host is the file the release needs? (a) md5, as dvc.lock records and today's check uses. (b) sha256: the manifest carries it for every file (computed locally from the DVC cache when the release is built), a candidate is found by size and md5, and the copy is accepted only when its sha256 on the host matches. Hashing 816 MB on the host costs a few seconds. Recommended: (b). Open.
D3Copy or link a reused file? (a) A full copy, as today: each release stays independent (ADR 0008), 816 MB more disk per release. (b) A hard link: no extra disk, but releases then share inodes, and a change to one changes the other. Recommended: (a); disk is not short (90 GB free). Open.

7. Scope and acceptance

  • A --stage-only deploy of a model whose export shares graphs with the live release sends only the files the host does not hold: for an export like ML-13's, about 21 MB, measured from rsync's sent bytes and the step's time in the log.
  • The deploy log says, per file, whether it was reused (and from where) or sent.
  • Every file of the staged release is checked on the host against D2's hash before the smoke; a reused file that fails is sent instead, and the release holds exactly the manifest's files.
  • With D1 (b) or (c): a file in the DVC store on the host is copied from there, and the deploy still works, sending everything, when the store is absent or unreadable.
  • scripts/rehearse_deploy_local.sh passes, with a case where a reused file is corrupt.
  • docs/agents/deploy.md's paragraph on a new model name's upload says what is sent now; ADR 0008 amended if D1 or D3 changes where a release's bytes come from.

Out of scope

  • The link itself (its speed, the Tailscale route).
  • The release's Python environment: uv builds it on the host from its own downloads, not over this link.
  • Sharing graphs between model exports in the repo or the DVC cache (one encoder file for every model): the DVC cache already stores each object once.

The retry sent only what was missing; the script's md5 check of every file and its listing check passed; the upload step took 146 s, the first attempt included. The staged tree's files carry the build's time, not the cache's, so rsync's size-and-time check did not skip the copies: it sent them as deltas against the identical files on the host, which cost seconds. A build-side step that seeds the release folder on the host by content before the rsync, keeping today's checks after it, is enough for D1 (a). Not implemented in the script.
