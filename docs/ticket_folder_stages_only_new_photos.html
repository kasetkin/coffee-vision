1. Summary

A stage run reads its own entry in dvc.lock. When only its photo folder changed since, it processes the photos that are new or changed, keeps the outputs of the others that are on disk as recorded, and deletes the outputs of photos that are gone. Anything else, or --full, rebuilds the folder from nothing. ADR 0037.

2. Background

  • Why every photo ran. DVC deletes a stage's outputs before it runs, and the scripts processed every photo of the folder. The outputs that existed came back byte-identical each time (ML-19 D49).
  • What dvc.lock holds. For each stage: the command, every input's md5 (a folder's as the md5 of its listing, the listing itself in the cache for data folders), the params' values and every output's md5. That is the record of the last run; the scripts read it, and run no DVC.
  • A photo's outputs depend on that photo alone, given the code, the model and the params, so keeping them gives the bytes a full run gives.

3. Before and after

Now

  • A run processes every photo of the folder.
  • 17 new photos in random_date_raccoon: about 45 minutes.

After

  • A run processes the new and changed photos; a change to the code, model, params or stage rebuilds in full.
  • 17 new photos: a few minutes, mostly hashing the folder and loading the segmenter.

4. What does not change

  • The outputs. The same bytes as a full rebuild; tests hold it on made-up folders.
  • When a stage runs. DVC decides that, as before.
  • merge_segpool and seg_dataset. Not touched: both take under a minute.

5. Risks

IDRiskEvidence and mitigation
R1Something that shapes an output but is not a dep of the stage changes, and old outputs stay. Every dep, param and the command are compared, as dvc.yaml names them. A module the code imports but the stage does not name was never caught by DVC either; it goes into the deps (ADR 0037). --full rebuilds from nothing.
R2An output on disk differs from the record (an interrupted run). A kept output is compared with its recorded md5; one that differs or is missing is made again, and a file no current photo makes is deleted. Tested.

7. Scope and acceptance

  • coffeecv/incremental.py, tested on a made-up repository (15 tests), and the real dvc.yaml's 41 stages resolve to their dvc.lock entries.
  • Both scripts incremental, with --full; tests that an incremental run equals a full rebuild, that a changed dep rebuilds in full, and that an output not as recorded is made again.
  • The code change recorded for the 41 stages with dvc commit: only the two scripts' md5 moved in dvc.lock.
  • The first real incremental run: ML-25's third batch, 17 photos, 2026-11-11: the three stages in 3 minutes (canonicalize 56 s, segcrop 83 s, merge_segpool 33 s), 394 photos kept, every output that existed unchanged.
  • seg_ml19_predict incremental (D2), tested with a stand-in segmenter; recorded with dvc commit; a run with nothing new: 4 s, 434 kept, the output as recorded.

Out of scope

  • The frozen seg_*_predict stages, which never run again.
