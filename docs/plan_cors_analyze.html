Implementation plan: other sites' pages can call /analyze and read the answer

The order of work for ticket OPS-19. There are three local strands: the front's site and its tests, the contract and the docs, and --verify's CORS checks. Then one release, which needs the owner's go and the owner's browser check. The site comes first because everything else describes or checks what it does. Nothing reaches the live site before P4.

Built from a read of the code at 5682d93, not from the ticket alone. Seven things the ticket does not cover turned up. They are folded in below. None of them needs a decision.

  1. The front's site ships only with a full release. build_front in scripts/deploy_webapp.sh renders the site template for each release, and there is no front-only deploy. So P4 is a full two-host deploy of the live model, and it stops photo answers for under 2 minutes (ADR 0026). Folded into P4.
  2. The preflight answer needs its own headers. if ($request_method = OPTIONS) { ... return 204; } is safe in nginx, since a return is one of the two things an if in a location does reliably, and it runs in the rewrite phase, before limit_conn. But an add_header inside the if replaces the location's own, so the block lists every CORS header itself. Folded into P1.
  3. The inference host's own busy 503 has no JSON body (llms.txt, "Errors"). The check service relays it, so the location's add_header ... always covers it, but no test answers 503 through the front's site yet. FakeInferenceHost.reply = 503 (in tests/test_front_check_service.py) can. Folded into P1.
  4. A CORS header from upstream would reach the browser twice. The check service relays every header from the inference host except its hop-by-hop ones (NOT_RELAYED). To test D1's proxy_hide_header, the fake inference host needs a way to add one header to its answer. Folded into P1.
  5. Nothing parses the front's access log except tests/test_front_site.py. Adding "$http_origin" at the end of the line keeps every existing field in place. The README's tail -f comment (line 254) and docs/logging_plan.html (§06's table, and the excluded-fields table beside Referer) describe the line. Folded into P1 and P2.
  6. The owner's browser check cannot fetch an example photo cross-origin. /examples/ has no CORS, and the ticket keeps it that way. So the check snippet in P4 picks a local file through an <input type=file> added to the page. It also runs from a page with no restrictive Content-Security-Policy (https://example.org), since a site's own connect-src blocks the fetch before CORS is even reached.
  7. --verify already keeps the headers of its POST (post_analyze writes them to $hdr). Adding an Origin header there checks D1 and D4 on the real 200 at no extra cost. Folded into P3.

1. Phase order and why

P1 changes the site and proves each answer's headers locally against a real nginx. P2 documents what P1 does. P3 teaches --verify to check it, so the release in P4 is checked and rolled back on a failure like any other. Only P4 touches the live site.

3. P1 — The front's site answers cross-origin callers

StatusDone 2026-11-08, adff0b3; 20 tests in tests/test_front_site.py pass against a real nginx
Blocked byNone

All in webapp/deploy/coffee-cv-front.nginx.conf.template, test first in tests/test_front_site.py. location = /analyze gains Access-Control-Allow-Origin "*" always and Access-Control-Expose-Headers "X-Request-Id" always (D1, D4). It also gets proxy_hide_header for the six CORS response headers (D1), and an if ($request_method = OPTIONS) block that adds Allow-Origin *, Allow-Methods POST, Allow-Headers * and Max-Age 7200, then return 204 (D2). @too_large, @busy and @offline each gain the same two always headers as the location. coffee_cv_front_minimal gains "$http_origin" at the end (D3).

  1. The fake inference host (tests/test_front_check_service.py) gains a class attribute for extra answer headers, reset in each setUp, so a test can make upstream send Access-Control-Allow-Origin.
  2. Tests, each sending an Origin. Each of these answers carries exactly one Access-Control-Allow-Origin: * and Access-Control-Expose-Headers: X-Request-Id:
    • the streamed 200, with X-Request-Id still there;
    • the check service's 400 and 413;
    • nginx's 413;
    • the busy 503 from the gate;
    • the inference host's own 503, relayed;
    • the offline 503 from the check service (inference host down);
    • the offline 503 from nginx (check service stopped);
    • a 200 whose upstream sent its own CORS header.
  3. Tests: OPTIONS /analyze gets a 204 with the four preflight headers. It also gets a 204 while a photo is in flight, not a busy 503, and with the check service stopped, which proves it never reaches it.
  4. Tests: the agent files keep their header. / and an example photo have none.
  5. Test: an upload sent with an Origin header has that origin, quoted, at the end of its line in coffee-cv-front.access. One without has "-".
  6. The template's comments say why: always, the named locations, the if holding its own headers, proxy_hide_header, and Chrome's Max-Age cap. Each cites OPS-19 and ADR 0035.
  7. Checks: tests/test_front_site.py passes with a real nginx (not skipped), and scripts/check.sh is green.

4. P2 — The contract and the docs

StatusDone 2026-11-08, a6a142e; tests/test_agent_files.py passes
Blocked byP1

The texts that say what P1 does, all calling the other side a cross-origin caller (the ticket's Activity). They also say what D5 asks of a calling site.

  1. webapp/static/llms.txt: a short section, "From a web page". It says the API may be called from a page on any site. It gives a fetch example with a FormData body, reading both NDJSON lines from response.body. It says the site should tell its visitors their photo is sent here, and that it is never stored. On a busy 503 the site waits about 10 s and retries, never in a loop and never in parallel, as in "Limits".
  2. webapp/static/openapi.json: the API's description says the same in a sentence.
  3. webapp/README.md: "For agents" says /analyze answers every origin too (ADR 0035), and the access log's tail -f comment names the Origin field.
  4. docs/inference_path.html: the front's step (around line 298) names the CORS headers and the preflight answered before the gate.
  5. docs/logging_plan.html: §06's row for coffee-cv-front.access lists the Origin. A row beside Referer's marks it included, because it is a site's address, not a visitor's, and it is the only way to tell other sites' traffic from the page's (OPS-19 D3).
  6. Checks: tests/test_agent_files.py passes (every URL in the files is one the release serves), llms.txt stays ASCII, and scripts/check.sh is green.

5. P3 — --verify checks CORS on the domain

StatusDone 2026-11-08, c3c606d, 4f85a0c; the checks run against a real nginx; the rehearsal cut short by the owner (see Activity); shellcheck not run
Blocked byP1

D7 (a). These checks are in verify()'s public block in scripts/deploy_webapp.sh, so a failure rolls a full deploy back like any other check. They use the origin https://verify.invalid, so their lines in the access log are plainly the deploy's own.

  1. post_analyze sends -H "Origin: https://verify.invalid". When the backend is enabled, check covers Access-Control-Allow-Origin = * and Access-Control-Expose-Headers = X-Request-Id from $hdr. The 503 branch with no backend checks the same header on the front's offline answer.
  2. A preflight: curl -X OPTIONS with Origin and Access-Control-Request-Method: POST, checked for a 204 and the four headers.
  3. A refusal: a POST of a text file as photo, checked for a 400 that carries Access-Control-Allow-Origin: *. It is refused at the front in milliseconds and never reaches the worker.
  4. docs/agents/deploy.md's --verify paragraph names the new checks.
  5. Checks: scripts/rehearse_deploy_local.sh passes (the runbook asks for it before a change to the deploy script), shellcheck is clean, and scripts/check.sh is green.
