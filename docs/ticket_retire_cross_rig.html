Ticket ML-1 · coffee-vision · training & evaluation

Retire cross-camera validation: one pooled dataset, bean class is the only label

Training and evaluation are built around leave-one-camera-out folds: a camera held out, a separate cross-rig test split, a cross-rig headline metric, and a rule that every change must win on it. The owner has decided to drop this. All cameras are treated as equal sources of photos, and the only thing the pipeline distinguishes is the ten bean classes. This ticket records what changes and why, how the workflow changes, and what the change costs. Nothing is implemented yet.

1. Summary

The pipeline already has the end state as one of its two modes. run_all_rigs.py and fit_frozen_head.py train on all four cameras with heldout_rig: "", and both production models were made that way (allrigs_dino3b16_s123, live, and allrigs_cam_s123, the fallback). Cross-rig logic lives in the other mode, the leave-one-camera-out folds, and in every tool built to read fold results. So most of the work is deletion. What remains is to make the all-cameras mode the only mode, move the few helpers that other code imports from fold modules, and replace the cross-rig selection rule with an in-distribution one.

The hard part is not the code. Once the folds are gone, the only metrics left are in-distribution: a new photo of beans the model has seen, taken with a camera it has seen. Those metrics are near ceiling (0.97), and they are nearly flat across choices (§5, R1). The ticket names this cost so that nobody later compares a new 0.97 with an old 0.887 as if they measured the same thing.

2. Background

Today, photos are split 70/15/15 into train/val/test within each camera and class, and a camera's position in the list seeds that split so that a rerun is byte-identical. D1 (§6) replaces this with a pooled split, within each class only, across all cameras.

3. What does not change (checked)

  • Serving. webapp/app.py, webapp/static/index.html, scripts/deploy_webapp.sh's release path, and the inference path in coffeecv/infer.py have no cross-rig logic. Both deployed models stay valid as they are. No redeploy is needed.
  • Loading old checkpoints. infer.config_for_checkpoint keeps only the keys RunConfig still defines (infer.py:243-245), so removing heldout_rig, xrig_patches_per_class and mixstyle_mode from the config does not break any model card in models/. None of the three affects patch geometry. Renaming train_rigs is different; see D4.
  • Data. The crop and merge_cam_* stages and the four data/cropped/cam_* pools stay. They are the photo pools the two deployed models were trained on.
  • MixStyle, agnostic mode. It mixes feature statistics between random samples in a batch and never sees which camera a sample came from. It stays in the ResNet18 recipe. Only the cross_rig mode, which needs camera labels and was closed as a null, goes.
  • The OOD guard's same-camera negatives. Negatives are shot on the same cameras as the training photos so the probe cannot learn "different camera" instead of "not coffee". That matches the new rule. It is not validation by camera.
  • The bean-pitch estimator's cross-camera consistency (bean_scale.py, geometry.py comments). That describes whether one ruler measures all cameras alike, which still matters when they are pooled.
  • The record. experiments/, the DVC cache, fold checkpoints and models/*.json cards are history, not logic. They are kept (D5).

4. Workflow, before and after

Now

  1. Screen a change on folds: 4 cameras × 3 seeds, each fold a full training run.
  2. Adopt on 12 paired cross-rig deltas, sign-consistent.
  3. Train again on all cameras to ship, 1–3 seeds; pick the seed on val.
  4. DINOv3 head: C is the median of the folds' picks.

After

  1. Screen a change on the pooled data: 3 seeds, one run each, paired per seed against the baseline at the same seed.
  2. Adopt on paired val deltas, sign-consistent over seeds. Test is a reported control (D2).
  3. The screen's best-val run is already a shipping candidate. There is no separate refit.
  4. DINOv3 head: C is fixed at 0.1 (D3).

A screen costs a quarter of what it did: 3 runs instead of 12. Unchanged: adopt only on paired multi-seed evidence; dvc repro, not direct python; commit code, params and outputs together; every lever stated on the command line; test split read once, never used to choose.

5. Risks

What the decision costs

IDRiskEvidence and mitigation
R1The remaining metric can barely tell choices apart. Val macro-F1 is near ceiling and nearly flat. The deployed head's own val split, across the whole C grid from 0.001 to 100, scores 0.9688–0.9763 (models/allrigs_dino3b16_s123.json, diagnostic_val_macro_f1_by_C). It would pick C=0.0316, where the folds picked 0.1, on a margin of 0.002. README.md already flags val saturation for ResNet18 checkpoint selection. Mitigations are in D2. Expect most screens to come back null. Before the first real screen is adopted on this metric, measure its own seed-to-seed noise — rerun the unchanged baseline at a few seeds, or bootstrap val macro-F1 over patches — so "sign-consistent over 3 seeds" (§4) has a measured floor to clear instead of an assumed one carried over from the fold protocol's ±0.048 band, which does not apply to this metric. That measurement also settles whether raising the val patch budget buys real separation before spending compute on it.
R2No number estimates a new camera or a new scoop of beans. Val and test photos come from the same bags and the same cameras as train. This is the trade the decision accepts. State it in README.md so that in-distribution scores are not read as real-world accuracy. Until the out-of-scope generalization ticket exists, the only remaining signals for camera- or scoop-level drift are manual spot-checks (as run against the legacy-lens photos) and the OOD guard; neither is a gate a change must pass, so a regression here can ship silently in the meantime.
R3Old and new headlines are not comparable. 0.887 (cross-camera, DINOv3) and 0.975 (val, same model) answer different questions. index.csv keeps both kinds of column; new rows leave xrig_* blank. Blank means not measured, as it does for pre-Phase-11 runs.
R4Work that relied on folds loses its protocol. DINOv3 §7.2, the formal adoption check, can no longer run as designed, so the owner's 2026-09-26 selection stands without it. Screen C, Screen D and C1-ship need a new protocol or are dropped (D7).

D1How are photos split into train/val/test? (a) Keep the split within each camera and class, with no camera ever reported or labelled. (b) Pool all photos and split within each class only. Owner decided (b), 2026-09-29 — overriding this ticket's (a) recommendation. Photos are pooled across all capture directories and split 70/15/15 within each class only. This gives up the guarantee that every capture appears in val/test in exact proportion, and it means the new code does not reproduce the deployed models' training data. Owner's call: that reproducibility isn't needed since Git/DVC already preserve it.
D2What selects and what is reported? Val patch macro-F1 selects (checkpoint, C, adoption). Reported: test patch macro-F1, and optionally test photo-level macro-F1 (40 patches per photo, the /classify path, via run_photowise). Owner accepted, 2026-09-29; photo-level test removed for now, 2026-09-30. Val patch macro-F1 selects (checkpoint, adoption; not C, see D3) and test patch macro-F1 is reported. The photo-level test is not implemented: run_photowise went with xrig_eval.py (restore from 0fa699c^), and the two geometry helpers only it used were deleted too. Was: add photo-level test, since it is what the site serves. The val patch budget (40/class/camera) is a separate, later question — see R1's mitigation; it should not be raised speculatively before that measurement exists.
D3How is the DINOv3 head's C chosen? (a) The run's own val pick. (b) Freeze C=0.1, the last fold median, as a constant. Owner decided (b), 2026-09-30, reversing the 2026-09-29 acceptance of (a): C defaults to 0.1 in fit_frozen_head.py (--C overrides it) and no longer reads exp240-251. The run's own val pick is still recorded as a diagnostic. Given R1, a val pick would mostly follow noise. The deployed model is not refitted.
D4Keep the word "rig" in config and code? (a) Rename train_rigs to data_dirs and Rig to Source, with an alias so old cards' train_rigs still loads. (b) Keep the names and only delete. Owner decided (a), 2026-09-29, naming it capture rather than "source": train_rigs → train_capture_dirs, Rig → Capture, RIGS → CAPTURES, with the alias in config_for_checkpoint. Reasoning: a capture is defined by camera + date + setup + lighting, so a future directory need not correspond to one physical camera the way "source" or "rig" imply. Without the alias, build_ood_reference on an old model would silently fall back to the default dirs. The internal seed component keeps its value; only the variable name changes. The four physical directory names (cam_pixel, etc.) are not renamed — out of scope, would churn DVC-tracked paths for no behavior change.
D5What happens to the fold-era record? Delete scripts whose only input is fold runs; keep experiments/, index.csv columns, EXPERIMENTS_LOG.md, model cards, results JSON and closed plan docs. Owner accepted, 2026-09-29. As stated. The record is data, not logic, and several memories and cards cite it.
D6Legacy merge_oneplus / oneplus_combined? Delete, or keep. Owner accepted: delete, 2026-09-29. No current consumer. Merging the four cam_* pools into one dir is not recommended.
D7Open items that assumed folds DINOv3 §7.2, §7.3 Screen D, §10 Screen C; reorg plan A1, A2, C1-ship (bean_k_lo=5). Owner accepted, 2026-09-29. Close §7.2 as superseded. Re-scope Screen D and C1-ship to the new protocol only if still wanted. Drop A2. Keep A1 only as class balance.

Out of scope

  • Retraining or redeploying. The live model and its fallback are unaffected.
  • Changing any served output, including the fallback's OOD warn-band text in infer.py.
  • A new generalization test set, such as fresh scoops or photos from a new phone. That would be the honest replacement for what R2 gives up, and deserves its own ticket.
  • Pushing the pending fold checkpoints to the DVC remote. They are history either way.
