Implementation plan: the mask overlay

The order of work for ticket OPS-6. Three strands: the server sends the mask, the deploy's smoke check learns to compare it, and the page draws it; then the deploy. The server comes first because the other two consume its answer. No phase changes a classification number.

Built from a read of the code at a290ce4, not from the ticket alone. Four things the ticket does not spell out turned up. All are folded in below; none needs a decision.

  1. The smoke comparison would fail on any mask string. compare_smoke passes the whole /crop body to _max_abs_diff, which requires strings to be equal. P2 takes mask out of both bodies before that and compares it decoded, by IoU. No test covers compare_smoke today; P2 adds the first.
  2. The mask must match the thumbnail's size to the pixel. /preview sizes the thumbnail with PIL's Image.thumbnail, which rounds. P1 takes the size from one helper used by both endpoints, instead of recomputing it in /crop.
  3. /crop cannot tell a fallback from "no crop" today. crop_info is None both on a ML-2 D18 fallback and when there is nothing to crop; the segmenter's own seg_fallback diagnostic is dropped. P1 returns it.
  4. #image-mask in index.html is a CSS clipping box, not a mask. Next to a segmentation mask the name misleads. P3 renames it #image-clip.

1. Phase order and why

P1 fixes the shape of /crop's answer, which P2 and P3 both read; they can run in either order after it. P3 stops for the owner to look at the overlay before anything ships; P4 stops for the owner's go to deploy. /classify is not touched in any phase.

3. P1 — /crop returns the mask

StatusOpen not started
Blocked byNone

crop() keeps the mask segment_bean_region already returns, scales it to the thumbnail's size, and sends it as a 1-bit PNG, base64 (ticket D7). On a fallback the mask is null and seg_fallback is true (D5). The mask is the full photo's mask scaled down, not the cropped one: the bean region outside the D4 box is part of it (D3).

  1. One helper gives the thumbnail size for a decoded photo's (w, h); /preview and /crop both use it (finding 2).
  2. /crop: scale the bool mask to that size (area average, then ≥ 0.5), encode as a mode-1 PNG, base64, in mask; add seg_fallback from the segmenter's diagnostics (finding 3). cropped, box and needs_review keep their meaning. Update the docstring and webapp/README.md's description of /crop.
  3. Tests, written first, in a new tests/test_webapp_crop.py under the real_data tier (importing webapp.app loads the model): on the tray smoke photo, the mask's size equals the /preview JPEG's, it is not empty, and it agrees with the full-resolution mask scaled down; on an EXIF-rotated photo, the mask's size equals the thumbnail's, not the stored pixels'; on a fallback (the segmenter stubbed to an empty mask, so it stays fast), mask is null and seg_fallback is true (ticket D10).
  4. Checks: the new tests pass and were seen failing first; tests/test_release_manifest.py still passes (no new file opened); /crop's box on the smoke photo is unchanged; the mask's size in bytes on the smoke photo is written in the Activity entry (ticket R4); scripts/check.sh --full passes.

4. P2 — the smoke check compares the mask

StatusOpen not started
Blocked byP1

compare_smoke pops mask from the expected and the served /crop bodies, compares the rest as today, and decodes the two masks: they must be the same size, both null or both present, and their IoU ≥ 0.98 (ticket D10). Its summary line prints the IoU next to the box diff.

  1. Tests, written first, in a new tests/test_release_probe.py (fast tier: they build small masks and smoke files, no model): a mask a few pixels off passes; a mask with IoU below 0.98 fails; a size mismatch fails; null against a mask fails; the box is still compared as before.
  2. Change compare_smoke; leave the other subcommands alone.
  3. Checks: the new tests pass and were seen failing first; scripts/rehearse_deploy_local.sh passes end to end with the new /crop answer.

5. P3 — the overlay on the page stop

StatusOpen not started
Blocked byP1

All in webapp/static/index.html, still one file with no build step. The mask is drawn on the photo's own displayed rect, through the same contain-fit math the box uses today.

  1. Rename #image-mask to #image-clip (finding 4).
  2. The tint: everything outside the bean region under 55% black (ticket D4). The box keeps its white outline and loses its box-shadow dimming (D3).
  3. The outline: the bean region's edge as a thin magenta line (255, 0, 255), and a "Show outline" checkbox below the preview that starts ticked, hides the outline only, and keeps its state across uploads in the page visit, not saved (D9).
  4. The fallback: when seg_fallback is true, no tint, no outline, no checkbox, and a note in #crop-note saying no coffee beans were found and the whole photo will be classified (D5).
  5. "Use full photo instead" hides the tint, the box, the outline and the checkbox; "Use detected crop" shows them again without a new request (D6). The overlay is redrawn on window resize, as the box is today.
  6. Checks, by hand on the local dev server (python -m webapp.app) at desktop and phone widths: the tray smoke photo, a frame-filling photo, a portrait EXIF-rotated photo, a HEIC photo, and a negative that falls back. Screenshots go to the owner.
  7. Stop for the owner: look at the overlay on the dev server or the screenshots, and accept it or ask for changes.
