Implementation plan: the mask overlay

The order of work for ticket OPS-6. Three strands: the server sends the mask, the deploy's smoke check learns to compare it, and the page draws it; then the deploy. The server comes first because the other two consume its answer. No phase changes a classification number.

Built from a read of the code at a290ce4, not from the ticket alone. Four things the ticket does not spell out turned up. All are folded in below; none needs a decision.

  1. The smoke comparison would fail on any mask string. compare_smoke passes the whole /crop body to _max_abs_diff, which requires strings to be equal. P2 takes mask out of both bodies before that and compares it decoded, by IoU. No test covers compare_smoke today; P2 adds the first.
  2. The mask must match the thumbnail's size to the pixel. /preview sizes the thumbnail with PIL's Image.thumbnail, which rounds. P1 takes the size from one helper used by both endpoints, instead of recomputing it in /crop.
  3. /crop cannot tell a fallback from "no crop" today. crop_info is None both on a ML-2 D18 fallback and when there is nothing to crop; the segmenter's own seg_fallback diagnostic is dropped. P1 returns it.
  4. #image-mask in index.html is a CSS clipping box, not a mask. Next to a segmentation mask the name misleads. P3 renames it #image-clip.

A review the same day, against 5a391dd, found four more. The owner amended D10 for findings 6 and 7; the rest are folded in.

  1. /crop has only the cropped mask. segment_bean_region returns the mask cut to the D4 box, and the full photo's mask stays inside segment_and_crop. Its diagnostics go into classify_one's entry, so the full mask cannot travel there. P1 adds a separate path for /crop and checks /classify bit-identical (ticket R5).
  2. load_rgb_image ignores EXIF orientation, on purpose. The thumbnail and the mask are both the stored pixels; the orientation test guards that they stay so (ticket R3, D10).
  3. IoU 0.98 was far looser than the evidence (about 1e-6 of pixels differ across CPUs). Now 0.999, not 1 (ticket R2, D10).
  4. A cached page can meet a server without mask after a rollback. P3 handles it (ticket R6).

1. Phase order and why

P1 fixes the shape of /crop's answer, which P2 and P3 both read; they can run in either order after it. P3 stops for the owner to look at the overlay before anything ships; P4 stops for the owner's go to deploy. /classify's route is not touched in any phase; P1 touches the segmenter code it shares, and proves its answers unchanged.

3. P1 — /crop returns the mask

StatusOpen not started
Blocked byNone

/crop gets the full photo's mask, scales it to the thumbnail's size, and sends it as a 1-bit PNG, base64 (ticket D7). On a fallback the mask is null and seg_fallback is true (D5). The mask is the full photo's mask scaled down, not the cropped one: the bean region outside the D4 box is part of it (D3). Today only the cropped one reaches /crop (finding 5), so the first task exposes the full one.

  1. Before any change, record release_probe.py classify on the compare photos of webapp/deploy/fixtures.txt, named by their repo paths (its --list wants them flat in one --dir, as on the VM), on the devcontainer, as the baseline for the parity check below.
  2. Expose the full photo's mask: BeanCrop gains photo_mask, the bool mask predict_mask returned, set on both branches of mask_and_crop. coffeecv/infer.py gains bean_region_preview(rgb, cfg) for /crop, returning (photo_mask or None on a fallback, crop_info, seg_fallback). It shares one helper with segment_bean_region for the segment_and_crop call and the crop_info shaping, so the two cannot disagree on the box. segment_bean_region's return value and diagnostics stay as they are: diagnostics end up in classify_one's entry (finding 5).
  3. One helper gives the thumbnail size for a decoded photo's (w, h); /preview and /crop both use it (finding 2).
  4. /crop: scale the bool mask to that size (area average, then ≥ 0.5), encode as a mode-1 PNG, base64, in mask; add seg_fallback (finding 3). cropped, box and needs_review keep their meaning. Update the docstring and webapp/README.md's description of /crop.
  5. Tests, written first, in a new tests/test_webapp_crop.py under the real_data tier. webapp.app creates its log directory and loads the model at import, so the test sets COFFEE_CV_LOG_DIR to a temporary directory before importing it, and skips when the model or the smoke photo is not pulled, as tests/test_release_manifest.py does. The cases (ticket D10):
    • On the tray smoke photo, which is not square: the mask's size equals the /preview JPEG's, it is not empty, and it agrees with the full-resolution mask by a path independent of the resize helper: the full mask sampled at each thumbnail pixel's centre, IoU ≥ 0.99. A swapped width and height fails.
    • On a copy of the smoke photo written to a temporary file with an Orientation tag of 6 (no photo is committed): the mask's size equals the thumbnail's, and both are the stored pixels' shape scaled down, not rotated (finding 6).
    • On a fallback, with coffeecv.segment_beans.BeanSegmenter.predict_mask patched to return an empty mask: mask is null and seg_fallback is true.
  6. Measure the margins for P2's threshold on the smoke photo's thumbnail mask: the IoU against itself shifted by one pixel, and against itself with its boundary pixels flipped at the rate ML-2 P0 measured. Write both in the Activity entry (ticket R2).
  7. Checks: the new tests pass and were seen failing first; release_probe.py compare-classify against the baseline passes with the default --tol 0, bit-identical (ticket R5); tests/test_release_manifest.py still passes (no new file opened); /crop's box on the smoke photo is unchanged; the mask's size in bytes on the smoke photo is written in the Activity entry (ticket R4); scripts/check.sh --full passes.

4. P2 — the smoke check compares the mask

StatusOpen not started
Blocked byP1

compare_smoke pops mask from the expected and the served /crop bodies, compares the rest as today, and decodes the two masks: they must be the same size, both null or both present, and their IoU ≥ 0.999 (ticket D10, R2). Its summary line prints the IoU and the count of differing pixels next to the box diff, so each deploy records how close the two machines' masks are.

  1. Tests, written first, in a new tests/test_release_probe.py (fast tier: they build small masks and smoke files, no model): a mask with a few boundary pixels flipped passes; the same mask shifted by one pixel fails; a size mismatch fails; null against a mask fails; the box is still compared as before. The test masks are large enough (a few hundred pixels across) that a one-pixel shift lands below 0.999, as on a real thumbnail.
  2. Change compare_smoke; leave the other subcommands alone.
  3. Checks: the new tests pass and were seen failing first; scripts/rehearse_deploy_local.sh passes end to end with the new /crop answer.

5. P3 — the overlay on the page stop

StatusOpen not started
Blocked byP1

All in webapp/static/index.html, still one file with no build step. The mask is drawn on the photo's own displayed rect, through the same contain-fit math the box uses today.

  1. Rename #image-mask to #image-clip (finding 4).
  2. How it is drawn: the PNG decodes opaque black and white, so it cannot be used as a tint as is. Decode it into an off-screen canvas at its natural (thumbnail) size, read it with getImageData, and write one overlay canvas of the same size: 55% black where the mask is 0, magenta on edge pixels, clear elsewhere. The overlay canvas is placed and scaled into the photo's displayed rect by the same contain-fit math as the box, so a resize repositions it without recomputing the tint.
  3. The tint: everything outside the bean region under 55% black (ticket D4). The box keeps its white outline and loses its box-shadow dimming (D3).
  4. The outline: the bean region's edge as a magenta line (255, 0, 255) about 2 CSS px wide at the displayed scale. A one-pixel edge at the thumbnail's 1024 px is half a CSS pixel on a phone, so the edge is widened by a radius taken from the display scale, and redrawn on resize only when that radius changes. No outline along the photo's own border, unlike seg_overlay.py: it would frame every frame-filling photo in magenta. The owner sees both choices at the stop. A "Show outline" checkbox below the preview starts ticked, hides the outline only, and keeps its state across uploads in the page visit, not saved (D9).
  5. The fallback: when seg_fallback is true, no tint, no outline, no checkbox, and a note in #crop-note saying no coffee beans were found and the whole photo will be classified (D5). The needs-review note shares #crop-note but cannot fire at the same time: a segmenter model's needs_review is always false (infer.py, segment_bean_region).
  6. A /crop answer with no mask field (a cached page against a rolled-back server, finding 8) shows the box outline only, with no tint and no error.
  7. "Use full photo instead" hides the tint, the box, the outline and the checkbox; "Use detected crop" shows them again without a new request (D6).
  8. Checks, by hand on the local dev server (python -m webapp.app) at desktop and phone widths: the tray smoke photo, a frame-filling photo, a portrait photo stored sideways with an Orientation tag, a HEIC photo, a negative that falls back, and a /crop answer with mask removed. Screenshots go to the owner, with a note that the portrait photo shows sideways as it does today (finding 6), so it is not read as an overlay bug.
  9. Stop for the owner: look at the overlay on the dev server or the screenshots, and accept it or ask for changes.
