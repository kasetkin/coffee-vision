Implementation plan: the mask overlay

The order of work for ticket OPS-6. Three strands: the server sends the mask, the deploy's smoke check learns to compare it, and the page draws it; then the deploy. The server comes first because the other two consume its answer. No phase changes a classification number.

Built from a read of the code at a290ce4, not from the ticket alone. Four things the ticket does not spell out turned up. All are folded in below; none needs a decision.

  1. The smoke comparison would fail on any mask string. compare_smoke passes the whole /crop body to _max_abs_diff, which requires strings to be equal. P2 takes mask out of both bodies before that and compares it decoded, by IoU. No test covers compare_smoke today; P2 adds the first.
  2. The mask must match the thumbnail's size to the pixel. /preview sizes the thumbnail with PIL's Image.thumbnail, which rounds. P1 takes the size from one helper used by both endpoints, instead of recomputing it in /crop. Superseded by finding 10: the mask no longer has to match the thumbnail's size.
  3. /crop cannot tell a fallback from "no crop" today. crop_info is None both on a ML-2 D18 fallback and when there is nothing to crop; the segmenter's own seg_fallback diagnostic is dropped. P1 returns it.
  4. #image-mask in index.html is a CSS clipping box, not a mask. Next to a segmentation mask the name misleads. P3 renames it #image-clip.

A review the same day, against 5a391dd, found four more. The owner amended D10 for findings 6 and 7; the rest are folded in.

  1. /crop has only the cropped mask. segment_bean_region returns the mask cut to the D4 box, and the full photo's mask stays inside segment_and_crop. Its diagnostics go into classify_one's entry, so the full mask cannot travel there. P1 adds a separate path for /crop and checks /classify bit-identical (ticket R5).
  2. load_rgb_image ignores EXIF orientation, on purpose. The thumbnail and the mask are both the stored pixels; the orientation test guards that they stay so (ticket R3, D10).
  3. IoU 0.98 was far looser than the evidence (about 1e-6 of pixels differ across CPUs). Now 0.999, not 1 (ticket R2, D10).
  4. A cached page can meet a server without mask after a rollback. P3 handles it (ticket R6).

A review as a Python web developer, against 214daa4, found two more; the owner answered both.

  1. An answer from an earlier upload can land on the next photo. The file input stays enabled while /preview and /crop run. P3 adds a token per upload (ticket R7, D13).
  2. The mask and the thumbnail need a shared frame, not a shared pixel grid. The page stretches the mask to the photo's displayed rect as it places the box by fractions, so /crop scales the mask by its own rounding and /preview is not touched (ticket D7 amended, R3). The mask's non-bean pixels are transparent, so P3 draws the tint and the outline by compositing, with no pixel readback (ticket D14).

1. Phase order and why

P1 fixes the shape of /crop's answer, which P2 and P3 both read; they can run in either order after it. P3 stops for the owner to look at the overlay before anything ships; P4 stops for the owner's go to deploy. /classify's route is not touched in any phase; P1 touches the segmenter code it shares, and proves its answers unchanged.

3. P1 — /crop returns the mask

StatusDone 2026-10-07, 9788325, 2d89e75, 02c2854 and the commit closing it
Blocked byNone

/crop gets the full photo's mask, scales it to long side ≤ PREVIEW_MAX_DIM, and sends it as a 1-bit palette PNG with its non-bean pixels transparent, base64 (ticket D7, amended). On a fallback the mask is null and seg_fallback is true (D5). The mask is the full photo's mask scaled down, not the cropped one: the bean region outside the D4 box is part of it (D3). Today only the cropped one reaches /crop (finding 5), so the first task exposes the full one.

  1. Before any change, record release_probe.py classify on the compare photos of webapp/deploy/fixtures.txt, named by their repo paths (its --list wants them flat in one --dir, as on the VM), on the devcontainer, as the baseline for the parity check below.
  2. Expose the full photo's mask: BeanCrop gains photo_mask, the bool mask predict_mask returned, set on both branches of mask_and_crop. coffeecv/infer.py gains bean_region_preview(rgb, cfg) for /crop, returning (photo_mask or None on a fallback, crop_info, seg_fallback). It shares one helper with segment_bean_region for the segment_and_crop call and the crop_info shaping, so the two cannot disagree on the box. segment_bean_region's return value and diagnostics stay as they are: diagnostics end up in classify_one's entry (finding 5).
  3. /crop: scale the bool mask to long side ≤ PREVIEW_MAX_DIM, aspect kept, never up (area average, then ≥ 0.5); encode it as a 1-bit palette PNG, palette black and white, index 0 (not bean) transparent: putpalette([0, 0, 0, 255, 255, 255]), then save(..., "PNG", bits=1, transparency=0, optimize=True) (checked on Pillow 12.3: bit depth 1, colour type 3, a tRNS chunk, an exact round trip); base64, in mask; add seg_fallback (finding 3). /preview is not touched (finding 10). cropped, box and needs_review keep their meaning. Update the docstring and webapp/README.md's description of /crop.
  4. Tests, written first, in a new tests/test_webapp_crop.py under the real_data tier. webapp.app creates its log directory and loads the model at import, so the test sets COFFEE_CV_LOG_DIR to a temporary directory before importing it, and skips when the model or the smoke photo is not pulled, as tests/test_release_manifest.py does. The cases (ticket D10):
    • On the tray smoke photo, which is not square: the mask's long side is ≤ 1024 px and its aspect is the photo's within one pixel, it decodes to indices 0 and 1 with index 0 transparent, it is not empty, and it agrees with the full-resolution mask by a path independent of the resize code: the full mask sampled at each mask pixel's centre, IoU ≥ 0.99. A swapped width and height fails.
    • On a copy of the smoke photo written to a temporary file with an Orientation tag of 6 (no photo is committed): the mask's aspect and the thumbnail's are both the stored pixels' within one pixel, not rotated (finding 6).
    • On a fallback, with coffeecv.segment_beans.BeanSegmenter.predict_mask patched to return an empty mask: mask is null and seg_fallback is true.
  5. Measure the margins for P2's threshold on the smoke photo's /crop mask: the IoU against itself shifted by one pixel, and against itself with its boundary pixels flipped at the rate ML-2 P0 measured. Write both in the Activity entry (ticket R2).
  6. Checks: the new tests pass and were seen failing first; release_probe.py compare-classify against the baseline passes with the default --tol 0, bit-identical (ticket R5); tests/test_release_manifest.py still passes (no new file opened); /crop's box on the smoke photo is unchanged; the mask's size in bytes on the smoke photo is written in the Activity entry (ticket R4); scripts/check.sh --full passes.

4. P2 — the smoke check compares the mask

StatusDone 2026-10-07, 58a6191 and the commit closing it; the rehearsal stopped at deploy 2 for disk space, see Activity
Blocked byP1

compare_smoke pops mask from the expected and the served /crop bodies, compares the rest as today, and decodes the two masks to bool by palette index: they must be the same size, both null or both present, and their IoU ≥ 0.999 (ticket D10, R2). Its summary line prints the IoU and the count of differing pixels next to the box diff, so each deploy records how close the two machines' masks are.

  1. Tests, written first, in a new tests/test_release_probe.py (fast tier: they build small masks and smoke files, no model): a mask with a few boundary pixels flipped passes; the same mask shifted by one pixel fails; a size mismatch fails; null against a mask fails; the box is still compared as before. The test masks are large enough (a few hundred pixels across) that a one-pixel shift lands below 0.999, as on a real /crop mask.
  2. Change compare_smoke; leave the other subcommands alone.
  3. Checks: the new tests pass and were seen failing first; scripts/rehearse_deploy_local.sh passes end to end with the new /crop answer.

5. P3 — the overlay on the page stop

StatusOpen not started
Blocked byP1

All in webapp/static/index.html, still one file with no build step. The mask is drawn on the photo's own displayed rect, through the same contain-fit math the box uses today, and stretched to it (ticket D7). No pixel is read back from a canvas (D14).

  1. Rename #image-mask to #image-clip (finding 4).
  2. A token per upload (ticket D13): each pick of a photo starts a new upload, and the handler checks its token after every wait (the /preview answer, the /crop answer, the mask's decode()), dropping a stale answer before it touches the preview, the box, the canvases or #crop-note.
  3. How it is drawn (D14): the mask's data URL decodes into an Image (await img.decode()); two canvases, tint and outline, sit in #image-clip under the box, with CSS size the photo's displayed rect and backing size that rect times devicePixelRatio. Each drawImage stretches the mask to the whole canvas. positionCropOverlay stays the one place that draws: it runs on the preview's load, on the /crop answer and on resize, and draws nothing until both the preview and the mask have loaded. A resize redraws both canvases.
  4. The tint: fill the tint canvas with rgba(0, 0, 0, 0.55), then draw the mask with destination-out, which clears the bean region (ticket D4). The box keeps its white outline and loses its box-shadow dimming (D3).
  5. The outline: on the outline canvas, draw the mask at 16 offsets on a circle of radius 2 CSS px (times devicePixelRatio), then the mask once with destination-out, then a magenta (255, 0, 255) fill with source-in: a 2 CSS px ring just outside the bean region, over the tint, covering no bean pixel (D2, D14). The part of the ring beyond the canvas is cut off, so the photo's own border never gets a line, unlike seg_overlay.py, which would frame every frame-filling photo in magenta. A "Show outline" checkbox in a <label> below the preview starts ticked, shows or hides the outline canvas only, with no redraw, and keeps its state across uploads in the page visit, not saved (D9).
  6. The fallback: when seg_fallback is true, no tint, no outline, no checkbox, and a note in #crop-note saying no coffee beans were found and the whole photo will be classified (D5). The needs-review note shares #crop-note but cannot fire at the same time: a segmenter model's needs_review is always false (infer.py, segment_bean_region).
  7. A /crop answer with no mask field (a cached page against a rolled-back server, finding 8) shows the box outline only, with no tint and no error.
  8. "Use full photo instead" hides the tint, the box, the outline and the checkbox; "Use detected crop" shows them again without a new request (D6).
  9. Checks, by hand on the local dev server (python -m webapp.app) at desktop and phone widths, on a phone with Safari and one with Chrome: the tray smoke photo, a frame-filling photo, a portrait photo stored sideways with an Orientation tag, a HEIC photo, a negative that falls back, a /crop answer with mask removed, and a second photo picked while the first one's /crop is in flight (D13). Screenshots go to the owner, with a note that the portrait photo shows sideways as it does today (finding 6), so it is not read as an overlay bug.
  10. Stop for the owner: look at the overlay on the dev server or the screenshots, and accept it or ask for changes.
