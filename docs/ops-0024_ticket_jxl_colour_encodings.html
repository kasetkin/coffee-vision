Ticket OPS-24 · coffee-vision · what the site accepts

Canonicalization reads a JPEG XL in linear Rec.2020 and in the other standard-range colour encodings, not only sRGB and D7's

The owner exports Canon CR3 raws from darktable to JPEG XL and wants to keep Rec.2020. The site refuses every Rec.2020 export darktable offers, because canonicalization reads a JPEG XL only in sRGB or in the canonical photo's own encoding (Rec.2020 primaries, BT.709 transfer), which darktable cannot write. This ticket widens what is read to linear Rec.2020 and the other standard-range encodings. HDR transfers (PQ, HLG) belong with ML-20. Written; decisions open, not planned, not implemented.

1. Summary

Today _decode_jxl reads a non-canonical JPEG XL only if its header declares, as an enumeration, RGB, D65, and either sRGB primaries with the sRGB transfer, or Rec.2020 primaries with the BT.709 transfer. Anything else is Unreadable: another transfer, other primaries, an embedded ICC profile, or floating-point samples. After this ticket it also reads the other standard-range enumerated encodings (linear Rec.2020 first) by building each one's source profile for LittleCMS. Which encodings, how their profiles are made, and what happens to ICC-tagged, float and HDR files are D1–D5.

2. Background

  • The rule today. canonical.py, _decode_jxl: want_icc, a colour space other than RGB, a white point other than D65 or more than one extra channel is refused. Of the enumerations, only (sRGB, sRGB) → LittleCMS's sRGB and (BT2100, BT709) → the committed rec2020_bt709.icc (ML-19 D46) are read. A float32 decode is refused. The docstring gives the reason: imagecodecs returns no ICC profile from a JPEG XL, so the source profile has to come from the header.
  • The header already parses the rest. jxl_header.py names primaries sRGB, BT2100 and P3, and transfers BT709, Linear, sRGB, PQ, DCI and HLG, plus an explicit gamma.
  • A linear Rec.2020 profile already exists. canonical.LINEAR_REC2020, built with ic.cms_profile for rawpy's output (RAW path), is the profile a linear Rec.2020 JPEG XL needs.
  • darktable's export list (owner's screenshot, 2026-11-13): sRGB, Adobe RGB, linear Rec709, Rec709, linear Rec2020, PQ Rec2020, HLG Rec2020, PQ P3, HLG P3, Display P3, linear ProPhoto. There is no Rec.2020 with a gamma curve. Of these, only sRGB opens today. "Rec709" (sRGB primaries, BT.709 transfer) and Display P3 (P3 primaries, sRGB transfer) are refused too; tests/test_canonical.py already encodes a Display P3 JPEG XL as a canonical near-miss.
  • What darktable writes (R1), read 2026-11-13 from the owner's eleven exports of one Canon EOS 90D photo (6984×4660, quality 90) with read_header and imagecodecs, not from their names. Every file is a bare, XYB (lossy) codestream with no boxes, no extra channels, orientation 1, and its colour as an enumeration: darktable embedded no ICC profile in any of them.

    The 10- and 12-bit files decode to uint16 with white at 1023 and 4095, and still canonicalize to the 8-bit file's pixels as the models read them (mean 123.16, max 255), so they need no change. The float file holds values from −0.295 to 1.074: colours outside sRGB, which clipping would flatten. The 8-bit linear file averages 58 of 255 where the 8-bit sRGB one averages 123: its shadows sit in few levels (R3). Not yet exported: linear Rec709, Rec709, PQ P3, HLG P3, linear ProPhoto.
  • Custom primaries are not read today. jxl_header._customxy reads past a custom white point's or primaries' xy coordinates without keeping them, so an Adobe RGB file's profile cannot be built from the header as it is parsed now.
  • RAW is no way round it. The site develops a CR3 straight into Rec.2020, but caps a RAW upload at 16 MP (openapi.json), which most current Canon bodies exceed.
  • The docs promise more than the code does. openapi.json and llms.txt list "JPEG XL" as accepted, with no word about colour encodings.
  • Dataset intake reads JPEG XL the same way. Since ML-28 D4 (ML-28) the owner's darktable JPEG XL developments go through the same canonicalization, so this widening also changes which of them the dataset can take (D5).

3. Before and after

Now

  • A JPEG XL is read in two enumerated encodings only: sRGB, and Rec.2020 with the BT.709 transfer.
  • darktable's linear Rec2020, Rec709, Display P3, Adobe RGB and ProPhoto exports are refused.
  • The refusal names the primaries and transfer, and does not say what to export instead.

After

  • Every encoding D1 admits is read through a source profile built for it, then canonicalized like any other photo, into Rec.2020 (BT.709 transfer).
  • PQ and HLG are refused with a message that points at an SDR export, until ML-20 decides otherwise (D3).
  • openapi.json and llms.txt say which JPEG XL encodings are read.

4. What does not change

  • The canonical photo. Still Rec.2020 with the BT.709 transfer, quality 95, read back as 8-bit sRGB (ADR 0033, ML-19 D7). Only what can be read into it widens.
  • Photos read today. An sRGB or D7-encoded JPEG XL, and every other format, canonicalizes to the same bytes; no re-canonicalization, no retrain.
  • The format list. JPEG XL is already an accepted format (ADR 0034); this ticket changes which of its colour encodings decode, not which formats reach a decoder.
  • One library. imagecodecs at its pinned version does the decode and the colour conversion (ADR 0033, ML-19 D44); no new dependency.

5. Risks

IDRiskEvidence and mitigation
R1darktable writes some profiles as an embedded ICC profile, not an enumeration, so widening the enumerations alone does not open them. Checked 2026-11-13 for sRGB, linear Rec2020, Display P3, Adobe RGB, HLG Rec2020 and PQ Rec2020 (Background): all enumerated, none with an ICC profile; Adobe RGB as custom primaries with an explicit gamma. Still to export and record: linear Rec709, Rec709, PQ P3, HLG P3, linear ProPhoto.
R2A profile built in code differs by rounding from libjxl's own, and moves pixels. ML-19 D46 measured a rounding-only profile difference moving 3% of 8-bit pixels by one level. For an input profile this changes only the new encodings' photos, which no model has seen yet. D2 decides whether that matters.
R3An 8-bit linear export bands in the shadows before it reaches the site. A property of the file, not of the decoder. Mitigation: the refusal and API docs advise 16-bit for linear encodings; nothing is refused for it.

6. Decisions

D1Which enumerated encodings are read? (a) linear Rec.2020 only (b) every SDR combination of sRGB, P3 and BT2100 primaries with the sRGB, BT.709, linear and explicit-gamma transfers, D65 (c) (b) plus custom primaries, which darktable's Adobe RGB export uses (and so _customxy keeping the xy coordinates) (d) (c) plus DCI white point and transfer Open.
D2Where does each new source profile come from? (a) built in code with ic.cms_profile, as LINEAR_REC2020 is (b) libjxl's own profile for each encoding, committed and hash-tested as D46's is Open.
D3PQ and HLG (HDR transfers)? (a) refused, with a message pointing at an SDR export; left to ML-20 (b) tone-mapped into the canonical range here Open.
D4Float samples (darktable's 32-bit export, values outside 0–1), and a JPEG XL with an embedded ICC profile (none of darktable's exports so far; other software)? Float: (a) still refused (b) decoded and clipped to 0–1, out-of-gamut colour flattened (c) decoded and converted by LittleCMS on float32 unclipped, clipped only in Rec.2020. ICC: (a) still refused (b) the profile read from the codestream by our own parser (c) a separate ticket Open.
D5Dataset intake: does the widening apply to the owner's darktable JPEG XLs in dataset/ as well (ML-28)? (a) yes, one decoder for both (b) visitor uploads only Open.

7. Scope and acceptance

  • R1's table: every darktable export profile, its header colour fields, and whether it opens before and after (six profiles recorded 2026-11-13; five to go).
  • A darktable linear Rec2020 export, 8- and 16-bit, uploads and gets an answer on the live site.
  • Tests: every encoding D1 admits decodes to the same canonical pixels (within a stated tolerance) as the same image encoded in sRGB; every one it does not admit is Unreadable with its message.
  • Today's sRGB and D7 JPEG XL fixtures canonicalize to unchanged bytes (tests/test_canonical_fixtures.py).
  • openapi.json and llms.txt list the encodings read.

Out of scope

  • HDR: PQ and HLG rendering and gain maps (ML-20).
  • Changing the canonical photo's own encoding, or what the models read (ADR 0033).
  • Raising the 16 MP cap on RAW uploads.
