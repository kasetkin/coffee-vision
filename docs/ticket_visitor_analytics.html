Owner request, 2026-08-31. After the server logging shipped: visitor analytics with Umami, as its own decision, not bundled with the logging rollout. Put on hold the same day, after a full plan and review.

1. Summary

Today the site has no analytics or tracking script at all; the only record of use is the structured server log (docs/logging_plan.html, no client IPs). After this ticket, Umami counts page views, served from the same VM under the site's own domain, with its dashboard reachable only through an SSH tunnel. The work is an install on the VM, nginx routes, the tracker in the page, and retention.

2. Background

  • Logging shipped on 2026-08-31 (3f08b4b, 1e6f42e, 7c73fab, 2b5e718): JSON request logs joined to nginx's access log by request_id, one-year rotation, no client IP. The app log stays the record of each classification; analytics adds no per-classify events.
  • The 2026-08-31 design was a Claude Code plan file, not a repo file, and is lost. What it settled: native install, no Docker (.out-of-scope/containerised-serving.md), Node.js through pnpm; Umami pinned at v3.3.1; path-based routing under /stats/, not a subdomain; nginx exposes exactly /stats/script.js and /stats/api/send as exact-match locations and nothing else; 90-day retention by a cron SQL job (Umami v3 has no retention setting); deploy files templated (CODING_STANDARDS.md).
  • The design predates OPS-1. The site now runs from immutable releases under its own user (ADR 0008), so where Umami lives and how its nginx routes are deployed must be re-checked against scripts/deploy_webapp.sh and webapp/deploy/.

3. Before and after

Now

  • No analytics; visits are visible only in the server log.

After

  • Umami counts page views under /stats/; dashboard over an SSH tunnel only; 90 days kept.

4. What does not change

  • The server log. It stays the one record of classifications and keeps no client IP.
  • The release layout. Umami is a separate service; the webapp's releases do not carry it.

5. Risks

IDRiskEvidence and mitigation
R1Every page-view beacon 404s silently. Umami's tracker bakes its collection endpoint in at build time (COLLECT_API_ENDPOINT / COLLECT_API_HOST), defaulting to /api/send, not a path next to the script. Under /stats/ routing, build with COLLECT_API_ENDPOINT=/stats/api/send, or the beacon falls through to the page's try_files. Found in the 2026-08-31 review.
R2The first migration fails on PostgreSQL 16. Since PostgreSQL 15 a non-owner role cannot create in the public schema, so prisma migrate deploy fails with "permission denied for schema public". Create the database as CREATE DATABASE umami OWNER umami;. Found in the 2026-08-31 review.
R3A default admin login on the dashboard. Umami installs with a documented default login; change it at install, before the tunnel is first used.

7. Scope and acceptance

  • A page view on the live site appears in the dashboard, and /stats/api/send returns success (R1).
  • Only /stats/script.js and /stats/api/send are reachable from outside; the dashboard only through the tunnel.
  • Rows older than 90 days are deleted by the retention job.
  • No client IP is stored by the site's own logs.

Out of scope

  • Per-classification analytics events (the server log covers them).
  • Docker (.out-of-scope/containerised-serving.md) and third-party analytics.
