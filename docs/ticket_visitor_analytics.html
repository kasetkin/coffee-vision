1. Summary

Today the logs count requests on each host, but nothing ties one photo's lines together across the page, the front and yappy, the page measures nothing, and a photo the page refuses never reaches a server. After this ticket every photo has a timeline (GLOSSARY.md): the page's own times and choices, sent once per photo, joined by one request ID to the front's and yappy's lines, which say what they alone know. One script reads both hosts and prints the counts and each step's times, or shows them on a local page. The work splits into the shared request ID, the hosts' new fields, the page's timeline and its endpoint, --verify, the script, and a line on the page saying what is logged.

2. Background

  • The 2026-08-31 design (a Claude Code plan file, lost; recorded here 2026-10-07): Umami v3.3.1 installed natively with pnpm on the VM, under /stats/, with exactly /stats/script.js and /stats/api/send public and the dashboard over an SSH tunnel, 90 days kept by a cron SQL job. Its review found two blockers: the beacon's path baked in at build time (R1 then), and CREATE DATABASE umami OWNER umami needed on PostgreSQL 15 and later (R2 then). Re-read 2026-11-09: the first is wrong, since the tracker sends to its own script's directory unless told otherwise (src/tracker/index.ts); the second stands. Umami is now v3.4.1 (2026-10-23, a security fix).
  • Why not Umami now (D2, .out-of-scope/visitor-analytics-service.md). ADR 0031 puts analytics at the front, the proxy: 958 MB of memory, 262 MB available and 547 MB of swap in use on 2026-11-09, with the check service allowed 600 MB for a 60 MP photo (ML-19 D38), no Node.js, 2.9 GB of disk free. And the front's site sees every visitor as 127.0.0.1: the proxy's stream {} block reads the SNI and opens its own connection to the site, so the visitor's address is known only there, per TLS session (OPS-15 D20). Umami's visitor is a hash of the IP and the browser, so every visitor with the same browser would be one visitor for a month.
  • What is logged today. The front's access log (365 days): time, nginx's $request_id, the app's ID, status, request, time, bytes, Origin (OPS-19 D3); no browser, no referrer. The check service: one text line per request to the journal, with no request ID; for a photo it canonicalizes, its extension, size in pixels, depth, time and memory; for one "canonical as sent", nothing about the photo. The app on yappy (365 days): decode_ms, crop_detect_ms (segmentation), inference_ms, preview_ms (since the app's start, decode and segmentation included), latency_ms, under an 8-hex ID it makes itself. Since ML-19 yappy sees only the canonical .jxl, so its upload_format and upload_bytes are the canonical photo's, not the visitor's original. The session log, the only file with the visitor's IP (30 days), is world-readable (-rw-r--r--) on the proxy.
  • The preview carries the mask. yappy decodes, segments, then sends the first part: the thumbnail, the mask and the box together (ADR 0023, OPS-7 D3); classification follows as the second part. "Preview received" and "mask received" are one moment.
  • Two tickets left questions here. OPS-17 D7 (which control a photo came from) and OPS-20's out of scope (whether visitors open either list). This ticket answers the first (D6); the second stays out (D11).

3. Before and after

Now

  • Page loads in the front's log, with no browser or referrer, so crawlers count as visits.
  • Each host logs under its own ID; the check service's line has none, and goes to the journal.
  • The page measures nothing; a photo it refuses, a busy wait or an abandoned photo leaves no trace.
  • The visitor's original format and size are not logged for an example or a canonical upload.
  • Reading any of it is a hand-made grep on each host.

After

  • The front's log adds the browser and the referrer (D5).
  • One request ID, made by the front's nginx, on every host's line and in the page's timeline (D8).
  • The page sends one timeline per photo, its own steps only (D7); the check service writes it, and its own line per request, to a file of its own, 365 days, no IP (D9).
  • One script prints the counts and each step's median and 90th percentile, or serves them on a local page (D13).
  • The page says what is logged (D15).

4. What does not change

  • No visitor IP in anything new. The session log stays the only file with it, 30 days (OPS-15 D20); the script never reads it (D13). Transparent proxying, which would carry the IP to the front's site, is not part of this ticket (D21).
  • The photo is never stored. Its name, format and size are logged (D10), not its pixels.
  • The API's contract. /analyze's request and answer stay as they are (ADR 0023, ADR 0035); a caller that sends no timeline loses nothing.
  • The answer's shape. The preview still carries the mask, after segmentation; a preview made at the front was considered and left for now (D12).
  • No identifier on the visitor's device. No cookie, no stored ID, so no unique-visitor count and no consent banner.

5. Risks

IDRiskEvidence and mitigation
R1Junk or forged timelines skew the numbers or fill the proxy's disk. Anyone can POST to /timeline, and the front cannot limit per visitor (it sees 127.0.0.1). The five layers of D17: the page reports only what the hosts cannot see; a strict schema; nginx's body limit, Origin rule and one global rate; a timeline counted only when its ID is a real request's; everything shown treated as text. 2.9 GB free on the proxy (2026-11-09).
R2A filename kept for a year names a person. Accepted by the owner (D10): usually not sensitive, useful for debugging. The page says so (D15).
R3The check service cannot write its file. Its unit runs with ProtectSystem=strict, is installed by root, and the deploy refuses a release whose rendered unit differs from the installed one. The owner installs the new unit and log directory before the release (plan).
R4Timelines go missing. A beacon can be lost when a phone kills the page. The hosts' lines are complete without it; the script counts photos with no timeline, so a loss shows as a number, not as silence.
R5The app's new request ID breaks what reads the old one. 8 hex characters today, nginx's 32 after. Read by webapp/app.py, its test and both nginx templates only (2026-11-09); the app keeps making its own ID when none, or a malformed one, comes in.
R6Crawlers counted as visitors. Filtered by the browser string (D5), which a crawler can fake; timelines come only from pages that ran the script, so photo counts are mostly people.

7. Scope and acceptance

  • A photo picked on the live site has one timeline: the page's, the front's and yappy's lines under one request ID, with each of §2's steps that applies to it.
  • An example, a "canonical as sent" upload, a busy wait, "Use full photo instead", an abandoned photo and a photo refused on the page each show as such.
  • The front's access log has the browser and the referrer; the session log is 0640.
  • No new line anywhere holds a visitor IP.
  • A malformed, oversized or other-site timeline is refused; one with an invented ID is shown as unverified, not counted.
  • The script prints the counts and each step's median and 90th percentile from both hosts, serves them on a local page, keeps nothing locally and reads no session log.
  • --verify's requests are left out of the counts, and --verify checks that its timeline was written.
  • The page and llms.txt say what is logged.

Out of scope

  • Umami or any analytics service, and third-party analytics (D2; .out-of-scope/visitor-analytics-service.md, .out-of-scope/containerised-serving.md).
  • Unique visitors, and any identifier stored on the visitor's device.
  • Visitors opening the format or example list (D11).
  • A preview made at the front (D12).
  • Transparent proxying and per-visitor limits (D21).
