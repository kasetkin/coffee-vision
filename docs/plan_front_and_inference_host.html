Implementation plan: the front and the inference host

The order of work for ticket OPS-15. Four strands are built and tested locally first (the front's check service, the inference host's site, the front's site and page, the two-host deploy); then the owner prepares the proxy, and the cutover moves the domain. Nothing changes for a visitor until P6.

Built from a read of the code at d9212c6 and of both hosts on 2026-11-02, not from the ticket alone. Four things the ticket does not cover turned up. They are folded in below, and the ones that need a decision are Q1–Q2 (§2).

  1. One log line cannot have two retentions. D13 keeps IPs 30 days and the rest 365, but the app writes one JSON line per request. Q1.
  2. A standard-library service has no production WSGI server. D7 rules out gunicorn on the front. Q2.
  3. The front cannot import coffeecv (numpy, PIL, OpenCV) to share the format allowlist with load_rgb_image. A test holds the front's list to coffeecv.photo_io's instead (P1).
  4. --compare's fixture is 7.6 MB, over D15's cap. It runs the release on yappy itself, not through the front, so it is unaffected; --verify uses the 1.8 MB smoke photo.

1. Phase order and why

Everything that can be proven locally comes first, so the proxy is touched only once its files are tested. The inference host's site (P2) can deploy alone behind today's passthrough only if it keeps the public port, so it ships together with the rest at P6. No phase changes a model number: the bytes the model decodes are the visitor's own (D2).

3. P1 — The front's check service

StatusOpen not started
Blocked byQ2

A new webapp/front/ package with its own pyproject.toml and uv.lock, Python 3.12, no dependencies (D7). It takes POST /analyze from the front's nginx, checks the file part and forwards the request unchanged to the inference host, streaming the answer back as it arrives.

  1. The check: the file part's leading bytes against the formats load_rgb_image reads (JPEG, PNG, WebP, HEIC/HEIF and AVIF by ftyp, JPEG XL, TIFF-based RAW and DNG, CR3, RAF and the rest of RAW_EXTENSIONS); a RAW file by its extension, as the app dispatches. A mismatch is a 400 {"error": ...} in the app's wording.
  2. Over 5 MB: a 413 {"error": ...} (D15), also enforced by nginx.
  3. The forward: the original request body, X-Real-IP passed on (D13), to the inference host's tailnet address from the release's config, with D16's timeouts. The answer is relayed chunk by chunk with X-Accel-Buffering: no and X-Request-Id kept.
  4. Unreachable or refusing inference host before an answer starts: a 503 {"error": "the classifier is offline"} (D12), apart from the gate's busy 503.
  5. Tests: every fixture format accepted; a renamed text file, a truncated header and an oversized body refused; the allowlist held to coffeecv.photo_io's by a test on the training side; streaming checked against a fake inference host that sends its two parts seconds apart; the offline 503. Added to scripts/check.sh.
  6. Checks: suite green; the service's RSS under a 5 MB upload, measured locally.

4. P2 — The inference host's site

StatusOpen not started
Blocked byQ1

yappy's nginx template becomes the inference host's: plain HTTP on its tailnet address only (D5), no TLS, no page.

  1. /analyze only, everything else a 404; limit_conn 1 as a backstop (D11); client_max_body_size 20m and MAX_UPLOAD_BYTES unchanged (D15); the whole upload buffered before gunicorn (D10); X-Accel-Buffering passed on.
  2. The access log per Q1, with its logrotate rule.
  3. The listen address comes from the deploy's config, not the template, so no tailnet address enters git.
  4. Checks: nginx -t on the rendered template in the rehearsal; the public port is no longer bound.

6. P4 — One release, two hosts

StatusOpen not started
Blocked byP1, P2, P3

scripts/deploy_webapp.sh deploys one release ID to both hosts (D3, D14).

  1. Stage both: the inference release on yappy as today, the front release (static files, the check service and its uv environment, the rendered site) on the proxy, every file checked against its digest.
  2. Stop both: coffee-cv-web on yappy for the smoke (ADR 0026), the check service on the proxy; the proxy's nginx keeps running (D14).
  3. Flip both, start both, then nginx -t and one reload on the proxy (D8), then --verify through the domain.
  4. Any failure after a stop reverts both to previous and starts them; --rollback switches both. A release's front site rides in the release, so a rollback restores it too (OPS-9's goal).
  5. scripts/rehearse_deploy_local.sh runs two hosts, with a failure injected on each in turn.
  6. Checks: the rehearsal passes, both injected failures leave both hosts on the old release, and a rollback returns both.
