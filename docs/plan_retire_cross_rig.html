Implementation plan: retire cross-camera validation

Sequencing for ticket ML-1 now that D1–D7 are answered. The work is mostly deletion, three renames (D4), and one real rewrite (D1(b)'s pooled split). This plan orders it so nothing imports from a module after it's deleted: extract what survives first, rewrite the split, rename, drop the cross_rig MixStyle mode, delete the fold-only modules and fix dvc.yaml, clean up docs, then test.

1. Phase order and why

run_folds.py, xrig_eval.py, and photo_pooling_eval.py are all marked for deletion, but each has one piece something outside the fold world still imports. Deleting file-first would break run_all_rigs.py, fit_frozen_head.py, and the DINOv3 test fixture at import time. So: extract survivors → rewrite the split → rename (D4) → drop cross_rig MixStyle → delete the fold-only modules and fix dvc.yaml → docs → tests.

2. Phase 1 — extract what survives

  1. Move dirty_provenance_paths, stale_crop_stages, and the generic dvc repro runner run() out of run_folds.py into config.py (or a new small repro_utils.py). run_all_rigs.py and fit_frozen_head.py import these for preflight checks and must keep working. These are the sweep drivers' shared preflight machinery, not fold-specific logic — they were only living in run_folds.py by accident of file history.
  2. Move build_xrig_dataset (xrig_eval.py:183-210) into fold_data.py, renamed off "xrig" (e.g. build_capture_dataset). Update coffeecv_dino/reference.py's import. Generic "every photo of one capture dir, split="all"" builder, no camera-holdout semantics. Feeds the DINOv3 backbone-equivalence test fixture, imported at module scope by test_dino_backbone.py and make_dinov3_fixture.py before any skip decorator runs.
  3. Confirm pool_photos (photo_pooling_eval.py) has no importer left once coffeecv_dino/screen.py is deleted (Phase 5) — its only other reference, in ood_eval.py, is a standalone copy, not an import. No move needed if confirmed; delete with the rest of photo_pooling_eval.py.

3. Phase 2 — rewrite the split (D1(b))

The target is dataset.py's split_photos_by_class (today called once per (rig, class) pair from MultiPhotoPatchDataset.__init__'s per-rig loop, dataset.py:406-430) and fold_data.py:build_fold_datasets — not run_all_rigs.py or fit_frozen_head.py, which only call through this shared path.

  1. Gather all photos for a class across every capture dir first, then split 70/15/15 once per class instead of once per capture dir. This is the actual D1(b) behavior change: pooled per-class split, no per-camera grouping.
  2. Reseed the split from (seed, class_idx) plus a stable per-photo key (e.g. sorted relative path), not the current rig_idx-dependent seed. Pooling makes split membership independent of capture-dir order in principle; the seed should match that, or the split silently changes whenever train_capture_dirs is reordered.
  3. Leave the patch-box extraction RNG (_extract_photo, dataset.py:461-470) alone — it seeds patch selection within an already-assigned photo, unrelated to which split the photo lands in.
  4. Drop heldout_rig/xrig_ds/the cross-rig branch from build_fold_datasets and FoldDatasets entirely. Keep the module/function/class names — D4 doesn't ask for this rename, don't add scope.
  5. Remove the xrig_metrics/xrig_loader/xrig_ds paths and the empty-predictions_xrig.csv workaround from train_baseline.py (the dvc.yaml plot declaration that workaround exists for is removed in Phase 5).

4. Phase 3 — D4 rename sweep

Rewrite the Rig dataclass's docstring in dataset.py while renaming it — "the rig is a first-class dimension because cross-rig transfer is the thing being measured" is no longer true. CAPTURES (the list of the four cam_* dirs, formerly RIGS in run_folds.py) needs a new home since that file is gone — put it in dataset.py next to Capture.
