1. Phase order and why

The country label is a code change that existing data can prove harmless. With classes.txt still in the old format, the new loader must give today's classes and today's patches bit for bit. The metadata strip is the same kind of change: only hashes move, and every crop must come out identical. Doing both before the merge keeps each check clean. Once the new photos are in, outputs are supposed to change, and nothing could tell a regression from the merge. The classes.txt rewrite lands in the same commit as the merge, so coverage_report never sees a declared class with no photos, or photos of an undeclared class.

3. P1 — one class list, every reader taught it

Today each of 14 call sites runs sorted(load_class_labels(path)), and the label is a position in a list of folder ids. Every one of them has to learn the country, and old frozen lists must keep reading as they do today. So the format is parsed in one place. A new stdlib-only module, coffeecv/class_list.py, has no torch, so coverage_report and the release can import it cheaply. Its interface:

ClassList(keys, labels, folders)    # keys: label order (index = model output); folders: key -> class folder ids
  .index(key)   .key_of(folder_id)
load_classes(path)    # the format decides:
                      #   D15  "id;Country[,Region[,Subregion]];misc"  -> one class per country, keys in order of
                      #        first appearance by id (= classes_short_map.txt), label = key (D2)
                      #   old  "id;label"  -> one class per folder id, sorted, label as written: every shipped
                      #        model's frozen .classes.txt reads exactly as today
folder_classes(path)  # one class per folder id, sorted, either format: for seg_lists and the DINOv3 fixture
read_coffees(path)    # [Coffee(folder_id, country, farm_region, misc)]: coverage_report, diagnostics

Parsing is strict. A file is all one format or an error. D15 lines must be ASCII with a non-empty country, and ids must not repeat. The format is the switch between country and folder classes: a new model's frozen .classes.txt is a copy of the D15 file, so it serves countries, and an old one serves folders. No config field is needed.

Dataset

  1. pooled_class_photos(captures, folder_ids) (dataset.py:343) pools every folder of one class across every capture. A capture is absent only if it has none of them. D6 then needs no code: the per-(capture, class) budget at dataset.py:581 already spreads over every photo of that class in that capture, whichever folder it came from.
  2. MultiPhotoPatchDataset takes the ClassList instead of (classes_file, class_ids). PatchMeta gains folder_id, the coffee a patch came from: the farm-region diagnostic (D10) and R3 need it.
  3. Keep the split key (capture, photo name). A country pools several folders inside one capture, so names must be unique across them. They are today, including the new photos (no repeated stem under any class_* folder). split_photos_by_class already raises on a duplicate; a test covers the cross-folder case.
  4. Delete load_class_labels and get_class_label once nothing imports them, so no reader can bypass the format check. PatchCoffeeDataset (dataset.py:96) goes with them. It is dead code, imported nowhere, but it calls load_class_labels, so the deletion would fail without it.
  5. An empty pool is an error, not a skip. ood_eval.id_photos (:241-246) continues past a class with no photos, so a country key passed where its folder ids belong would silently drop that country from the OOD probe's positives. It raises instead, naming the class. split_census (dataset.py:425) keeps recording pooled: 0, and split_report exits non-zero on it.

4. P2 — the strip tool, and the new photos first

The 2026-09-30 ood_positives strip is documented in its README, but its tool is not in the repo. D13 now covers JPEG, HEIC and DNG, and the strip must be repeatable, so it becomes a committed tool: python -m coffeecv.strip_metadata DIR... --manifest labels/ml3/strip_manifest.csv [--dry-run].

  1. Backend: exiftool for all three formats. It edits metadata without re-encoding image data, and handles HEIC and DNG, which a hand-written JPEG segment editor would not. Add libimage-exiftool-perl to .devcontainer and record its version in the manifest. The strip runs locally only; the VM receives stripped files.
  2. What goes is D13.1 as a deny list: GPS, device and lens serials, maker notes, C2PA/JUMBF, extended XMP (HDR+), embedded thumbnails and previews, owner/artist fields. The rest stays, ICC and Orientation included. They stay because they are not private and they describe the photo; no stage of this pipeline applies them. Segcrop and serving both decode with load_rgb_image, which ignores EXIF rotation (segcrop_session.py:16-17), and the crop stage that did apply it goes in P2b. The exact exiftool arguments are fixed by a --dry-run over one file of every (camera, format) pair, which lists what would go.
  3. Per file, in a temp copy, replaced atomically only if every check passes: decode with dataset.load_rgb_image before and after (rawpy for DNG), and the pixel arrays must be equal. For a JPEG with an MPF gain map, the secondary image's bytes must be equal too, and likewise a HEIC's auxiliary images (depth, gain map). The pixel check cannot see a lost Orientation or ICC profile, because load_rgb_image ignores both. So every kept field is compared byte for byte before and after: Orientation, the ICC profile's bytes, Make, Model, DateTimeOriginal and the exposure tags. This matters for the new photos: 80 of the 90 Sony photos have Orientation 3, 6 or 8, and every Pixel and OnePlus photo carries an ICC profile. A post-strip audit with exiftool -a -G1, including embedded documents, fails on any deny-listed tag. The manifest row is path, sha256_before, sha256_after, pixel_sha256, removed. It is the re-key map for P3 and the record of D13.
  4. Fix the set of new photos (Q4): the owner confirms there are no more, then the count per (session, class folder) is recorded in labels/ml3/new_photos.csv, with path, camera model from EXIF and capture time, and copied into the ticket's tables. Checks before anything is stripped: every class folder is one of the fourteen in D15 (a new coffee needs its own classes.txt line first); every random_date_raccoon photo is from the Pixel 9 Pro, because the folder joins cam_pixel (D6); and every dated session's photos are from its own camera. Nothing joins after this step.
