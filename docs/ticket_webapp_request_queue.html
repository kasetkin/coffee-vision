Owner request, 2026-10-17. While planning OPS-7: create a ticket for implementing a queue (or maybe even batch processing) for multiple users in parallel. Facts and a stub only, not a full ticket yet.

1. Summary

Stub. The question is how the service should handle a second visitor while a first visitor's photo is in flight: queue them, run them side by side, or batch their photos through the models together. Nothing is proposed yet.

2. Background

Read at 6c45b78; to be checked when the ticket is written.

  • One worker, one request. gunicorn runs one sync worker with --timeout 30 (webapp/deploy/coffee-cv-web.service.template). nginx caps the backend at one request in flight server-wide (limit_conn 1) and gives a second request an immediate 503 (webapp/deploy/coffee-cv.nginx.conf.template). After OPS-7 the page shows a busy message for it (OPS-7 D12).
  • How long the worker is busy. After OPS-7, every pick costs a full classification in one request: about 9.4 s median and 11.4 s max server-side on yappy's GPU (ML-7 P10, 13 fixtures, /classify, segmenter included). Before OPS-7, a visitor who stopped at the mask held it for about 2 s (OPS-7 R6).
  • The models are loaded per worker. Each worker loads and warms every graph at boot (ADR 0021), and on the GPU it must prove the GPU ran the warm-up (ADR 0020). A second worker means a second copy of the models and its own GPU context; its memory on yappy has not been measured.
  • Batching. A photo is 40 patches through DINOv3, run at the batch its LiteRT manifest names. The converted graphs are built for that batch (ADR 0022), so batching patches from several photos means fitting them to that batch or converting again. The segmenter runs one photo at a time.
  • Constraints. No state between requests (ADR 0023); no containers on the server (.out-of-scope/containerised-serving.md); the request log records latency_ms and, after OPS-7, preview_ms, which show how busy the worker is.

3. Questions to research

  • A queue in front of the one worker (in nginx, or in the app) against more workers; which one stays inside gunicorn's and nginx's 30 s timeouts with several visitors waiting.
  • The GPU and host memory a second worker costs on yappy.
  • Whether DINOv3, and the segmenter, can batch photos from several visitors, and what that does to each visitor's wait.
  • What the page shows while a photo is queued (its place in the queue, or the progress circle only).
  • How much traffic there is: the request log's rate of 503s and of overlapping requests.
