1. Summary

Today a photo's identity in most records is its path under dataset/. After this ticket, the records name a photo by its hash, and one committed index maps each hash to the path or paths where the file is now. A rename or move then changes one line of the index, rebuilt by a command, instead of every record that names the photo. The work splits into: the index; the small records (pool exclusions, reference photos, strip manifest); the segmenter dataset and the labelling sessions; the classifier's split, which changes every split and so lands with a training session; and retiring the rename tool. Which hash, how copies count and how the split is derived are the owner's decisions (D1–D7), all open.

2. Background

  • Records keyed by path today (read 2026-11-03):
    • labels/ml5/seg_dataset.yaml: one entry per photo, keyed by path, with its sha256; a group is named by a path. The file is append-only (ML-5 D11): a rebuild refuses a listed path that is gone, so on 2026-11-03 13 renamed entries were edited by hand.
    • labels/ml5/split_units.yaml: the owner's ties between photos, by path.
    • coffeecv/seg_review.py: a photo's item id is seg_dataset.photo_id(path), which also names its mask files under data/ml5_labels/<session>/. Since ML-16 D2 a carried or rechecked label falls back to the sha256 when the path is gone; seg_predict and seg_finetune read the same ids (seg_finetune checks each label's sha256).
    • labels/ml3/pool_exclude.csv: session, class folder and file name. merge_rig --exclude silently skips a row that names no photo, so the row for the declined IMG_20261008_092822 stopped applying when the owner renamed it (fixed in f15342d; its derivation in analysis/ml3/mask_review.py follows renames by sha256 since 3249e92).
    • coffeecv_dino/reference_photos.txt: a path, with an optional draw key so a rename keeps the fixture (ML-14 D16).
    • labels/ml3/strip_manifest.csv: one row per path; a rename adds a same-hash row (99 rows on 2026-11-03).
    • dataset/segmenter_positives.manifest.csv: duplicate_of names a path (15 rewritten on 2026-11-03).
    • coffeecv/dataset.py: the classifier's photos are CapturePhoto(capture, name), and split_photos_by_class sorts a class's photos by (capture, name), then shuffles with a seed of (seed, class_idx, 9999) (ML-1 D1(b)). Any rename or added photo in a class reshuffles that whole class's split. The patch boxes are drawn per photo_idx in the same sorted order (ML-8 D2), so they move too.
    • coffeecv/rename_photos.py with labels/photo_renames.csv (8 rows): rewrites the live records after a rename, for OOD negatives only.
  • Copies (2026-11-03): dataset/ holds 2,465 photos with 2,407 distinct sha256s, in 58 copy groups. Most are segmenter positives copied from pool photos (54 of the 313). One hash can therefore have several paths, and the index must allow that.
  • Copies the classifier counts twice: 4 byte-identical pairs in the classifier's pool (1,433 photos), all in 2026-08-25__oneplus, each a -2 file beside its original: Colombia Pink Bourbon 193337626 and 193428942, Vietnam Robusta 193823453 and 193927646. On the split as computed on 2026-11-03, 3 of the 4 pairs sit in two splits: 193428942 in train and val, 193823453 in train and val, 193927646 in train and test. seg_dataset already keeps one entry per sha256.
  • A file's hash is not permanent: the metadata strip changes the file's bytes and keeps its pixels (ADR 0013). The strip manifest records sha256_before, sha256_after and pixel_sha256 for every photo it handled.

3. Before and after

Now

  • A rename means finding and editing every record that names the photo, by hand or with rename_photos (OOD negatives only).
  • A missed record silently stops applying, or a test fails far from the rename.
  • Adding or renaming one photo reshuffles its class's classifier split.
  • A byte copy in the classifier's pool is two photos, and can sit in two splits.

After

  • Records name a photo by its hash; one committed index maps each hash to its present path or paths.
  • A rename is one command that rebuilds the index; a test fails while any index line names a missing file.
  • Depending on D4, a photo's classifier split does not move when other photos are added or renamed.
  • Depending on D3, a byte copy is one photo to the classifier.

4. What does not change

  • The photos' names and folders. The owner keeps naming and moving files as now; the class still comes from the class folder.
  • Run records. analysis/, outputs/, experiments/, verdict logs and model cards keep the paths their runs read, as rename_photos already leaves them.
  • Grouping and splits already given. The segmenter dataset's entries keep their split and group (ML-5 D11, ADR 0029); only how they are keyed changes.
  • The strip. coffeecv.strip_metadata and its checks stay as they are (ADR 0013).

5. Risks

IDRiskEvidence and mitigation
R1A re-strip changes every key it touches. The strip rewrites metadata, so the file sha256 changes while the pixels stay (ADR 0013). Mitigation: strip before a photo enters any record, as now; or key by the pixel hash (D1 (b)); the strip manifest's before and after hashes allow a re-key.
R2A new classifier split breaks comparison with earlier runs. Any change to how the split is derived (D4) moves photos between train, val and test, so runs before and after cannot be paired (ADR 0002). Mitigation: it lands with a training session that sets a new baseline, not alone.
R3Re-keying an append-only file could move a listed entry. seg_dataset.yaml is append-only (ML-5 D11). Mitigation: a migration test that every entry keeps its split and group, and that the set of photos is unchanged.
R4One hash, several paths. 58 copy groups under dataset/. The index maps a hash to a list of paths, and a record that means one particular copy (the segmenter positive, not its pool original) has to say which (D5).
R5Mask files renamed under DVC. If labelling items become hashes (D6), mask files of new sessions get new names; earlier sessions stay under their ids, so the carry needs to read both. Closed sessions are not rewritten.

6. Decisions

IDQuestionOptionsOwner decision
D1Which hash is the key? (a) the file's sha256, as seg_dataset.yaml and the labels already record (b) the decoded pixels' sha256 (pixel_sha256), which survives a metadata change but costs a full decode per photo (c) both: file sha256 as the key, the pixel hash kept to re-key after a re-strip. Claude recommends (a). Open.
D2Where does the hash-to-path map live? (a) a committed index, e.g. labels/photo_index.csv (sha256, path), rebuilt by a command and checked by a test against the files (b) computed from dataset/ on every run, nothing committed (c) the strip manifest, extended. Claude recommends (a): a diff shows each rename, and it needs no photos checked out to read. Open.
D3Does a byte copy in the classifier's pool count once? (a) yes, one photo per hash, in one split (b) no, as today. Claude recommends (a): today 3 of the 4 pairs sit in two splits. Open.
D4How is a photo's classifier split derived? (a) from its own hash and the seed, per photo, so it never moves when others are added or renamed; the split shares then hold only on average (b) the same seeded shuffle as now, over photos sorted by hash instead of (folder, name) (c) unchanged (ML-1 D1(b)). Both (a) and (b) change every split once, and land with a training session (R2). Claude recommends (a). Open.
D5How is seg_dataset.yaml keyed, and which copy does an entry mean? (a) keyed by sha256 with the path as a value, migrated once with every split and group kept; an entry names its source, so a segmenter positive and its pool original stay apart (b) keyed by path, as now. Claude recommends (a). Open.
D6How does a labelling session name a photo and its mask files? (a) by sha256, from the next session on; the carry reads earlier sessions by their ids (b) by the path-derived id, with ML-16 D2's sha256 fallback, as now. Open.
D7Is "a photo is identified by its hash" an ADR? (a) yes, a new ADR; it replaces ML-1 D1(b)'s sort key if D4 is (a) or (b) (b) no, decisions in this ticket only. Open.

7. Scope and acceptance

  • D1–D7 decided by the owner, and a plan written.
  • The hash-to-path index and its rebuild command; a test fails while an index line names a missing file or a photo is missing from the index.
  • The pool exclusions, reference photos, strip manifest and the segmenter positives' duplicate_of name photos by hash.
  • The segmenter dataset and the owner's split units keyed per D5, every listed entry's split and group unchanged.
  • The labelling, fine-tuning and prediction tools per D6.
  • The classifier per D3 and D4, landing with a training session.
  • A rename of a photo by the owner needs only the index rebuild: tested by renaming a photo in a fixture and running every record's reader.
  • coffeecv/rename_photos.py and labels/photo_renames.csv retired, or kept for history only.

Out of scope

  • ML-16 and its training session: this ticket starts after it.
  • Rewriting run records, closed labelling sessions or experiment folders to new keys.
  • Near-copies by content (coffeecv.find_duplicates): only byte-identical files share a hash.
