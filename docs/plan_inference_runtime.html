Implementation plan: LiteRT and ONNX Runtime on the iGPU, Vulkan against OpenCL

The order of work for ticket ML-7, first strand: how the two models run on yappy's Intel iGPU through two runtimes, LiteRT and ONNX Runtime (ORT), on two GPU paths, Vulkan and OpenCL. Each runtime's CPU path and the current PyTorch serving are measured beside them. Both models are converted once per format (.tflite, .onnx) and checked on the CPU first, so every path of a runtime runs the same files on the same inputs. LiteRT on OpenCL needs a source build and is the last resort: tried only if every other cell fails (ticket D10). No phase changes what the site serves. The phases that move serving onto a runtime are added after the owner chooses (ticket D2).

Built from a read of the code at 69d9870, the LiteRT 2.3.0 wheel's Python sources, ORT's execution-provider docs and the host itself, not from the ticket alone. Eight things the ticket does not cover turned up. They are folded in below, and the ones that need a decision are Q1–Q4 (§3).

  1. No backend switch in LiteRT's Python. GpuOptions has enforce_f32 but no way to pick OpenCL or WebGPU. Environment.create(runtime_path=...) does exist (ai_edge_litert/environment.py), and LiteRT loads its GPU library from that directory. So each LiteRT path gets its own runtime directory holding libLiteRt.so and exactly one GPU library (P2, P6).
  2. Vulkan can silently land on the CPU. Without GPU access, Vulkan offers only llvmpipe, Mesa's CPU renderer (ticket 2.4). This holds for both runtimes' Vulkan paths. Every Vulkan run sets VK_ICD_FILENAMES to Intel's driver alone, so llvmpipe cannot be picked, and strace confirms which driver loaded (P2).
  3. LiteRT's OpenCL path needs the unversioned libOpenCL.so, which yappy does not have. A symlink in the scratch directory, found through LD_LIBRARY_PATH, avoids installing a package on the host (P6).
  4. The LiteRT converter needs torch below 2.14, and training is on 2.14 (ticket 2.3). So it gets its own uv project, apart from the training lock (ADR 0007) (P1).
  5. The devcontainer's disk has 11 GB free (99% used), likely too little for a Bazel build of LiteRT; the owner is freeing space. Its glibc (2.41) is newer than yappy's (2.36), so a library built here may not load there. yappy has 139 GB free but 4 slow cores and 7.5 GB of RAM (Q1, P6).
  6. A self-built accelerator may not fit the wheel. LiteRT #10446 was a libc++/libstdc++ mismatch between LiteRT's libraries. The OpenCL library is built at the wheel's own tag, v2.3.0, with the repo's toolchain. If it still won't load, libLiteRt.so is built from the same tag and the pair is used (P6).
  7. ORT reaches both paths from pip, with no build. Vulkan comes through the WebGPU plugin (onnxruntime-ep-webgpu 0.4.0, 2026-09-22, manylinux 2.28, for onnxruntime 1.24.4 or later). Like LiteRT's, it uses Dawn, which runs on Vulkan on Linux. OpenCL comes through the OpenVINO execution provider (onnxruntime-openvino). It replaces the onnxruntime package, so it gets its own venv. ORT's docs give the WebGPU plugin no precision setting, so its fp32 is checked, not assumed (P2, P3).
  8. The ONNX export gets its own environment too. The training lock has no onnx (ML-2 D23; third_party/efficientvit/PATCHES.md row 3). The export runs from a separate uv project at the training lock's torch 2.14 and timm 1.0.30, plus onnx, onnxscript and onnxruntime. It is the same torch the release route would export with (ticket D6) (P1).

1. How each path reaches the GPU

All the GPU cells end at the same iGPU through the same kernel driver. What differs is the software between the runtime and the driver. "WebGPU" is a browser standard, but no browser is involved here: both runtimes bundle Dawn, Chrome's WebGPU engine, as a plain library, and Dawn turns WebGPU calls into Vulkan calls. Vulkan is used for compute, not graphics: the model's operations become compute shaders, programs the GPU runs on tensors, and nothing is drawn.

LayerVulkan pathOpenCL path
LiteRTlibLiteRtWebGpuAccelerator.so, in the wheel. ML Drift writes each operation as a WGSL compute shader, and Dawn runs them. Last resort (D10, P6). libLiteRtOpenClAccelerator.so, built from source at v2.3.0. ML Drift writes each operation as an OpenCL C kernel.
ORTThe onnxruntime-ep-webgpu plugin. ORT's own WGSL kernels, run by Dawn. The OpenVINO execution provider. OpenVINO's GPU plugin compiles the graph into OpenCL kernels.
API layerDawn translates WebGPU into Vulkan, through the libvulkan.so.1 loader. The ICD loader libOpenCL.so picks the vendor driver.
DriverMesa 22.3.6 ANV, Intel's open-source Vulkan driver (libvulkan_intel.so), which compiles shaders to GPU code. Intel NEO 22.43 (libigdrcl.so), Intel's OpenCL driver, which compiles kernels to GPU code.
Kernel and devicei915 through /dev/dri/renderD128 (the render group), on the Alder Lake-N iGPU: 24 EUs at 750 MHz, sharing the host's RAM.

Each cell compiles the same model through a different stack. Speed and exact numbers can differ, and any cell can fail where another works. The ML Drift paper measured LiteRT's OpenCL path about 2× faster than its WebGPU path on one Intel model, on another OS. That is the case for keeping LiteRT on OpenCL as the last resort rather than dropping it.

2. Phase order and why

Conversion comes first and runs on the CPU. A .tflite or .onnx that already disagrees with PyTorch on the CPU would make every GPU number for it meaningless, and both GPU paths of a runtime run the same file. The Vulkan paths come next, then ORT's OpenCL path. None of the three needs a build. The measurement runs once, with every cell in one interleaved session, so that heat and clock speed affect them alike. P5 reports, and the owner chooses. P6, LiteRT on OpenCL, runs only if P5 finds that every other cell failed and the owner says go (D10). No phase changes a served number. New files go to the scratch directory on yappy and to analysis/ml7_gpu/.

4. P1 — Convert both models to both formats and check them on the CPU

StatusOpen not started
Blocked byNone

The graphs are the models as served (ticket §4), cut where serving's own code already cuts them, and the same in both formats:

  • The DINOv3 graph returns the 1536-d cls_mean readout. The head and the guard stay in numpy, so parity is judged on what they consume.
  • The segmenter is two graphs, as in segment_beans.py: the encoder, and the prompt encoder with the mask decoder. The box goes in as two points labelled 2 and 3, and all three masks and their IoUs come out. multi3 is selected outside the graph, as today. The ONNX export is of these same wrapper modules, not upstream's scripts. Upstream's use the legacy exporter, and their single-mask option picks by IoU.
  • LiteRT has no dynamic batch (litert-torch #870), so DINOv3 is converted at batch 8 (40 patches = 5 calls) and at batch 40 (1 call). The ONNX files use the same fixed batches, so the two runtimes run the same shapes.
  1. Two uv projects, each with its own pyproject.toml and uv.lock. Both import coffeecv.backbones and the vendored efficientvit as they are.
    • analysis/ml7_gpu/convert_litert/: torch 2.13 (CPU), timm 1.0.30, litert-torch 0.9.4, segment-anything 1.0.
    • analysis/ml7_gpu/convert_onnx/: the training lock's torch 2.14.0 and timm 1.0.30, segment-anything 1.0, onnx, onnxscript, onnxruntime and onnxconverter-common.
    coffeecv.dino_classifier refuses a timm mismatch, not a torch one. The readouts are compared with torch 2.14's in the last task, so a torch 2.13 difference would show there.
  2. Inputs: for each of the 13 photos in webapp/deploy/fixtures.txt, the serving path's preprocessed tensors, from the training environment (torch 2.14): the 40 patches [40,3,224,224], the encoder input [1,3,1024,1024] and the transformed box. Saved to inputs.npz, so every path gets the same bytes and preprocessing is outside the comparison.
  3. References: the PyTorch outputs for those inputs in the training environment. These are the readouts, the encoder embeddings, the three low-resolution masks and their IoUs, the final masks after postprocess_masks and the D18 rule, and the probabilities and guard verdicts. Saved to refs.npz.
  4. Convert to LiteRT: dino_b16_readout_b8.tflite, dino_b16_readout_b40.tflite, xl0_encoder.tflite, xl0_v3_decoder_box.tflite. Record for each the op histogram, any tensor above 4-D (these fall back to the CPU on LiteRT's GPU), the file size and sha256.
  5. Export to ONNX, the same four graphs as .onnx, with torch.onnx.export(dynamo=True) at the default opset 20. Weights go in an .onnx.data file beside each graph, and the two always travel together. Record for each the op histogram, the opset, the file sizes and sha256. If an execution provider in P2 or P3 rejects opset 20, re-export at 18 and note it.
  6. fp16 copies of the four .onnx files, for ORT's WebGPU cell (Q4). They are converted with onnxconverter-common's float16 converter with keep_io_types=True, so inputs and outputs stay fp32 and the scripts do not change. They are not checked on the CPU, where ORT has no fp16 kernels.
  7. The bicubic neck, in both formats. If it does not convert exactly, stop and report. It is not swapped for bilinear, which would be a different model (ticket §4). ONNX has a cubic Resize; its coefficient must match torch's (-0.75), checked in the exported graph.
  8. CPU parity against refs.npz, with D7's measures: readout cosine and max-abs difference, mask IoU after the shared post-processing, top-1 and guard verdict per photo. LiteRT runs on XNNPACK at 4 threads, ORT on its default CPU provider at 4 threads. The files, inputs and references go to DVC, like the other analysis outputs.
  9. Checks: all eight files convert, and CPU parity meets D7's proposal (cosine ≥ 0.99999, IoU ≥ 0.999, no change of answer) for each, or the gap is reported with its cause before P2.

5. P2 — The Vulkan paths on yappy

StatusOpen not started
Blocked byP1
  1. Scratch directory ~/ml7/ on yappy as coffee-deploy (already in render). It holds the P1 files and one uv venv per stack. Nothing goes under /opt/coffee-cv.
    • venv_litert: ai-edge-litert==2.3.0 and numpy.
    • venv_ort_webgpu: onnxruntime (1.24.4 or later) and onnxruntime-ep-webgpu==0.4.0.
  2. LiteRT's runtime directory ~/ml7/rt_vulkan/: the wheel's libLiteRt.so and libLiteRtWebGpuAccelerator.so, and no other GPU library.
  3. analysis/ml7_gpu/run_litert.py and analysis/ml7_gpu/run_ort.py: one graph, one path, one precision per process. Both log the same fields: cold start (time to the first output, kernel compilation included), warm times, CPU time against wall time and peak RSS. Both save the outputs to an .npz.
    • LiteRT: options are passed in full (Options with CpuOptions(num_threads=4)), because the hardware_accel= shortcut silently sets 1 CPU thread. It logs is_fully_accelerated().
    • ORT: session.disable_cpu_ep_fallback=1, so a graph that does not fit the GPU fails rather than half-running on the CPU. It logs get_providers() and verbose node placement.
  4. Prove the GPU ran, for each runtime. Use VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/intel_icd.x86_64.json, so llvmpipe is not on offer. strace -f -e trace=openat must show libvulkan_intel.so and /dev/dri/renderD128 opened. CPU time well below 4× wall time is the sanity check: llvmpipe would keep all cores busy.
  5. If LiteRT 2.3.0 crashes in WebGPU start-up (LiteRT #10446, fixed on 2026-10-09 after 2.3.0), retry with the nightly wheel and note the version.
  6. Checks: each of the eight files runs on its runtime's Vulkan path. For each, the log records whether it ran fully on the GPU (if not, which ops fell back or why the session refused), the IoU and cosine against refs.npz, and one cold and one warm time. For ORT's WebGPU plugin, the readout's cosine shows whether it computes in fp32.

7. P4 — The comparison run

StatusOpen not started
Blocked byP2, P3, Q3, Q4

One session on yappy, with the webapp and nginx stopped and nothing else running. The cells are run in rotation, three rounds, so that clock speed and heat fall on all of them alike. Each cell is a fresh process: one cold start, 3 warm-ups, then 20 timed runs.

  1. For each cell and graph (DINOv3 at batch 8 and 40, encoder, decoder), record:
    • whether it ran fully on its device;
    • cold start;
    • warm median and p90;
    • CPU time against wall time;
    • peak RSS, and the drop in MemAvailable (GPU memory is host memory);
    • NaN or Inf in any output;
    • a 100-call stability run on the faster DINOv3 batch.
  2. Parity is computed locally from the saved outputs with the repo's code, against refs.npz and D7's measures, per photo.
  3. Per photo, the encoder, decoder and 40 patches are added up into a projected model time for each cell. It is labelled a projection: preprocessing, decoding and the second segmenter pass for /crop are left out, and are the same for every cell.
  4. Results go to analysis/ml7_gpu/results.json and the scripts to analysis/ml7_gpu/, committed. The raw outputs go to DVC.
  5. Checks: every cell either has its numbers or is marked failed, with the error. No GPU cell counts unless P2's or P3's proof of the GPU held in that session.

9. P6 — Last resort: LiteRT on OpenCL, built from source stop

StatusOpen not started; runs only under D10
Blocked byP5 (no cell passes, and the owner says go)

Tried only if every other cell failed (ticket D10). It is the one cell that needs a source build, a library that has to match the wheel it plugs into, and a rebuild on every LiteRT upgrade (ticket R6).

  1. Check out google-ai-edge/LiteRT at tag v2.3.0 in the devcontainer (Q1). Read litert/runtime/accelerators/gpu/BUILD for the OpenCL target's exact name, and build it with the repo's own Bazel configuration. The build log and commands are kept in analysis/ml7_gpu/opencl_build.md. Built in the devcontainer, the library must show no GLIBC_ version above 2.36 (objdump -T) before it goes to yappy.
  2. Runtime directory ~/ml7/rt_opencl/: the wheel's libLiteRt.so and the built OpenCL library, with no WebGPU library. A libOpenCL.so symlink to /usr/lib/x86_64-linux-gnu/libOpenCL.so.1 sits in ~/ml7/lib/, on LD_LIBRARY_PATH.
  3. Prove OpenCL ran: strace must show libLiteRtOpenClAccelerator.so, libOpenCL.so, NEO's libigdrcl.so and /dev/dri/renderD128, and no libvulkan.
  4. If the library does not load with the wheel's libLiteRt.so, build libLiteRt.so at the same tag and use the pair. That pair, not the wheel, is then what is measured, and the report says so.
  5. Measure it with P4's scripts and fields, in a session of its own, with the PyTorch baseline run again beside it so the two are comparable. The site is stopped for that session only (Q3). Results are added to results.json and the README.
  6. Stop for the owner if the build fails after one working session, if it cannot fit in the devcontainer (Q1), or when the cell is measured: it passes or fails by D10's test, and the owner decides.

Explicitly not in this change

  • Everything in the ticket's "Out of scope".
