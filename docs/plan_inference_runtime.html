  1. Baseline first. The ticket's R1 asks for a per-stage baseline before any integration work. The app already logs decode_ms, crop_detect_ms and inference_ms per request (webapp/app.py), and the segmenter times its resize, encoder, decoder and upsample (segment_beans.py). P0 reads the first and runs the second, before any conversion.
  2. The iGPU's ceiling is low in fp32. These are estimates from public specifications, not measurements. The CPU peaks at about 190 GFLOPS fp32 (4 Gracemont cores, 16 FLOP per cycle, about 2.9 GHz on all cores). The iGPU peaks at about 290 (24 EUs, 16 FLOP per cycle, 750 MHz), or about 580 in fp16. The two share a 6 W package budget and one memory bus. DINOv3 B/16 is about 17.6 GMAC per patch, so 40 patches are about 1.4 TFLOP: at least 7.5 s on this CPU at full efficiency. So in fp32 a GPU cell may tie or lose; the headroom is fp16 on the GPU and int8 on the CPU.
  3. The likely-fastest CPU path was missing. ORT's OpenVINO provider on the CPU joins P3 and P4, in the venv P3 already builds. ORT's own CPU cell also runs a DINOv3 graph with ORT's transformer fusions (P1), since the dynamo exporter leaves attention unfused.
  4. int8 has a path on this CPU. ORT's MLAS swaps in AVX-VNNI int8 kernels when the CPU has them (platform.cpp), and the N100 does. An int8 XL0 encoder is measured for information only; it is judged by mask IoU, and serving it stays with ticket D4. DINOv3 stays fp32 (D4's concern about the head and probe).
  5. A photo replay replaces the projected model time. The projection left out the second segmenter pass for /crop as "the same for every cell", but that pass is an encoder run, which differs per cell. Summed per-graph medians also miss sustained clocks, both models in memory at once, and transfers between stages. P4 times whole photos in one process, the encoder counted twice.
  6. The pass test needs a margin. "Beats the baseline" lets a 3% win through. Q5 set the bar (ticket D15): a replay p90 at least 25% below the baseline's, beyond the spread between rounds.
  7. Proof of the GPU, tightened. ORT's thread pool spin-waits by default, which inflates CPU time on a GPU run and takes power from the GPU on a 6 W chip; GPU cells turn it off. strace proves only that the device was opened. Each run also samples the i915 counters in sysfs, which the deploy user can read without root or a new package (read on yappy 2026-10-13: GPU frequency, RC6 idle time, power-limit throttle flags; intel_gpu_top, perf and turbostat are not installed).
  8. Two exact rewrites instead of a stop. The neck resizes to a fixed 64×64, so its bicubic step is a constant linear map, written as two matmuls with torch's own coefficients. timm's 5-D qkv split is rewritten in 4-D. Both are the same model, so ticket §4 holds, and both formats get them (P1).
  9. fp16 that can answer a question. A blanket fp16 copy predictably overflows in attention. The fp16 ONNX copies keep Softmax, LayerNorm and the attention-score MatMul in fp32 (P1); one blanket copy still checks the NaN (ticket D12).
  10. Continuous parity measures. Top-1 and guard flips over 13 photos carry little weight. Every parity report adds the largest change in a class probability, the probe-score change beside each photo's distance from 0.5, and the largest change in low-resolution mask logits before the threshold.

1. How each path reaches the GPU

All the GPU cells end at the same iGPU through the same kernel driver. What differs is the software between the runtime and the driver. "WebGPU" is a browser standard, but no browser is involved here: both runtimes bundle Dawn, Chrome's WebGPU engine, as a plain library, and Dawn turns WebGPU calls into Vulkan calls. Vulkan is used for compute, not graphics: the model's operations become compute shaders, programs the GPU runs on tensors, and nothing is drawn.

Each cell compiles the same model through a different stack. Speed and exact numbers can differ, and any cell can fail where another works. The ML Drift paper measured LiteRT's OpenCL path about 2× faster than its WebGPU path on one Intel model, on another OS. That is the case for keeping LiteRT on OpenCL as the last resort rather than dropping it.

2. Phase order and why

The baseline comes first: if the models are not most of the time per photo, no runtime fixes the latency, and the owner hears that before any conversion. Conversion comes next and runs on the CPU. A .tflite or .onnx that already disagrees with PyTorch on the CPU would make every GPU number for it meaningless, and both GPU paths of a runtime run the same file. The Vulkan paths come next, then ORT's OpenVINO provider on the GPU and the CPU. None of these needs a build. The measurement runs once, with every cell in one interleaved session, so that heat and clock speed affect them alike. P5 reports, and the owner chooses. P6, LiteRT on OpenCL, runs only if P5 finds that every other cell failed and the owner says go (D10). No phase changes a served number. New files go to the scratch directory on yappy and to analysis/ml7_gpu/.
