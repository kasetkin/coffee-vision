Implementation plan: LiteRT and ONNX Runtime on the iGPU, Vulkan against OpenCL

The order of work for ticket ML-7, first strand: how the two models run on yappy's Intel iGPU through two runtimes, LiteRT and ONNX Runtime (ORT), on two GPU paths, Vulkan and OpenCL. Each runtime's CPU path and the current PyTorch serving are measured beside them, and so is ORT's OpenVINO provider on the CPU. P0 first times where the 20–27 s per photo goes today. Both models are converted once per format (.tflite, .onnx) and checked on the CPU first, so every path of a runtime runs the same files on the same inputs. LiteRT on OpenCL needs a source build and is the last resort: tried only if every other cell fails (ticket D10). No phase changes what the site serves. The phases that move serving onto a runtime are added after the owner chooses (ticket D2).

Built from a read of the code at 69d9870, the LiteRT 2.3.0 wheel's Python sources, ORT's execution-provider docs and the host itself, not from the ticket alone. Eight things the ticket does not cover turned up. They are folded in below, and the ones that needed a decision were Q1–Q4 (§3); Q5 came from the review below. All five are answered.

  1. No backend switch in LiteRT's Python. GpuOptions has enforce_f32 but no way to pick OpenCL or WebGPU. Environment.create(runtime_path=...) does exist (ai_edge_litert/environment.py), and LiteRT loads its GPU library from that directory. So each LiteRT path gets its own runtime directory holding libLiteRt.so and exactly one GPU library (P2, P6).
  2. Vulkan can silently land on the CPU. Without GPU access, Vulkan offers only llvmpipe, Mesa's CPU renderer (ticket 2.4). This holds for both runtimes' Vulkan paths. Every Vulkan run sets VK_ICD_FILENAMES to Intel's driver alone, so llvmpipe cannot be picked, and strace confirms which driver loaded (P2).
  3. LiteRT's OpenCL path needs the unversioned libOpenCL.so, which yappy does not have. A symlink in the scratch directory, found through LD_LIBRARY_PATH, avoids installing a package on the host (P6).
  4. The LiteRT converter needs torch below 2.14, and training is on 2.14 (ticket 2.3). So it gets its own uv project, apart from the training lock (ADR 0007) (P1).
  5. The devcontainer's disk has 11 GB free (99% used), likely too little for a Bazel build of LiteRT; the owner is freeing space. Its glibc (2.41) is newer than yappy's (2.36), so a library built here may not load there. yappy has 139 GB free but 4 slow cores and 7.5 GB of RAM (Q1, P6).
  6. A self-built accelerator may not fit the wheel. LiteRT #10446 was a libc++/libstdc++ mismatch between LiteRT's libraries. The OpenCL library is built at the wheel's own tag, v2.3.0, with the repo's toolchain. If it still won't load, libLiteRt.so is built from the same tag and the pair is used (P6).
  7. ORT reaches both paths from pip, with no build. Vulkan comes through the WebGPU plugin (onnxruntime-ep-webgpu 0.4.0, 2026-09-22, manylinux 2.28, for onnxruntime 1.24.4 or later). Like LiteRT's, it uses Dawn, which runs on Vulkan on Linux. OpenCL comes through the OpenVINO execution provider (onnxruntime-openvino). It replaces the onnxruntime package, so it gets its own venv. ORT's docs give the WebGPU plugin no precision setting, so its fp32 is checked, not assumed (P2, P3).
  8. The ONNX export gets its own environment too. The training lock has no onnx (ML-2 D23; third_party/efficientvit/PATCHES.md row 3). The export runs from a separate uv project at the training lock's torch 2.14 and timm 1.0.30, plus onnx, onnxscript and onnxruntime. It is the same torch the release route would export with (ticket D6) (P1).

Review, 2026-10-13 (ticket D14). An inference review of this plan found it strong on correctness checks and weak on two questions: where the time goes today, and whether this iGPU can win at all. The owner had every finding folded in:

  1. Baseline first. The ticket's R1 asks for a per-stage baseline before any integration work. The app already logs decode_ms, crop_detect_ms and inference_ms per request (webapp/app.py), and the segmenter times its resize, encoder, decoder and upsample (segment_beans.py). P0 reads the first and runs the second, before any conversion.
  2. The iGPU's ceiling is low in fp32. These are estimates from public specifications, not measurements. The CPU peaks at about 190 GFLOPS fp32 (4 Gracemont cores, 16 FLOP per cycle, about 2.9 GHz on all cores). The iGPU peaks at about 290 (24 EUs, 16 FLOP per cycle, 750 MHz), or about 580 in fp16. The two share a 6 W package budget and one memory bus. DINOv3 B/16 is about 17.6 GMAC per patch, so 40 patches are about 1.4 TFLOP: at least 7.5 s on this CPU at full efficiency. So in fp32 a GPU cell may tie or lose; the headroom is fp16 on the GPU and int8 on the CPU.
  3. The likely-fastest CPU path was missing. ORT's OpenVINO provider on the CPU joins P3 and P4, in the venv P3 already builds. ORT's own CPU cell also runs a DINOv3 graph with ORT's transformer fusions (P1), since the dynamo exporter leaves attention unfused.
  4. int8 has a path on this CPU. ORT's MLAS swaps in AVX-VNNI int8 kernels when the CPU has them (platform.cpp), and the N100 does. An int8 XL0 encoder is measured for information only; it is judged by mask IoU, and serving it stays with ticket D4. DINOv3 stays fp32 (D4's concern about the head and probe).
  5. A photo replay replaces the projected model time. The projection left out the second segmenter pass for /crop as "the same for every cell", but that pass is an encoder run, which differs per cell. Summed per-graph medians also miss sustained clocks, both models in memory at once, and transfers between stages. P4 times whole photos in one process, the encoder counted twice.
  6. The pass test needs a margin. "Beats the baseline" lets a 3% win through. Q5 set the bar (ticket D15): a replay p90 at least 25% below the baseline's, beyond the spread between rounds.
  7. Proof of the GPU, tightened. ORT's thread pool spin-waits by default, which inflates CPU time on a GPU run and takes power from the GPU on a 6 W chip; GPU cells turn it off. strace proves only that the device was opened. Each run also samples the i915 counters in sysfs, which the deploy user can read without root or a new package (read on yappy 2026-10-13: GPU frequency, RC6 idle time, power-limit throttle flags; intel_gpu_top, perf and turbostat are not installed).
  8. Two exact rewrites instead of a stop. The neck resizes to a fixed 64×64, so its bicubic step is a constant linear map, written as two matmuls with torch's own coefficients. timm's 5-D qkv split is rewritten in 4-D. Both are the same model, so ticket §4 holds, and both formats get them (P1).
  9. fp16 that can answer a question. A blanket fp16 copy predictably overflows in attention. The fp16 ONNX copies keep Softmax, LayerNorm and the attention-score MatMul in fp32 (P1); one blanket copy still checks the NaN (ticket D12).
  10. Continuous parity measures. Top-1 and guard flips over 13 photos carry little weight. Every parity report adds the largest change in a class probability, the probe-score change beside each photo's distance from 0.5, and the largest change in low-resolution mask logits before the threshold.

1. How each path reaches the GPU

All the GPU cells end at the same iGPU through the same kernel driver. What differs is the software between the runtime and the driver. "WebGPU" is a browser standard, but no browser is involved here: both runtimes bundle Dawn, Chrome's WebGPU engine, as a plain library, and Dawn turns WebGPU calls into Vulkan calls. Vulkan is used for compute, not graphics: the model's operations become compute shaders, programs the GPU runs on tensors, and nothing is drawn.

LayerVulkan pathOpenCL path
LiteRTlibLiteRtWebGpuAccelerator.so, in the wheel. ML Drift writes each operation as a WGSL compute shader, and Dawn runs them. Last resort (D10, P6). libLiteRtOpenClAccelerator.so, built from source at v2.3.0. ML Drift writes each operation as an OpenCL C kernel.
ORTThe onnxruntime-ep-webgpu plugin. ORT's own WGSL kernels, run by Dawn. The OpenVINO execution provider. OpenVINO's GPU plugin compiles the graph into OpenCL kernels.
API layerDawn translates WebGPU into Vulkan, through the libvulkan.so.1 loader. The ICD loader libOpenCL.so picks the vendor driver.
DriverMesa 22.3.6 ANV, Intel's open-source Vulkan driver (libvulkan_intel.so), which compiles shaders to GPU code. Intel NEO 22.43 (libigdrcl.so), Intel's OpenCL driver, which compiles kernels to GPU code.
Kernel and devicei915 through /dev/dri/renderD128 (the render group), on the Alder Lake-N iGPU: 24 EUs at 750 MHz, sharing the host's RAM.

Each cell compiles the same model through a different stack. Speed and exact numbers can differ, and any cell can fail where another works. The ML Drift paper measured LiteRT's OpenCL path about 2× faster than its WebGPU path on one Intel model, on another OS. That is the case for keeping LiteRT on OpenCL as the last resort rather than dropping it.

2. Phase order and why

The baseline comes first: if the models are not most of the time per photo, no runtime fixes the latency, and the owner hears that before any conversion. Conversion comes next and runs on the CPU. A .tflite or .onnx that already disagrees with PyTorch on the CPU would make every GPU number for it meaningless, and both GPU paths of a runtime run the same file. The Vulkan paths come next, then ORT's OpenVINO provider on the GPU and the CPU. None of these needs a build. The measurement runs once, with every cell in one interleaved session, so that heat and clock speed affect them alike. P5 reports, and the owner chooses. P6, LiteRT on OpenCL, runs only if P5 finds that every other cell failed and the owner says go (D10). No phase changes a served number. New files go to the scratch directory on yappy and to analysis/ml7_gpu/.

5. P1 — Convert both models to both formats and check them on the CPU

StatusDone 2026-10-13: 4b5e751, 6ed80c6; every base conversion passes D7 on the CPU; the int8 encoder fails and is dropped
Blocked byP0

The graphs are the models as served (ticket §4), cut where serving's own code already cuts them, and the same in both formats:

  • The DINOv3 graph returns the 1536-d cls_mean readout. The head and the guard stay in numpy, so parity is judged on what they consume.
  • The segmenter is two graphs, as in segment_beans.py: the encoder, and the prompt encoder with the mask decoder. The box goes in as two points labelled 2 and 3, and all three masks and their IoUs come out. multi3 is selected outside the graph, as today. The ONNX export is of these same wrapper modules, not upstream's scripts. Upstream's use the legacy exporter, and their single-mask option picks by IoU.
  • LiteRT has no dynamic batch (litert-torch #870), so DINOv3 is converted at batch 8 (40 patches = 5 calls) and at batch 40 (1 call). The ONNX files use the same fixed batches, so the two runtimes run the same shapes.
  • Two exact rewrites in the export wrappers, the same in both formats:
    • The bicubic neck. SamNeck resizes three stage outputs to a fixed 64×64 (UpSampleLayer(size=(64, 64)), bicubic, align_corners=False). Each resize is a constant linear map, so it becomes A_h · X · A_wᵀ. The matrices are made by passing an identity through torch's own F.interpolate, so they carry torch's coefficient (-0.75), coordinate mapping and edge clamping. Matmuls lower in every runtime, so LiteRT's missing bicubic op and the settings of ONNX's cubic Resize no longer matter.
    • 4-D attention. timm's attention reshapes qkv to 5-D, which LiteRT's GPU cannot hold (ticket 2.4). The wrapper splits q, k and v first and reshapes each in 4-D.
    Each rewritten module is checked against the original in torch 2.14 on the fixtures' inputs before export: differences at float rounding only (max-abs under 1e-5 of the output's largest magnitude, on the neck output and the readout).
  1. Two uv projects, each with its own pyproject.toml and uv.lock. Both import coffeecv.backbones and the vendored efficientvit as they are.
    • analysis/ml7_gpu/convert_litert/: torch 2.13 (CPU), timm 1.0.30, litert-torch 0.9.4, segment-anything 1.0.
    • analysis/ml7_gpu/convert_onnx/: the training lock's torch 2.14.0 and timm 1.0.30, segment-anything 1.0, onnx, onnxscript, onnxruntime and onnxconverter-common.
    coffeecv.dino_classifier refuses a timm mismatch, not a torch one. The readouts are compared with torch 2.14's in the last task, so a torch 2.13 difference would show there.
  2. Inputs: for each of the 13 photos in webapp/deploy/fixtures.txt, the serving path's preprocessed tensors, from the training environment (torch 2.14): the 40 patches [40,3,224,224], the encoder input [1,3,1024,1024] and the transformed box. Saved to inputs.npz, so every path gets the same bytes and preprocessing is outside the comparison.
  3. References: the PyTorch outputs for those inputs in the training environment. These are the readouts, the encoder embeddings, the three low-resolution masks and their IoUs, the final masks after postprocess_masks and the D18 rule, and the probabilities and guard verdicts. Saved to refs.npz.
  4. Convert to LiteRT: dino_b16_readout_b8.tflite, dino_b16_readout_b40.tflite, xl0_encoder.tflite, xl0_v3_decoder_box.tflite. Record for each the op histogram, any tensor above 4-D (these fall back to the CPU on LiteRT's GPU), the file size and sha256.
  5. Export to ONNX, the same four graphs as .onnx, with torch.onnx.export(dynamo=True) at the default opset 20. Weights go in an .onnx.data file beside each graph, and the two always travel together. Record for each the op histogram, the opset, the file sizes and sha256. If an execution provider in P2 or P3 rejects opset 20, re-export at 18 and note it.
  6. fp16 copies of the four .onnx files, for ORT's WebGPU cell (Q4), made with onnxconverter-common's convert_float_to_float16 and keep_io_types=True, so inputs and outputs stay fp32 and the scripts do not change. They are mixed precision: op_block_list is the converter's default list plus Softmax, LayerNormalization (or the ops of a decomposed LayerNorm), and node_block_list names the attention-score MatMul (q·kᵀ) of each block, found in the exported graph. op_block_list replaces the default list rather than adding to it, so the default is passed in explicitly. One blanket fp16 copy of dino_b16_readout_b8, nothing kept in fp32, answers ticket D12's question of whether DINOv3 really returns NaN. None is checked on the CPU, where ORT has no fp16 kernels.
  7. ORT's transformer fusions for DINOv3: onnxruntime.transformers.optimizer.optimize_model(model_type="vit") on both DINOv3 graphs, giving dino_b16_readout_b8.opt.onnx and _b40.opt.onnx. Record which fusions applied (attention, LayerNorm, GELU); the RoPE attention may not match ORT's patterns, and a no-op is reported as one. They run on ORT's CPU provider only, beside the plain graphs.
  8. An int8 XL0 encoder, for information only (ticket D4 decides serving): xl0_encoder.int8.onnx, static QDQ quantisation (onnxruntime.quantization.quantize_static, per-channel weights), calibrated on the encoder inputs of 32 photos from the segcrop stage's sessions under dataset/, spread across cameras, none of them a fixture. DINOv3 is not quantised: D4's concern is the head and the probe, fitted on fp32 embeddings.
  9. The bicubic neck goes through the matmul rewrite above in both formats. If the rewrite does not match torch at float rounding, stop and report. It is never swapped for bilinear, which would be a different model (ticket §4).
  10. CPU parity against refs.npz, with D7's measures: readout cosine and max-abs difference, mask IoU after the shared post-processing, top-1 and guard verdict per photo. Beside them, the continuous measures: the largest change in a class probability, the change in the probe score next to the photo's distance from the 0.5 threshold, and the largest change in the low-resolution mask logits before the threshold. LiteRT runs on XNNPACK at 4 threads, ORT on its default CPU provider at 4 threads. The files, inputs and references go to DVC, like the other analysis outputs. The 13 fixtures serve this comparison; the validation photos are for D7's gate in the release route.
  11. Checks: all eight base files convert, and CPU parity meets D7 (cosine ≥ 0.99999, IoU ≥ 0.999) for each, or the gap is reported with its cause before P2. Photos that change top-1 or guard verdict are listed, not blocking (D7).
