Logging the classifier service without collecting on people

A plan for adding real operational visibility — maintenance, incident response, bottleneck analysis — to the deployed /classify service, while keeping the posture the service already has: no accounts, no image storage, no persistent identifiers. Every field below is judged against one question: does this answer something you'll actually need to ask, or is it just data because it was easy to capture?

1 gunicorn worker, sync stateless — no accounts, no cookies current sink: journald coffee-cv-web.service

Image bytes / filenames
never logged — already an invariant
Existing invariant, kept as-is: webapp/README.md already documents the rule for this service — "verdicts + exceptions; never image bytes or filenames." This plan is an extension of that rule, not a replacement for it. The upload is written to a fixed-suffix tempfile, decoded, and deleted in a finally; nothing here proposes changing that.
The gap that actually motivates this: right now, if /classify gets slow, or the OOD guard starts refusing everything, or one browser's uploads keep failing to decode, there's no log line that would tell you. The two startup messages are everything the service currently emits.

02Ground rules

What every field hypothesis below is checked against.

  1. Name the question before the field. A field earns a place in the schema by answering a maintenance, incident, or bottleneck question you can state in one sentence. "Might be useful someday" doesn't qualify.
  2. No persistent identifiers. No cookies, no fingerprinting, no per-visitor ID that outlives one request.
  3. A request ID stitches log lines, not visitors. It ties nginx's line and the app's line about the same HTTP call together. It is never reused across two different calls, so it can't become a tracking ID by accident.
  4. Everything stays on the one VM. No third-party log shipping or SaaS sink — that would turn a config decision into a data-processor relationship with its own paperwork.
  5. Retention is enforced by config, not memory. Every log tier gets an explicit auto-expiry, set in journald/logrotate, not "someone remembers to clean it up."
  6. IP addresses are personal data. Treated that way by default: for now, that means not logged at all, in any form — see §03-C.

04Never logged, full stop

Hard excludes, regardless of how useful they'd seem:
  • Image bytes, thumbnails, or anything derived from pixel content
  • The client's original filename, in any form (already true — the tempfile suffix is fixed/generic, never derived from upload.filename)
  • EXIF metadata, including GPS tags — moot today since nothing reads EXIF, stated here so it stays true if that ever changes
  • Full raw User-Agent string beyond the short-lived window needed to derive the coarse category
  • Any cookie, session token, or device fingerprint — none exist today; logging is not a reason to add one
  • Client IP address, in any form, at any layer (for now — see §03-C)

05Tying one request together, without tying two together

A request_id (8 hex chars, generated per request) gets attached to the nginx line and every app-side log line for that one HTTP call — the join key that makes an incident traceable end to end. It is discarded the moment the request finishes serving its purpose as a join key: it is never written anywhere alongside a second request's ID, so it cannot be used to reconstruct "this visitor made these three requests." Only ever surfaced back to the client on error responses ("quote this code if you report a bug") — genuinely useful for support, and not personal data since it identifies a request, not a person.

06Retention shipped · 7c73fab

App and nginx logs now run a full year instead of weeks — long enough to compare this month's refusal rate or latency against the same month last year, not just recent incident response. Aggregated rollups (F) were already indefinite; nothing about them changes.

Checked against the real VM, not assumed: 60GB free on / (37GB of 97GB used — df -h on the box this already runs training on). Worst case for a full year: the service is capped at 1 concurrent request by nginx's limit_conn, and inference takes 6–8s, so even saturated non-stop for 365 days straight that's roughly 4.5M requests — about 1.8GB of app log plus 450MB of nginx log, uncompressed, before logrotate's own compression shrinks it further. Under 5% of free space, at a load real traffic won't come close to. Disk was never actually the constraint here.

07Rollout, in three phases

Phases 1 and 2 are shipped and deployed to production. Retention (§06) shipped alongside them, in its own commit.

Deploy incident, caught and fixed live, 2026-08-31: the first production deploy crash-looped coffee-cv-web.service immediately — its ProtectSystem=strict sandboxing makes the whole filesystem read-only except an explicit allowlist, and /var/log/coffee-cv was never added to it, so every worker died at import time (OSError: Read-only file system). No local smoke test could have caught this; the dev server doesn't run under systemd at all. Fixed with ReadWritePaths=/var/log/coffee-cv in webapp/deploy/coffee-cv-web.service (commit 2b5e718), verified via a real request through the live HTTPS endpoint afterward — both logs written, correct request_id join, zero restarts since.
phase 1

Structured request logs

shipped · 3f08b4b

webapp/app.py · coffeecv/infer.py — one JSON line per request to /var/log/coffee-cv/app.jsonl via a WatchedFileHandler (so external logrotate can rotate it with no signal/restart), plus a separate line for decode failures and unhandled exceptions, joined by request_id. coffeecv/infer.py gained the decode/crop-detect/inference timing split and decoded dimensions as new, purely-additive keys on the diagnostic dict classify_one already returned — no change to any measurement its parity guarantee depends on. Smoke-tested against the real model and a real photo, including a simulated logrotate rename to confirm the handler reopens on its own.

phase 2

nginx: dedicated log, shared request_id

shipped · 1e6f42e

webapp/deploy/coffee-cv.nginx.conf.template — landed at /var/log/nginx/coffee-cv.access, not the coffee-cv.log this section originally sketched: Ubuntu's stock /etc/logrotate.d/nginx globs /var/log/nginx/*.log, which would have silently double-rotated a same-named file at the distro's own 14-day default, fighting §06's 365. Dropping the .log suffix keeps it out of that glob entirely. $request_id in the original sketch was also wrong in a subtler way — that's nginx's own per-connection id, not the one webapp/app.py generates; the shipped format captures $upstream_http_x_request_id instead, reading the id back off the app's X-Request-Id response header.

phase 3

Daily rollups (optional, not shipped)

scripts/

A small cron job reading journalctl -o json --since yesterday to compute category-F counts/percentiles into a rotated summary file. Deliberately not a public /metrics endpoint — that's a new dependency and a new surface for a service this size. Worth doing once there's enough traffic that eyeballing phase 1's log lines stops being practical; skip it until then.
