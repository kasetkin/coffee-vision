On Android the page's controls are Choose Photo (the photo picker), Select File (a file browser) and a camera button

Since OPS-17 an Android phone shows Choose Photo and Take Photo, and both open the same system chooser, Camera or Files, in Chrome and in Firefox. The owner tested candidate inputs on an Android phone (2026-11-08) and chose controls that each do one thing: Choose Photo opens the photo picker, Select File a file browser, and a square camera button, an icon with no text, the camera (D1, revised 2026-11-09). Desktop does not change; iPhone's Take Photo becomes the same camera button (D8). Choose Photo keeps its name on every platform (D10). Written 2026-11-08; D1–D15 decided 2026-11-09; not implemented.

1. Summary

HTML has one hint about the camera, capture, and nothing that says "no camera". What an Android browser opens follows from the input's accept list. The page's list carries file extensions (.dng, .cr3, .hif, …) beside its MIME types; in Chrome that defeats both capture and the photo picker, so both of OPS-17's controls open the same Camera / Files chooser. After this ticket an Android browser shows three controls: Choose Photo, whose list is the accepted MIME types alone (Chrome opens the photo picker), Select File, whose list names no image type (Chrome and Firefox offer Files only), and a square camera button, a camera icon with no text at the other two's height, whose input is image/* with capture="environment" (Chrome opens the camera directly; Firefox, whose capture path for images is broken since Firefox 128, its Camera / Files chooser) (D1), placed last (D9). iOS keeps Choose Photo, and its Take Photo becomes the same camera button (D8); a desktop keeps Choose Photo.

2. Background

  • The inputs today (webapp/static/index.html at 305bc68): photo-input (Choose Photo) and camera-input (Take Photo, capture="environment"), each with the accepted formats' MIME types and then their extensions, held to coffeecv/data/accepted_formats.csv by tests/test_accepted_formats_named.py (ADR 0034). Take Photo's label is shown when isMobile() finds a phone or tablet (OPS-17 D2, D3).
  • Chrome on Android, read from Chromium's ui/android/.../SelectFileDialog.java (main, 2026-11-08; read, not run): each accept entry becomes a MIME type, an extension through Android's MimeTypeMap, and an extension it does not know becomes application/octet-stream. The camera opens directly only when capture is set and every entry is an image/ type; the photo picker opens only without capture and with image (or video) types alone; otherwise a chooser, with the camera in it whenever any entry is an image/ type, or the list is empty or */*.
  • Firefox on Android, read from android-components' feature/prompts/file/FilePicker.kt and MimeType.kt (mozilla-firefox/firefox main): the chooser offers the camera when any entry starts with image/ and the camera permission is granted; the photo picker is only a fallback when permissions are denied. The test (below) found capture has no effect. The cause, read from source (2026-11-09, Firefox 159.0.1; not tested): GeckoView turns capture on (dom.capture.enabled, Bug 1553603, Firefox 70) and passes environment on as FacingMode.BACK_CAMERA, but since Bug 1864350 (Firefox 128) MimeType.Image builds its camera intent in buildCaptureIntent, while FilePicker.buildIntentList's direct-camera branch still calls buildIntent, which returns null for images; so it falls through to the chooser. Bug 1911552 ("support of the property capture") is open, with no cause found.
  • Select File's list (read from source, 2026-11-09; not tested): Chrome treats application/octet-stream as generic and opens Files with no filter, so any file can be picked (SelectFileDialog.showExternalPicker: "If some of the extensions are generic, just let user select all files"). Firefox's MimeType.Wildcard.buildIntent puts it on the Files intent as EXTRA_MIME_TYPES, and Android's file browser (AOSP DocumentsUI, picker/Config.isDocumentEnabled through MimeTypes.mimeMatches) greys out a file whose type does not match, so a JPEG, HEIC or RAW photo may not be pickable there. An extension Android does not know comes out unfiltered in both: Chrome makes it application/octet-stream, Firefox */*. .bin is not such an extension: Android maps it to application/octet-stream.
  • The owner's test, 2026-11-08, on an Android phone, a throwaway page served at the domain in place of the live page (Activity), each input hidden behind a label as on the live page:

3. Before and after

Now

  • Android, Chrome and Firefox: Choose Photo and Take Photo both open a Camera / Files chooser.
  • iOS: Choose Photo (the library, Files, iOS's camera entry) and Take Photo (the camera).
  • Desktop: Choose Photo.

After

  • Android: Choose Photo, Select File and the camera button. Chrome: the photo picker, Files, and the camera directly. Firefox: the Camera / Files chooser, Files, and the chooser again (D1).
  • iOS: Choose Photo as now, and the same camera button in place of the words Take Photo (D8). Desktop: as now.
  • A test holds the Android inputs' lists, the camera button's accessible name and the platform check.

4. What does not change

  • iOS and desktop. Their controls, labels and accept lists stay as OPS-17 left them (D2).
  • What the service accepts. accepted_formats.csv, the front's check, its 40 MB cap and canonicalization (ADR 0033, ADR 0034). Select File lets a visitor pick any file; the front refuses one in no accepted format, as it refuses one sent by any other caller.
  • The path after a pick. Each control feeds choose() and is disabled while a photo is in flight (OPS-7 D4).

5. Risks

IDRiskEvidence and mitigation
R1A button with no words may not read as the camera to every visitor, nor to a screen reader. An inline SVG camera, and "Take Photo" as text read aloud but not shown, and as the tooltip (D13). Chrome's photo picker has no camera of its own (the test), so this button is Chrome's only camera on the page.
R5The camera button on iOS is not tested. Only its look changes on iOS: its input stays OPS-17's, which opens the camera there. The owner checks it on an iPhone after the release (D7, D8).
R2The photo picker may not show every accepted format (a RAW file, a photo outside the gallery). Not checked. Select File reaches any file the phone holds.
R3Select File shows every file, not only photos. Its list names no image type, or the camera comes back (Background). A wrong file gets the front's refusal, which names the accepted formats.
R6Firefox's Select File may grey out every photo (Background). Read from source, not tested. The owner's check picks a JPEG and a RAW file through Select File in both browsers; if Firefox greys them, D11's fallback list.
R7Three controls do not fit a narrow phone: at 360 px the card leaves about 286 px, and today's buttons (min-width: 8rem, a wrapping row) need about 323. D12: the Android row never wraps. Screenshots at 320, 360 and 412 px wide.
R4Browsers change this behaviour; it is read from source and one test on one phone, not from a specification. The test after the release (D7) repeats it on Chrome and Firefox.
