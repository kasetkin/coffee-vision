1. Summary

HTML has one hint about the camera, capture, and nothing that says "no camera". What an Android browser opens follows from the input's accept list. The page's list carries file extensions (.dng, .cr3, .hif, …) beside its MIME types; in Chrome that defeats both capture and the photo picker, so both of OPS-17's controls open the same Camera / Files chooser. After this ticket an Android browser shows three controls: Choose Image, whose list is the accepted MIME types alone (Chrome opens the photo picker), Select File, whose list names no image type (Chrome and Firefox offer Files only), and a square camera button, a camera icon with no text at the other two's height, whose input is image/* with capture="environment" (Chrome opens the camera directly; Firefox, which ignores capture, its Camera / Files chooser) (D1), placed last (D9). iOS keeps Choose Photo, and its Take Photo becomes the same camera button (D8); a desktop keeps Choose Photo.

2. Background

  • The inputs today (webapp/static/index.html at 305bc68): photo-input (Choose Photo) and camera-input (Take Photo, capture="environment"), each with the accepted formats' MIME types and then their extensions, held to coffeecv/data/accepted_formats.csv by tests/test_accepted_formats_named.py (ADR 0034). Take Photo's label is shown when isMobile() finds a phone or tablet (OPS-17 D2, D3).
  • Chrome on Android, read from Chromium's ui/android/.../SelectFileDialog.java (main, 2026-11-08; read, not run): each accept entry becomes a MIME type, an extension through Android's MimeTypeMap, and an extension it does not know becomes application/octet-stream. The camera opens directly only when capture is set and every entry is an image/ type; the photo picker opens only without capture and with image (or video) types alone; otherwise a chooser, with the camera in it whenever any entry is an image/ type, or the list is empty or */*.
  • Firefox on Android, read from android-components' feature/prompts/file/FilePicker.kt and MimeType.kt (mozilla-firefox/firefox main): the chooser offers the camera when any entry starts with image/ and the camera permission is granted; the photo picker is only a fallback when permissions are denied. The test (below) found capture has no effect.
  • The owner's test, 2026-11-08, on an Android phone, a throwaway page served at the domain in place of the live page (Activity), each input hidden behind a label as on the live page:

3. Before and after

Now

  • Android, Chrome and Firefox: Choose Photo and Take Photo both open a Camera / Files chooser.
  • iOS: Choose Photo (the library, Files, iOS's camera entry) and Take Photo (the camera).
  • Desktop: Choose Photo.

After

  • Android: Choose Image, Select File and the camera button. Chrome: the photo picker, Files, and the camera directly. Firefox: the Camera / Files chooser, Files, and the chooser again (D1).
  • iOS: Choose Photo as now, and the same camera button in place of the words Take Photo (D8). Desktop: as now.
  • A test holds the Android inputs' lists, the camera button's accessible name and the platform check.

4. What does not change

  • iOS and desktop. Their controls, labels and accept lists stay as OPS-17 left them (D2).
  • What the service accepts. accepted_formats.csv, the front's check, its 40 MB cap and canonicalization (ADR 0033, ADR 0034). Select File lets a visitor pick any file; the front refuses one in no accepted format, as it refuses one sent by any other caller.
  • The path after a pick. Each control feeds choose() and is disabled while a photo is in flight (OPS-7 D4).

5. Risks

IDRiskEvidence and mitigation
R1A button with no words may not read as the camera to every visitor, nor to a screen reader. A plain camera glyph, and the button's accessible name and tooltip "Take Photo". Chrome's photo picker has no camera of its own (the test), so this button is Chrome's only camera on the page.
R5The camera button on iOS is not tested. Only its look changes on iOS: its input stays OPS-17's, which opens the camera there. The owner checks it on an iPhone after the release (D7, D8).
R2The photo picker may not show every accepted format (a RAW file, a photo outside the gallery). Not checked. Select File reaches any file the phone holds.
R3Select File shows every file, not only photos. Its list names no image type, or the camera comes back (Background). A wrong file gets the front's refusal, which names the accepted formats.
R4Browsers change this behaviour; it is read from source and one test on one phone, not from a specification. The test after the release (D7) repeats it on Chrome and Firefox.
