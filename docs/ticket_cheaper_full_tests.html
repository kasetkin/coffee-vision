1. Summary

A deploy that changes no ML code still spends most of its time in the full tier, re-checking that code on the CPU. A profile of the whole suite found four tests worth half of it. Two of them change here: a split test that decoded the whole pool now builds its splits from a small linked pool (D1), and the LiteRT-against-PyTorch comparison runs on two photos instead of four (D2). The third, the fine-tune resume test, is recorded for later (D3); the fourth, two app boots merged into one, saves too little to do now.

2. Background

  • The gate. scripts/deploy_webapp.sh runs scripts/check.sh --full before anything reaches the host; the deploy of d9212c6 spent 841 s in it (646 tests), its host steps a few minutes.
  • The profile, 2026-11-02. A full run timing every test and every class's setUpClass, which --durations leaves out: 805 s, 653 tests. A first run measured 1,214 s and is void: its wrapper script ran the suite at import, so the three workers test_strip_metadata.TestPool spawns each ran the suite again beside it. check.sh is not affected: under python -m unittest, multiprocessing does not re-import a __main__ module in its workers.
  • Where the time went (clean run): test_frozen_checkpoint.TestSplitsBuiltAloneAreIdentical 155 s; test_litert.TestAgainstPyTorch 134 s (answers 62, readouts 52, masks 13, setup 8); test_seg_finetune.Resume's "a state with other inputs" 79 s; test_release_manifest and test_litert.TestServiceBoots 22 s each; test_strip_metadata's parallel-against-serial run on two real photos 44 s. Every other file under 30 s.
  • The split test built the val split alone and with the test split from data/segcropped/pool, 1,376 photos: about 400 val and test crops decoded, the val ones twice, to check a property that is per class and per photo (coffeecv/fold_data.py's docstring).
  • The LiteRT comparison ran the smoke photo, a HEIC and two compare JPEGs through both backends three times each (masks, readouts, answers). Both backends receive the same decoded pixels. The deploy's --compare runs every fixture through PyTorch here and the release on the host (ADR 0020).

3. Before and after

Now

  • The split test decodes the whole pool's val and test crops: 155 s.
  • LiteRT against PyTorch on 4 photos: test_litert 157 s in all.

After

  • The split test builds from 20 linked photos of two countries, Ethiopia pooled from folders 001 and 008: 3 s.
  • LiteRT against PyTorch on the smoke photo and the first compare JPEG; the service still boots and answers on the HEIC: test_litert 91 s.

4. What does not change

  • The full tier runs on every deploy. The owner keeps it; nothing is skipped or moved to the fast tier.
  • What the split test checks. The same assertion, val alone equal to val built with test, box for box; it now also asserts that both splits are non-empty, which a small pool could otherwise make vacuous. With the draw made to depend on the splits asked for, it fails (checked 2026-11-02).
  • The HEIC path on the served graphs. TestServiceBoots still uploads the HEIC to the app running LiteRT without torch.

5. Risks

IDRiskEvidence and mitigation
R1A LiteRT-against-PyTorch drift that shows only on the dropped photos passes locally. Both backends see the same pixels, so only the photo's content differs. The deploy's --compare checks all thirteen fixtures on the host, but it runs only when asked; accepted by the owner in D2.
R2The small pool misses a case the whole pool had. The split is seeded on (seed, class, photo pool) and each box on (seed, class, photo, split): no interaction across classes beyond pooling folders into a country, which Ethiopia (001, 008) keeps.

6. Decisions

IDQuestionOptionsOwner decision
D1The split test on the whole pool? (a) keep the whole pool (b) a small pool linked from it, two countries, one pooled from two folders (b), 2026-11-02. No case lost; about 150 s saved.
D2How many photos for LiteRT against PyTorch? (a) four: the smoke photo, a HEIC, two compare JPEGs (b) two: the smoke photo and one compare JPEG (b), 2026-11-02. About 65 s saved; R1 accepted.
D3Resume's "a state with other inputs is deleted": four changes, each by two toy fine-tunes (79 s)? (a) keep the eight runs (b) one change end to end, the other three by their effect on the resume fingerprint, with no training Recorded, not done, 2026-11-02: the owner keeps (a) for now. (b) would save about 60 s and lose the end-to-end proof for three of the four changes.

7. Scope and acceptance

  • The split test builds from a small linked pool, passes, and fails when a split's draw depends on the splits asked for (D1).
  • TestAgainstPyTorch runs on two photos; TestServiceBoots keeps the HEIC; tests.test_litert passes, 38 tests (D2).
  • A full run timed against the 805 s profile: 547 s, 653 tests, the one error the unrecorded photo in dataset/ood_negatives/user_realworld raises in both runs.

Out of scope

  • Skipping or tiering tests by what a deploy changes: the owner keeps the full tier.
  • D3, and one app boot for test_release_manifest and TestServiceBoots (about 20 s).
  • test_strip_metadata's parallel-against-serial run, 44 s, not diagnosed; its spawned workers each import the heavy modules.
  • test_litert compares the ML-8 checkpoint (segxl0v3, seed 123), not the live model.
