1. Summary

Stub. The question is where the host's decode_ms goes and how much of it can go, without changing the 8-bit sRGB the models read (ML-19 D7, D8). Nothing is proposed yet.

2. Background

  • Measured at the release (2026-11-08, the app's log on yappy): a 12 MP photo 12.1 s server-side, 3.7 s of it decode_ms; the 50 MP example 24.8 s, 15.9 s of it decoding. Before, 8.4 s (ML-13).
  • The decode (canonical.load_canonical): imagecodecs.jpegxl_decode to 16 bits, then LittleCMS from Rec.2020 to 8-bit sRGB in 128-row strips with NOOPTIMIZE, chosen because it matches float32's output (ML-19 P1). Neither step's thread count, nor the split between them, has been measured on the host.
  • The bar. Any faster path has to give the same 8-bit sRGB, or pass ML-19 D8's tests and the deploy's --compare; the host is the Intel N100, where libjxl's encoder already differs (ML-19 D51).
