OPS-1 · coffee-vision · implementation plan

Serve the webapp from isolated releases in /opt

The production service moves out of the training checkout into immutable releases under /opt/coffee-cv, each with its own uv-managed environment and only the files it needs. Deploys are one command, can run while a sweep trains, and never touch it.

1. Goal

Today coffee-cv-web runs from ~/coffee-vision with ~/coffee-vision-venv, the same checkout and venv that training sweeps rewrite and install into, and its ResNet18 path reads ~/.cache/torch at every start. What production serves therefore depends on the state of whatever experiment is running, and the site has been switched off for every sweep. It has been off since 2026-09-20.

End state:

  • The service runs from a release directory under /opt/coffee-cv, with its own environment and nothing under /home.
  • Nothing done in the training checkout or venv changes what production serves.
  • A deploy is one command. It may run while a sweep trains, and once two releases exist, rolling back is one command too.

2. Decisions

DecisionWhy
Serve from /opt/coffee-cv/releases/<id>, selected by a current symlink. Keep only current and previous. Production shares no files with training. Switching releases is one atomic symlink change. Two releases keep disk use bounded and still allow a one-command rollback.
One uv-managed .venv per release, with packages copied (UV_LINK_MODE=copy) and versions locked in webapp/uv.lock. Installs are reproducible and hash-verified. Each release is fully independent, so a rollback restores exactly the packages that release was tested with.
Copy only the files the service opens, as listed in the release manifest. Nothing training writes can reach production, and a test keeps the list accurate.
The model is chosen inside the release, in release.env. Code and model always switch together, and roll back together.
nginx serves the page from the release (current/webapp/static). The page and the API it calls change together, and there is no manual copy step to forget.
The service runs as a dedicated coffee-cv system user, in the existing systemd sandbox tightened to ProtectHome=true. A compromised worker can neither reach home directories nor signal the training jobs, which run as alioth.
Deploy only commits on origin/main, starting with a fast-forward of main to dino-integration. main becomes the record of what production runs, and every commit that is ever served is backed up on GitHub.
The first release ships allrigs_dino3b16_s123. Owner's choice. Until a second release exists, the fallback is redeploying allrigs_cam_s123 with the same script (about 10 minutes).
Deploys may run while a sweep trains, inside kernel-enforced limits (§5). The site no longer waits days for a sweep to end, and the limits guarantee that the sweep's files, memory and disk space stay untouched.
The VM's sweep commits come back through plain merges and tmp/* branches (§6). experiments/index.csv records the commit each run was trained on. Merges keep every recorded hash valid.

Paths use three template variables with these defaults: APP_ROOT=/opt/coffee-cv, APP_USER=alioth (the deploy user) and SERVICE_USER=coffee-cv. They are rendered with envsubst, like $DOMAIN is today.

4. What to build

4.1 Python environment (uv)

  • What to declare. webapp/pyproject.toml lists exactly what the 13 release modules import. Versions are copied from pip freeze of the production venv on the VM, a read-only step. Transitive packages are held to the same freeze with constraint-dependencies. webapp/uv.lock is committed, and uv verifies every artifact's hash from it on install.
  • torch and torchvision come from the PyTorch CPU index through [tool.uv.sources]. environments limits the lock to Linux x86_64, the only platform it serves.
  • timm 1.0.29 is declared without huggingface_hub/safetensors through [[tool.uv.dependency-metadata]]. Those two exist only to download weights, and the service never downloads anything.
  • opencv is the headless build, at the production version. If the pre-cutover comparison (§4.8) shows any difference, switch to the build the production venv has.
  • uv itself is pinned with required-version. It is installed as one binary at /usr/local/bin/uv on the VM, checked by sha256, and at the same version locally, where uv lock runs.
# webapp/pyproject.toml   (‹prod› = version from the production pip freeze)
[project]
name = "coffee-cv-webapp"
version = "0"
requires-python = "==3.12.*"
dependencies = [
  "flask==3.1.3", "gunicorn==26.2.0", "numpy==2.4.4", "pyyaml==6.0.3",
  "pillow==12.2.0", "pillow-heif==‹prod›", "pillow-avif-plugin==1.6.0",
  "pillow-jxl-plugin==1.3.8", "rawpy==0.27.0", "opencv-python-headless==‹prod›",
  "torch==2.13.0", "torchvision==0.28.0", "timm==1.0.29",
]

[tool.uv]
package = false
required-version = "==‹uv version›"
environments = ["sys_platform == 'linux' and platform_machine == 'x86_64'"]
constraint-dependencies = ["werkzeug==3.1.8", "jinja2==3.1.6", "…"]   # rest of the prod freeze

[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
torchvision = { index = "pytorch-cpu" }

[[tool.uv.dependency-metadata]]
name = "timm"
version = "1.0.29"
requires-dist = ["torch", "torchvision", "pyyaml"]

Each release's venv is built on the VM at the release's final path, inside a capped unit (§5):

export UV_CACHE_DIR=/opt/coffee-cv/uv-cache UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
export UV_PROJECT_ENVIRONMENT=/opt/coffee-cv/releases/$ID/.venv
cd /opt/coffee-cv/releases/$ID
uv sync --project webapp --locked --no-dev --compile-bytecode --python /usr/bin/python3.12
.venv/bin/python -m compileall -q coffeecv webapp
  • --locked refuses a lock that no longer matches pyproject.toml.
  • /usr/bin/python3.12 with UV_PYTHON_DOWNLOADS=never keeps the interpreter outside /home and identical to the one production uses today.
  • Bytecode is compiled at build time because the service can neither write .pyc files nor afford to compile torch on every start.
  • The venv is built in its final directory and never moved, because the console scripts in .venv/bin contain its absolute path.

4.3 ResNet18 without downloaded weights

For inference, build_model creates the ResNet18 backbone with weights=None, set by a flag passed from coffeecv/infer.py:264. Training keeps its ImageNet initialisation.

Why: the fallback model, allrigs_cam_s123, must start under ProtectHome=true, which hides ~/.cache/torch. load_model uses load_state_dict with strict=True (coffeecv/infer.py:265), so the checkpoint overwrites every parameter and buffer anyway. The test is therefore bit-identical logits before and after the change, on a fixed image set.

4.4 Build stamp

webapp/deploy/write_build_info.py gains --ref <sha> and --model <name>. It writes the ref's commit, dirty: false and the model name. Why: a release is exported from a commit, not from the working tree, and the app puts this stamp on its startup line and on every request line.

4.5 Service unit

webapp/deploy/coffee-cv-web.service.template changes these lines. Every other hardening line stays as it is.

User=$SERVICE_USER
Group=$SERVICE_USER
WorkingDirectory=$RELEASE_DIR
EnvironmentFile=$RELEASE_DIR/release.env
Environment=PYTHONDONTWRITEBYTECODE=1 COFFEE_CV_LOG_DIR=$LOG_DIR
ExecStart=$RELEASE_DIR/.venv/bin/gunicorn -w 1 --worker-class sync \
    -b 127.0.0.1:$PORT --timeout 30 --no-control-socket webapp.app:app
ProtectHome=true
ReadWritePaths=/var/log/coffee-cv
  • Two renderings of one template:
    • production: RELEASE_DIR=/opt/coffee-cv/current, PORT=8000, LOG_DIR=/var/log/coffee-cv;
    • smoke test: RELEASE_DIR=/opt/coffee-cv/releases/<id>, PORT=8001, LOG_DIR=/var/log/coffee-cv/smoke.
    Both run as $SERVICE_USER, so their sandboxing is identical.
  • Which release a process uses: systemd resolves current when the service starts, and coffeecv.config.REPO_ROOT is built with Path.resolve(). A running process therefore stays on the release it started from until it is restarted.
  • Permissions: releases are owned by alioth with modes 0755/0644, so coffee-cv can read them but not write them. ProtectSystem=strict makes them read-only to the service as well.
  • Logs: coffee-cv.logrotate.template uses su $SERVICE_USER $SERVICE_USER.

4.6 nginx

In coffee-cv.nginx.conf.template, root becomes $APP_ROOT/current/webapp/static. Nothing else changes. nginx follows the symlink on every request, so the page switches at the flip.

4.7 Server scripts

  • setup_server.sh keeps only the prerequisites for a fresh box: installing nginx, the cert directory and its permissions, and ufw. It drops:
    • the pip install into the training venv;
    • rendering the unit, nginx and logrotate files;
    • the /var/www copy;
    • systemctl enable --now.
    A fresh box has no release to run until the first deploy, and deploy_webapp.sh owns every rendered file from now on.
  • deploy_webapp.sh --bootstrap does the one-time setup. Every part of it is safe while a sweep trains:
    • create the coffee-cv system user (no login, no home);
    • create /opt/coffee-cv, owned by alioth;
    • install the pinned uv;
    • hand /var/log/coffee-cv and its files to coffee-cv;
    • render the logrotate file.
  • webapp/README.md describes the new deploy, rollback and fallback commands.

4.8 Deploy script: scripts/deploy_webapp.sh <git-ref> <model-name>

Runs locally and drives the VM over SSH. Options:

  • --bootstrap: the one-time setup in §4.7;
  • --stage-only: preflight and steps 1–3, no flip;
  • --compare: the pre-cutover comparison, described after the steps;
  • --verify: step 7 alone;
  • --rollback: switch back to previous.

It reads DOMAIN, APP_USER, SERVICE_USER, APP_ROOT and HOST (default powervpsssh).

  1. Preflight (VM, read-only). Refuse to continue unless MemAvailable is at least 5 GB, /opt has at least 10 GB free, and uv is at the pinned version. Record the sweep's PIDs and the size of ~/sweep.log (§5).
  2. Build from the ref, locally.
    • Resolve the ref to a sha after git fetch origin. Refuse the sha unless git merge-base --is-ancestor <sha> origin/main passes.
    • git archive the manifest's git-tracked paths.
    • Add models/<name>.pt from the working tree or the local DVC cache (.dvc/cache/files/md5/<aa>/<rest>). Refuse if its md5 differs from the ref's .pt.dvc.
    • For DINOv3, add the backbone .pth. Refuse if its sha256 differs from the ref's models_pretrained/manifest.json.
    • Write BUILD_INFO.json and release.env.
    • Compute the smoke test's expected response locally: run the staged tree's own webapp.app through Flask's test client on the smoke photo, with COFFEE_CV_LOG_DIR pointed at a scratch directory. The smoke photo is one fixed raw photo from dataset/, pinned by path and sha256 in the script.
  3. Stage in place.
    • rsync to /opt/coffee-cv/releases/<id>/ with --copy-dest pointing at the current release, so files that haven't changed are copied on the VM instead of sent over the network again.
    • Build the venv (§4.1) inside a capped unit (§5).
    • Check the contents against the manifest, then write .complete.
  4. Smoke-test in the real sandbox.
    • Render the smoke unit and its limits drop-in (§5), then start it.
    • POST the smoke photo to /classify, /crop and /preview. Top-1 must match exactly, and scores must agree within 1e-4, because float32 results differ slightly between machines. model_sha must match.
    • Record time-to-ready and request latency. Gate on them only when no sweep is running, since the caps throttle the smoke on purpose. gunicorn's 30 s timeout also covers worker boot.
    • Stop and remove the unit, its drop-in and /var/log/coffee-cv/smoke.
  5. Render the production files. Render the unit and the nginx config.
    • If the unit changed, install it and run daemon-reload.
    • If the nginx config changed, back up the old file, install the new one and run nginx -t. If the test fails, restore the backup and stop.
    All of this happens before the flip.
  6. Flip. Point previous at the old target, then ln -sfn releases/<id> current.new && mv -T current.new current. Reload nginx if its config changed.
  7. Restart coffee-cv-web only if it is enabled. If it is disabled, stop here and print systemctl enable --now coffee-cv-web followed by deploy_webapp.sh --verify.
  8. Verify.
    • Backend, on 127.0.0.1:8000: GET / → 404, GET /classify → 405, and the startup journal line shows the expected commit and model_sha.
    • Public site: GET https://$DOMAIN/ → 200 with a body whose sha256 equals the release's index.html. A POST /classify of the smoke photo returns the expected top-1; retry it once on 503, because nginx allows one request in flight.
    • If a check fails: roll back when previous exists; otherwise stop the service, which leaves the site as it is today (page up, /classify 502), and report.
  9. Prune and postflight. Keep current and previous, and delete every other release, including any without .complete. Run uv cache prune. Print the sweep's PIDs and log size next to the preflight values.

--rollback swaps current and previous, restarts the service and runs step 7. Model and page follow the symlink. Fallback before a second release exists: deploy_webapp.sh <sha> allrigs_cam_s123.

--compare checks that the new venv gives the same answers as the old one. It runs the staged release's code on a fixed set of 10 raw photos (pinned in the script), inside a capped unit, twice: once with the training venv's interpreter (python -B, so nothing is written into that venv) and once with the release venv. Same machine, code and weights, so the outputs must be bit-identical; any difference comes from a package version and must be explained before the service is enabled. If the training venv lacks timm 1.0.29, compare against the local outputs instead, within 1e-4.

5. Running alongside a sweep

Everything up to and including the flip may run while a sweep trains. The service stays off until the owner enables it. Each way the deploy could reach the sweep is bounded by the kernel:

ResourceGuaranteeHow
FilesNothing of the sweep's is written: ~/coffee-vision, ~/coffee-vision-venv, ~/sweep.log, ~/sweep_status.log, ~/.cache. Every code-running step (venv build, compileall, --compare, smoke) runs as a transient systemd unit with ProtectSystem=strict and ProtectHome=read-only (the smoke: true). Only /opt/coffee-cv is writable to it, plus /var/log/coffee-cv/smoke for the smoke. The other steps write fixed absolute paths under /opt/coffee-cv, /run/systemd/system and, for the rendered production files, /etc.
ProcessesNothing the sweep runs is signalled, restarted or reloaded. The sweep is not a systemd unit. daemon-reload and an nginx reload act only on their own units. The service is not started while it is disabled.
MemoryAn overrun kills the deploy step, never the sweep. MemoryMax=3G and MemorySwapMax=0 on every unit, so the OOM killer acts only inside that unit. The page cache from its writes is charged to the unit too, so it cannot push the sweep's cached data out of memory. Preflight requires 5 GB available.
CPUAt most 1 logical CPU for builds and 2 for the smoke, about 10 minutes per deploy. CPUQuota=100% / 200%, a hard cap. The sweep's own thread count is unchanged, so its results are too.
DiskA deploy cannot fill the disk under the sweep. Preflight requires 10 GB free on /opt, which sits on the same disk the sweep writes to.

Each code-running step, shown for the venv build:

sudo -n systemd-run --wait --pipe --collect --uid="$APP_USER" --gid="$APP_USER" \
    -p ProtectSystem=strict -p ProtectHome=read-only -p PrivateTmp=yes \
    -p ReadWritePaths=/opt/coffee-cv \
    -p CPUQuota=100% -p MemoryMax=3G -p MemorySwapMax=0 --nice=19 \
    --working-directory=/opt/coffee-cv/releases/$ID \
    -E UV_CACHE_DIR=/opt/coffee-cv/uv-cache -E UV_LINK_MODE=copy -E UV_PYTHON_DOWNLOADS=never \
    -E UV_PROJECT_ENVIRONMENT=/opt/coffee-cv/releases/$ID/.venv \
    /usr/local/bin/uv sync --project webapp --locked --no-dev --compile-bytecode --python /usr/bin/python3.12

The smoke unit gets its limits from /run/systemd/system/coffee-cv-smoke.service.d/limits.conf: CPUQuota=200%, MemoryMax=3G, MemorySwapMax=0. The drop-in adds only limits, so the smoke's sandbox stays identical to production's.

Never run during a sweep:

  • setup_server.sh, because it runs apt and ufw.
  • A second remote_launch.sh with default paths. Its first action is rm -f ~/sweep.log ~/sweep_status.log. The deploy never calls it.
  • Git commands that move the VM's checkout (merge, pull, checkout). §6's VM step runs after the sweep.
  • apt, reboots, and anything that writes under ~/coffee-vision*.

Proof: the deploy prints the sweep's PIDs (pgrep -f 'run_folds|train_baseline') and the size of ~/sweep.log before its first VM step and after its last. The same PIDs still running and a log that kept growing show the sweep was left alone. If the sweep finished on its own in between, its SWEEP_DONE_EXIT line shows that.

6. Git history

A sweep commits one experiment per fold into the VM's own main. These commits come back with fetch and merge only, rehearsed on tmp/* branches, so every commit keeps its hash and every git_commit recorded in experiments/index.csv stays valid.

# 0. Now, local: main becomes the deploy branch
git switch main
git merge --ff-only dino-integration             # 7 commits, main has none of its own
git push origin main

# 1. After exp239 has finished (SWEEP_DONE_EXIT in ~/sweep_status.log), local
git fetch powervpsssh main:tmp/vm-sweep          # the VM's commits as a local branch
git switch -c tmp/merge-sweep main               # rehearse on a copy; main does not move yet
git merge -m "Merge exp232-239 (ResNet18 seeds 123/7) from the VM" tmp/vm-sweep
#   run the checks below, then:
git switch main
git merge --ff-only tmp/merge-sweep              # main moves only now
git branch -d tmp/merge-sweep tmp/vm-sweep
git push origin main

# 2. The VM catches up: a fast-forward, nothing rewritten
git push powervpsssh main:tmp/from-local         # a branch the VM does not have checked out
#   on the VM, in ~/coffee-vision:
git status --short                               # leftovers? diff them against the last commit
git merge --ff-only tmp/from-local               # if it refuses over leftovers: git stash push -u, retry
git branch -d tmp/from-local

Checks before main moves:

  • git diff --stat main tmp/merge-sweep lists only files the sweep writes (experiments/, params.yaml, dvc.lock, outputs/), and nothing in coffeecv/ or webapp/.
  • experiments/index.csv has every row from both sides (exp232–239 and exp252–254) and no conflict markers.
  • Every git_commit in those rows resolves: git cat-file -e <sha>^{commit}.

If a check fails, git switch main, delete the scratch branch with git branch -D tmp/merge-sweep, and merge again. main never moved.

  • No conflict is expected. A rehearsal with exp232–234 on 2026-09-27 merged cleanly: index.csv is kept in experiment order, so the VM's rows land between 231 and 240 and the local ones after 251. If it conflicts anyway, keep every row in experiment order. params.yaml keeps the last fold's seed and held-out rig, as after every sweep.
  • DVC: the merge brings dvc.lock, which points at the new fold checkpoints. Those files reach the DVC remote via dvc push from the VM once the remote is back.
  • Every future sweep: the VM starts equal to main. After the sweep, run steps 1–2 again; if main did not move meanwhile, step 1 is a plain fast-forward.
  • During a sweep, only read-only fetches: git fetch powervpsssh main.

7. Execution order

Local, any time

  1. §6 step 0: fast-forward main to dino-integration and push it; all further work goes on main
  2. Read-only from the VM: pip freeze of ~/coffee-vision-venv, its opencv build, and whether timm 1.0.29 is installed
  3. Install pinned uv; write webapp/pyproject.toml; run uv lock (§4.1)
  4. ResNet18 weights=None for inference, with the bit-identical-logits test (§4.3)
  5. Manifest and tests/test_release_manifest.py, covering both models and all three endpoints (§4.2)
  6. write_build_info.py --ref --model (§4.4)
  7. Unit, nginx and logrotate templates; the trimmed setup_server.sh; webapp/README.md (§4.5–4.7)
  8. scripts/deploy_webapp.sh with all options (§4.8, §5)
  9. Rehearse locally in a scratch root: build, stage, flip, prune, --rollback. The devcontainer has no systemd, so the systemd steps are stubbed here and run for real in Phase A
  10. Commit and push to origin/main

VM, Phase A: allowed during the sweep

  1. deploy_webapp.sh --bootstrap
  2. deploy_webapp.sh <main-sha> allrigs_dino3b16_s123 --stage-only; record RSS and timings
  3. --compare on the staged release: outputs must be bit-identical
  4. Full deploy up to the flip. The service stays disabled, and the public site behaves as today: the page loads and /classify answers 502

Phase B: the owner, any time

  1. sudo systemctl enable --now coffee-cv-web, then deploy_webapp.sh --verify

After exp239

  1. §6 steps 1–2: merge the sweep's commits into main, then fast-forward the VM
  2. Delete webapp/requirements.txt and webapp/requirements-nodeps.txt; the old service no longer exists

9. Risks

RiskMitigation
The locked package versions differ from the ones the model was checked withVersions come from the production pip freeze, and --compare must be bit-identical before the service is enabled.
The DINOv3 smoke needs more than 3 GBThe smoke dies alone and the sweep is unaffected. Raise its cap using the RSS recorded in --stage-only, staying within MemAvailable.
A throttled smoke hits gunicorn's 30 s timeoutThe smoke fails and the sweep is unaffected. Raise the smoke's quota to 300%.
No one-command rollback until the second releaseThe fallback is deploy_webapp.sh <sha> allrigs_cam_s123, about 10 minutes. The manifest and logits tests keep that path deployable.
The DVC remote is still downModel files come from the local tree or DVC cache and are checked against the hashes in git. The remote is not needed.
The live site next to a sweep runs short of memoryUse the RSS recorded in Phase A. If memory is tight, keep the site off during sweeps, as now.

10. Out of scope

  • Changing the training checkout, the training venv, or how sweeps are launched.
  • CPU priority between sweeps and the site. When both are busy they share the CPU, and whether the site stays on during a sweep is the owner's call.
  • nginx changes beyond the new root.
  • Moving serving to another machine or into a container.
