Ticket OPS-19 · coffee-vision · the front's site and the public contract

The front answers /analyze with CORS headers, so a script on another site's page can send a photo and read the answer

Today /analyze is open to anyone with curl or a server, but a browser blocks a script on any other origin from reading its answer, because the front sends no Access-Control-Allow-Origin on it. This ticket adds CORS to /analyze at the front's nginx, on every answer including the front's own refusals, and says so in the public contract. Written 2026-11-08; D1–D7 decided the same day (ADR 0035); planned in plan_cors_analyze.html; implemented locally (P1–P3), not released.

1. Summary

Today a cross-origin caller (a script on a page served from an origin other than the live site's) can send a photo to /analyze, but the browser hides the answer from it. After this ticket the front's nginx sends Access-Control-Allow-Origin: * (D1) on every /analyze answer: the streamed 200, the check service's and the app's 400, 413 and 503, and the front's own 413, busy 503 and offline 503. It also answers a preflight OPTIONS itself (D2), without taking the one-at-a-time gate. The work has three parts: the front's site and its tests, the contract (llms.txt, openapi.json, the README), and a front release verified on the domain with a cross-origin request.

2. Background

Read from the code at 89d628a.

  • The front already uses CORS for the agent files. webapp/deploy/coffee-cv-front.nginx.conf.template sends Access-Control-Allow-Origin "*" on /llms.txt, /openapi.json and /.well-known/ard.json, "so a tool running in a browser can fetch them too". The /analyze location sends none. Neither the check service (webapp/front/check_service.py) nor the app (webapp/app.py) sets a CORS header.
  • The API is already public. webapp/README.md, "For agents": "open to LLM agents acting for a person, through the same POST /analyze the page uses: no key, no separate endpoint", and robots.txt allows /analyze. CORS limits only what a browser lets a page read. A server or curl can already call /analyze from anywhere.
  • A cross-origin upload already reaches the front. A fetch with a FormData body and no custom headers is a CORS "simple request": the browser sends it with no preflight and only hides the answer. So a page elsewhere can already make the service classify a photo and hold the gate for about 9–11 s; it just cannot read the result. CORS changes who can read the answer, not who can send a photo.
  • Preflight. A caller that adds a header outside the CORS safelist (a custom X- header, for example) triggers an OPTIONS preflight. Access-Control-Allow-Headers: * allows any such header except Authorization, which the Fetch standard requires to be named; the API takes no credentials, so it is not allowed (D2). Browsers cap Access-Control-Max-Age: Chrome at 7200 s, Firefox at 86400 s. Today that goes to the check service, which has only do_POST and do_GET, so http.server answers 501 and the browser gives up.
  • nginx's add_header traps. Without always it adds the header only to 2xx and 3xx answers, so a script could not read a 413 or a busy 503 and would see an opaque network error instead. The front's 413 and 503 come from the named locations @too_large, @busy and @offline, which do not inherit /analyze's add_header and need their own. An add_header in a location also drops any inherited from the server level.
  • Streaming. The answer is NDJSON in two parts (ADR 0023). A cross-origin fetch can read it as a stream through response.body, as the page does, once the answer carries Access-Control-Allow-Origin. Nothing about buffering changes.
  • One worker for everyone. limit_conn at the front lets one photo through at a time, for every caller together (OPS-15 D11). llms.txt, "Limits", tells callers to wait about 10 s on a busy 503 and not to send in parallel.
  • Logging. The front's access log (coffee_cv_front_minimal) records no Origin or Referer. docs/logging_plan.html excluded Referer as adding nothing for a single-page app. With other sites calling, the request's Origin is the only way to tell their traffic from the page's.
  • Tests. tests/test_front_site.py runs the rendered front site against a fake inference host (for example test_a_second_photo_while_one_is_in_flight_is_busy), so CORS on each answer can be tested there.

3. Before and after

Now

  • A cross-origin caller can POST a photo, but the browser blocks it from reading any answer, a refusal included.
  • A preflight OPTIONS /analyze gets a 501 from the check service.
  • llms.txt and openapi.json say nothing about calling from a browser.

After

  • Every /analyze answer carries Access-Control-Allow-Origin: * (D1) and exposes X-Request-Id (D4), the front's own 413 and 503 included, so a cross-origin caller reads the answer, streamed, and the errors.
  • OPTIONS /analyze gets a 204 with the allowed method and headers from the front's nginx (D2), without taking the gate or reaching the check service.
  • The front's access log records each request's Origin (D3).
  • llms.txt, openapi.json and the README say the API can be called from a page on any site, with a short fetch example, and what it asks of that site (D5).

4. What does not change

  • The page. It is same-origin and does not need CORS.
  • The one-at-a-time gate and the limits. One photo at a time for every caller, 40 MB and 60 megapixels a photo. CORS adds no capacity.
  • The check service, the inference host and the models. The headers are the front nginx's; the inference host stays reachable only from the front (ADR 0031).
  • No key, no account, no cookies. The API takes no credentials, so CORS allows none (no Access-Control-Allow-Credentials).
  • The photo is never stored, whichever site sends it.

5. Risks

IDRiskEvidence and mitigation
R1A popular site's visitors take the one worker, and the page's own visitors get "busy". The gate is shared by every caller (section 2), and a page elsewhere can already hold it without CORS, so this ticket makes such use worth building rather than newly possible. Mitigation: D3 logs the Origin, so the owner can see who uses the service; a later ticket (a per-origin limit, or an allow-list, D1 (b)) can narrow access if one site crowds out the page. The owner accepts the rest in D1.
R2A script cannot read the front's own refusals, and sees a network error where the contract promises a 413 or 503. nginx's add_header needs always for error statuses, and the named locations need their own (section 2). A proxy_hide_header drops any CORS header from the check service's answer (D1), so one sent upstream someday is never doubled, which a browser rejects. Tests in tests/test_front_site.py check the header on the 200, a 400, the front's 413, the busy 503 and the offline 503.
R3A preflight takes the gate, or reaches the check service. A return 204 for OPTIONS in location = /analyze runs in nginx's rewrite phase, before limit_conn. A test sends a preflight while a photo is in flight and expects a 204, not a busy 503.
R4Visitors of another site send their photos here without seeing this site's terms. The page's promise that the photo is never stored holds for every caller, but those visitors never read it. The contract says so to the site that makes the call, and asks it (a "should": nothing can enforce it) to tell its visitors where their photo goes (D5).

6. Decisions

IDQuestionOptionsOwner decision
D1Which origins may read the answer? (a) any origin, Access-Control-Allow-Origin: *, as for the agent files (recommended: it matches "free, no key, no account", the API is already open to servers, and a * cannot be combined with credentials, which the API has none of) (b) an allow-list of origins in the deploy's config, echoed back with Vary: Origin, so each new site asks the owner first (a), 2026-11-08. Access-Control-Allow-Origin: * on every /analyze answer. An allow-list would limit who reads the answer, not who takes the gate, since a simple request is sent either way. Also a proxy_hide_header Access-Control-Allow-Origin (and the other CORS response headers) on /analyze, so the header is never doubled if the app or the check service ever sends one.
D2Does the front answer a preflight? (a) yes: OPTIONS gets a 204 from the front's nginx with Access-Control-Allow-Methods: POST, Access-Control-Allow-Headers: * and Access-Control-Max-Age: 86400 (recommended: a caller's library may add a header, and a 204 from nginx costs nothing) (b) no: only simple requests work, and the contract says to send no custom headers (a), 2026-11-08, with Access-Control-Max-Age: 7200, Chrome's cap, not 86400. Allow-Headers: * does not cover Authorization, and it stays unlisted: the API takes no credentials.
D3Does the front's access log record the request's Origin? (a) yes, as one more field of coffee_cv_front_minimal, kept 365 days like the rest of the line (recommended: it is a site's address, not a visitor's, and without it R1 cannot be seen) (b) no, as for Referer today (a), 2026-11-08. Logged as "$http_origin", quoted like $request: browsers send Origin on every POST, so the page's own uploads log the live site's origin, a cross-origin caller its own, a sandboxed or file:// page null, and curl or an agent -. No field joins it to the stream log's visitor IPs. docs/logging_plan.html gains the field.
D4Is the app's X-Request-Id exposed to cross-origin scripts? (a) yes, Access-Control-Expose-Headers: X-Request-Id, so another site can quote a request when it reports a problem (recommended) (b) no (c) as (a), and the front also sends its own $request_id on its 413 and 503 refusals (a), 2026-11-08. Not (c): the front's refusals (too large, busy, offline) have nothing to report, and the page's answers stay as they are.
D5What does the contract ask of a site that calls the API from its page? (a) llms.txt and openapi.json say the API may be called from any page, ask the site to tell its visitors their photo is sent here, and ask it to wait and retry on a busy 503 rather than loop (recommended) (b) say only that CORS is allowed (a), 2026-11-08, with a short fetch example. Telling visitors is a "should", not a "must": nothing can enforce it, and the photo is never stored whoever sends it.
D6Does "the API is open to pages on any origin" get an ADR? (a) yes, if D1 is (a): it binds later tickets (a per-origin limit, a key, analytics) and is hard to take back once other sites depend on it (recommended) (b) no, a D-number here is enough (a), 2026-11-08: ADR 0035, "The API is open to pages on any origin".
D7How is the release checked on the domain? (a) --verify gains curl checks (a request with an Origin header gets Access-Control-Allow-Origin on a 4xx; OPTIONS gets a 204), and the owner runs one browser fetch by hand from the devtools console of an unrelated page, recorded in Activity (recommended: the header is checked on every deploy at no cost) (b) a headless browser in --verify (c) the browser check by hand only (a), 2026-11-08. Not (b): a headless browser is a heavy dependency for the deploy, for one check.

7. Scope and acceptance

  • The front's site sends Access-Control-Allow-Origin: * (D1) on every /analyze answer: the streamed 200, the check service's 400 and 413, the front's own 413, the busy 503 and the offline 503, never twice; tested in tests/test_front_site.py.
  • Per D2, OPTIONS /analyze gets a 204 with Access-Control-Allow-Methods: POST, Access-Control-Allow-Headers: * and Access-Control-Max-Age: 7200, even while a photo is in flight, and never reaches the check service; tested.
  • The agent files' CORS is unchanged, and no other path gains it; tested.
  • Per D3, coffee_cv_front_minimal records "$http_origin", and docs/logging_plan.html says so. Per D4, every /analyze answer sends Access-Control-Expose-Headers: X-Request-Id; tested.
  • llms.txt, openapi.json, webapp/README.md ("For agents") and docs/inference_path.html say what D5 decides, calling the other side a cross-origin caller; tests/test_agent_files.py passes.
  • A front release, verified on the domain (docs/agents/deploy.md) per D7: --verify passes with its new CORS checks, and the owner's fetch from the devtools console of an unrelated page reads both parts of the answer for an example photo, and a busy 503's JSON.

Out of scope

  • API keys, accounts or per-site quotas. A per-origin limit is a later ticket if R1 shows up in the log.
  • More capacity: a second worker or a queue (OPS-10, the request-queue ticket).
  • An embeddable widget or script for other sites to drop in; this ticket opens the API only.
  • CORS on any path other than /analyze, beyond the agent files that already have it.
