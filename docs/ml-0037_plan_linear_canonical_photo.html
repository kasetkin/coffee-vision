Implementation plan: a linear Rec.2020 canonical photo, one read-back, the preview's picture at the front

The order of work for ticket ML-37. Three strands: the canonical photo and its read-back (D1–D3, D8, D9, D12), the models' input after it (D11), and the preview (D4, D15). The code comes first and moves no stored output (P1–P4). The first step that changes a number is P5's re-run of the canonical store, then the re-crop (P6) and the classifier's refit, judged against D13's bar (P7). Everything ships in one release (P8). No fine-tune runs in this ticket (D14).

Built from a read of the code at 8a81fd9, not from the ticket alone. Eight things the ticket does not cover turned up. They are folded in below, and the ones that need a decision are Q1–Q3 (§2).

  1. The front answers only once the host has. check_service.forward sends the visitor's status line and headers after getresponse(), so a refusal from the host (its 503 busy, an app failure) is today an HTTP status. To send the picture first (D15), the front must open its own 200 stream before the photo crosses; whatever the host says after that has to become a line in the stream. The public API says the classification or an error is "always the second line" (openapi.json, llms.txt; cross-origin callers since OPS-19). Q1.
  2. The head's augmented views resize between two pipelines. HeadAugment.view runs the patch pipeline on the stored uint8 patch, then eval_resize to 224 px, then the input pipeline (JPEG compression, blurs, noise, Downscale) on the result. Under D11 (b) the resize gives float, so the input pipeline would run on float. Q2.
  3. The segmenter's fine-tune keeps its photos at the frame in memory. seg_finetune.TrainSet holds every training photo sam_resized to 1,024 px as uint8 (about 2.6 GB, ticket R9). A float sam_resize would make that 10.4 GB in float32. No fine-tune runs in this ticket (D14), but the code is shared. Q3.
  4. rec2020_bt709.icc cannot be deleted. colour_declaration reads a JPEG XL declaring Rec.2020 with the BT.709 curve, today's canonical form, through it: the page's four example files until they are re-made, and any such file a visitor or an API caller still sends (the front re-encodes every upload, OPS-22 D3). It stays as the source profile for that declaration; only the canonical path stops using it. Folded into P3.
  5. The header reader stops before the intensity target. jxl_header.read_header returns after the colour encoding; the intensity target is in the tone-mapping fields that follow it, present only when the header's extra_fields is set. Folded into P1.
  6. The store's tone-mapped path gets simpler. to_rec2020 already goes to LINEAR_REC2020 for a picture above white, applies the EETF there, and then needs a second LittleCMS transform to the BT.709-curve profile. With a linear target, that second transform goes. Folded into P3.
  7. The front's memory. Its unit has MemoryMax=600M. D12 (a)'s float path peaked at 433 MB in the research, and the preview's read-back adds 101 MB in strips (§2 of the ticket). The proxy's MemAvailable was as low as 158 MB on 2026-11-02 (deploy.md). The two peaks must not overlap: the picture is made after the encode has returned. Measured in P3 and P4; a higher MemoryMax is the owner's, as root on the proxy.
  8. Disk. 101 GB free and an 84 GB DVC cache on 2026-11-26. The new store (about 7 GB) and crops (about 27 GB) are written beside the old ones in the workspace and copied into the cache: about 70 GB. Checked before P5.

1. Phase order and why

The read-back and the encoder's new settings come first as code nothing calls (P1), so they are tested against LittleCMS and float64 references with no DVC stage moving. The float resizes (P2) and the switch to the linear canonical photo (P3) are each a code change that moves the models' input; they are written and tested on a few photos, and the store is re-run once, after both, in P5. The preview strand (P4) needs only P3's read-back and runs beside P5–P7. P7 is the first recorded number: the refit, judged by D13's bar, fixed before the runs. The release (P8) ships the store's code, the front, the host, the new head and the preview together, as ML-29's P11 did.

3. P1 — the read-back, the encoder and the header, not wired in

StatusDone 2026-11-26: d575de7; not wired in, the encoder's defaults byte-identical
Blocked byNone

One new module, coffeecv/readback.py: uint16 linear Rec.2020 in, uint8 sRGB out, in numpy float32 (D2, D3, D9), in strips of rows on a thread pool, as rec2020_to_srgb is. It is the one function the store, the host and the front will call. Nothing calls it yet, so no DVC stage moves.

  1. The matrix from the two sets of primaries and D65, derived in code (not a copied table) and checked against the inverse of ITU-R BT.2087's published BT.709-to-BT.2020 matrix; the sRGB curve in closed form (IEC 61966-2-1); clip to [0, 1]; rint to uint8. In strips of 256 rows, never a whole-photo float copy (the ticket's R10: 1,074 MB whole against 101 MB).
  2. Tests, written first: grey ramps to their sRGB values exactly; the primaries and white; a strip size and thread count that do not change a pixel; against LittleCMS float32 within 0.5 of a level and a float64 reference within 0.01 before rounding, on synthetic pictures and on 20 dataset photos; numpy's version pinned in the module as imagecodecs is (D9).
  3. jxl_encode.encode_rec2020 takes the transfer and the intensity target as arguments, today's values the default; jxl_header reads on past the colour encoding to the tone-mapping fields and returns the intensity target (finding 5). Tests: a file written linear at 203 reads back as linear, 203, 16-bit, lossy; imagecodecs decodes it to the samples written within the coding's error.
  4. Checks: the defaults leave every encode byte-identical (a test on a known photo's canonical bytes); scripts/check.sh green.

4. P2 — the resizes give float (D11)

StatusOpen not started
Blocked byNone Q2, Q3 answered

model_io's two resizes take the 8-bit picture and give float32 in [0, 1], by PIL's bilinear in mode "F", channel by channel: the same filter as today, with no rounding after it (D11's research). Serving and training both go through model_io, so parity holds by construction.

  1. sam_resize and sam_input: uint8 in, float32 out, normalised without the / 255 of a uint8; eval_resize and eval_patch the same. _to_chw_normalised takes [0, 1] float.
  2. HeadAugment.view as Q2 answers; seg_finetune.TrainSet as Q3 answers, its departure written in its docstring and in ML-33's ticket.
  3. Tests, written first: the float resize against torch's antialiased interpolate within 0.01 of a level (D11's research named it the oracle); a picture already at size unchanged; uint8 input fed through it within 1.0 level of today's 8-bit output; tests/test_model_io.py's torchvision parity moved to the new contract.
  4. The litert export's check on the deploy fixtures (ADR 0020) re-run, since the graphs' inputs change by the rounding only; docs/inference_path.html updated (CODING_STANDARDS, "A serving change updates the serving path page").
  5. Checks: on 13 photos, the segmenter's input and DINOv3's within 2.02 levels of today's (D11's research), the masks' IoU against today's reported; the frozen head's fit run at toy scale through its real entry point; scripts/check.sh --full green.
