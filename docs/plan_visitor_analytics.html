  4. The app's ID is 8 hex characters; nginx's is 32. It is read only by webapp/app.py, tests/test_webapp_analyze.py and both nginx templates. The app takes an incoming ID only in nginx's form, and otherwise makes its own, as it does today for the smoke test and direct calls. Folded into P1.
  5. yappy's nginx must pass the ID on. It logs $upstream_http_x_request_id and keeps doing so. It forwards the incoming X-Request-Id to the app unchanged. Folded into P1.
  6. preview_ms folds in the decode and segmentation. It counts from the app's start to the preview going out. Step 12 needs its own preview_build_ms, from the end of segmentation to the part written. Folded into P2.
  7. Only --verify crosses the domain. The smoke test runs on yappy itself, on its own port and into its own log directory, so it never reaches the front's logs. --verify's requests carry a header, X-Coffee-CV-Probe: verify. The front's access log and the check service log it, and the script leaves those requests out. A visitor who sends it only hides their own requests. Folded into P2 and P5.
  8. The session log is world-readable. Its files are -rw-r--r-- www-data root (read 2026-11-09). The logrotate rule gains create 0640 www-data adm, and the existing files are changed once by hand (D18). Folded into P2 and P9.
  9. No browser in the devcontainer. As for OPS-20, the page is checked in headless Chromium with Playwright, from a script outside the repo. Folded into P4.

Refusing a missing Origin risks losing real timelines from some browsers.P3

3. P1 — One request ID

StatusDone 2026-11-09, f76a0d3
Blocked byNone

The front's nginx makes the ID ($request_id, 32 hex characters) and every hop keeps it (D8). Work on a branch, ops3-timelines, merged to main by a merge commit (ADR 0017).

  1. The front's site: proxy_set_header X-Request-Id $request_id on /analyze. add_header X-Request-Id $request_id always in @too_large, @busy and @offline. A visitor's own X-Request-Id is replaced, never passed on.
  2. The check service: read the ID from the incoming header, keep it in its log line (P2), forward it to yappy, and send it on its own JSON answers (400, 413, 503, 500), which today carry none.
  3. yappy's site: pass the incoming X-Request-Id to the app unchanged.
  4. The app: take the incoming ID when it has nginx's form (32 lowercase hex characters), else make its own as today. X-Request-Id on the answer is still the ID it used.
  5. Checks: tests/test_front_site.py (a real nginx) shows one ID in the front's access line, the check service's answer and the fake inference host's request, and on each of the front's refusals. tests/test_front_check_service.py and tests/test_webapp_analyze.py cover a malformed or missing incoming ID. The full suite is green.

4. P2 — The hosts' new fields

StatusDone 2026-11-09, d22478e
Blocked byP1

What the hosts alone can see (D6, D9, D10): the check service's line becomes JSON in a file of its own, and the app and the front's access log gain the fields §2 of the ticket names.

  1. The check service writes one JSON line per request to /var/log/coffee-cv-front/requests.jsonl, with no IP. The line has the ID, the time, the endpoint, the outcome, the probe marker, and these fields:
    • the original's filename (capped at 200 characters), extension, detected format and bytes;
    • whether the photo was canonicalized or "canonical as sent", and if canonicalized the time, pixels, depth, peak and swap, as the text line has today;
    • the canonical photo's bytes;
    • the crossing's milliseconds, from connect to the last byte sent;
    • the time to yappy's headers, to the first chunk (the preview) and to the last chunk;
    • the bytes relayed and the total time.
    The journal keeps the start-up line only.
  2. The app: preview_build_ms in its request line (step 12). That is logging only: what /analyze runs does not change, so docs/inference_path.html is not touched.
  3. The front's access log adds three fields at the end of its line, so existing readers still parse it: "$http_user_agent", "$http_referer" (D5) and $http_x_coffee_cv_probe.
  4. The unit template: LogsDirectory=coffee-cv-front, and the comment saying it writes no file is corrected. The logrotate template: the new file, 365 days, with copytruncate or a reopen as the check service needs; the session log gains create 0640 www-data adm (D18). setup_front.sh installs both, idempotently, for P9.
  5. Checks: test_front_check_service.py covers each field: canonical as sent, canonicalized, refused, offline, cut mid-answer. A test checks that no line holds an address. test_front_site.py checks the access log's new fields, with the visitor's 127.0.0.5 in none of them. logrotate -d accepts the rendered rules. The full suite is green.

5. P3 — POST /timeline

StatusDone 2026-11-09, 400d5a4
Blocked byP2

The endpoint the page sends its timeline to (D7, D16), with D17's layers 2 and 3. The schema is one module, used by the check service to accept and by the script (P6) to read.

  1. The schema, written once as data:
    • the request ID, or none for a photo refused on the page;
    • the ID of the run this one re-runs ("Use full photo instead");
    • the control (Choose Photo, Take Photo, Select File, the camera button, an example) and the example's name, checked against examples.json;
    • the outcome (answered, refused on the page, refused by the front, busy given up, offline, cut, abandoned);
    • each busy attempt's ID and wait;
    • the page's times for steps 1–6, 13, 14, 16 and 17, in whole milliseconds from 0 to 600 000;
    • the probe marker.
    Unknown keys or values are refused with a 400.
  2. The check service: POST /timeline reads at most the body limit, checks it against the schema, writes it to the same file as a line of kind timeline with json.dumps, and answers 204. Past the daily cap it drops the timeline and counts it (Q2).
  3. The front's site: location = /timeline with its own client_max_body_size, no limit_conn, a global limit_req keyed on $server_name (Q2), and a 403 for another site's Origin (Q3). It sends no CORS headers. It is logged in the access log like any request.
  4. Checks: tests for each refusal: an unknown key, a value outside its set, a negative or huge time, a malformed ID, an oversized body, another site's Origin, a burst past the rate, and the daily cap. A test checks that a field with a newline or control character is written as one JSON line. /analyze's gate is never taken by /timeline. The full suite is green.

6. P4 — The page's timeline

StatusDone 2026-11-09, c015fe7
Blocked byP3

The page measures its steps on performance.now() and sends one timeline per photo (D7). The photo's path through choose(), analyze(), postAnalyze() and send() stays the same; the timeline is gathered beside it.

  1. The page marks the times at:
    • the control's tap, and the file arriving;
    • an example's download;
    • the size check;
    • each attempt's start, upload sent, headers and busy wait;
    • the preview part arriving and being drawn;
    • the classification arriving and being shown.
    The connection setup is read from the XHR's Resource Timing entry when the browser gives one.
  2. It sends the timeline once, when the answer is shown or an error or refusal is shown, and on pagehide or a new pick for a photo still in flight (abandoned). A photo refused for size on the page sends one with no ID. "Use full photo instead" sends its own, naming the first run's ID.
  3. A failed or refused beacon is ignored: the page never waits on it, retries it or shows it.
  4. Checks: tests in the style of tests/test_example_photos.py's ThePage: the page's controls, outcomes and fields match P3's schema. In headless Chromium, against the local front with the fake inference host: one timeline each for an own photo, an example, an oversized photo, a busy retry, "Use full photo instead" and a photo abandoned for another, each accepted by P3 and joined to the check service's line. The full suite is green.

8. P6 — The script

StatusDone 2026-11-09, 4764896, 0fc034a
Blocked byP2, P3

One module, coffeecv/timelines.py, in the shape of seg_review, with two subcommands: summary, which prints, and serve, which serves a page on 127.0.0.1 (D13).

  1. Reading:
    • over SSH as the deploy users, read the front's access log, the check service's file and yappy's app log and access log, rotated and compressed files included, from a given date, and never from before the release (D20);
    • never read the session log;
    • hold everything in memory and write nothing locally.
  2. Joining (D17's layer 4): by request ID; the first timeline per ID counts and the others are flagged; a timeline with an ID no host knows is unverified; one with none is unverifiable. The probe marker's lines are left out.
  3. summary prints, for a chosen period:
    • per day: page loads without crawlers, referrers, photos by control, by example and by format and size;
    • each step's median and 90th percentile, split by control and by canonicalized or not;
    • failures by kind;
    • other sites' calls by Origin;
    • the unverified, suspicious and dropped timelines.
    Every string a visitor sent is printed without control characters (layer 5).
  4. serve shows the same numbers, each step's distribution, and a list of photos whose timeline opens step by step. Every string a visitor sent goes into the page as text, never as HTML (layer 5).
  5. Checks: tests on recorded log lines from P1–P5's tests and the rehearsal, including forged, duplicate and malicious ones. The script refuses a path to the session log. The full suite is green.
