Ticket OPS-5 · coffee-vision · tooling and guardrail

leak_check --staged checks each staged file as it is staged, from the index, not its copy on disk

The pre-commit hook's leak check reads each staged file's working-tree copy. A leak in a staged line that is edited away on disk passes the hook and is committed, and the repo's history is not rewritten. OPS-4's plan found this (finding 1), and the owner split it into this ticket (OPS-4 D6). OPS-4's coffeecv.ruff_staged already reads staged blobs, so the reader exists. Decisions answered and planned 2026-11-08; not implemented.

1. Summary

Today python -m coffeecv.leak_check --staged takes the staged file list from the index but reads each file's contents from disk, so it checks the working tree, not the commit. After this ticket it reads each staged blob from the index, as coffeecv.ruff_staged does: a leak in the index is refused even when fixed on disk, and a leak only on disk does not block the commit. The work splits into: the text check on staged blobs, the image check on staged blobs (exiftool needs a file), tests on a temp repo for both directions, and the comments that today say "until OPS-5".

2. Background

  • The file list is the index's, the contents are the disk's. published_files(root, staged=True) runs git diff --cached --name-only --diff-filter=ACMR (coffeecv/leak_check.py, published_files). scan() then reads root / rel from disk, skipping symlinks and non-files by their disk state, and image_findings() passes the disk paths to one exiftool call. The module docstring says so: "--staged reads each staged file's working-tree copy". Read at d4068d9.
  • Both directions are wrong. A line staged with an email address and edited away on disk passes the hook and is committed (a leak). A leak added on disk but not staged refuses a commit that does not contain it (a false refusal). scripts/check.sh's full scan before a push reads the working tree on purpose, since it checks what git add -A would publish, and it would not see the first case once the disk is clean.
  • The test does not cover contents. tests/test_leak_check.py's test_staged_sees_only_the_index checks which files are listed. In it the disk and the index hold the same bytes, so it passes either way.
  • The reader exists. OPS-4 P5's coffeecv/ruff_staged.py reads each blob with git show :<path>, and skips symlinks and submodules by their index mode (git ls-files -s: 120000, 160000). Its tests on a temp repo cover a file clean in the index and dirty on disk, and the reverse.
  • Comments that name this ticket. .githooks/pre-commit says the leak check "reads each staged file's working-tree copy, not the index, until OPS-5"; coffeecv/ruff_staged.py's docstring says the same. leak_check's own docstring describes the disk read as intended.

3. Before and after

Now

  • --staged lists the staged files and reads them from disk.
  • A staged leak fixed on disk is committed; an unstaged leak on disk refuses the commit.
  • Staged images are read by exiftool from disk.
  • The hook's comment says the two checks read different things.

After

  • --staged reads each staged blob from the index; symlinks and submodules are skipped by index mode.
  • A staged leak is refused even when fixed on disk; a leak only on disk does not block the commit.
  • A staged image's blob is what exiftool checks, and a finding names the staged path.
  • The hook, leak_check and ruff_staged say both checks read the index.

4. What does not change

  • The full scan. leak_check without --staged, as scripts/check.sh runs it, keeps reading the working tree: it checks what git add -A would publish, untracked files included.
  • The rules. What counts as a leak (public IPs, emails, credentials, photo metadata, the owner's private patterns) and the allow-lists stay as they are.
  • The hook's shape. It still runs leak_check --staged and ruff_staged, both always.

A blob written to a temp file must keep its extension, and the finding must name the staged path, not the temp one. A test with a staged GPS photo whose disk copy is stripped covers it. Mostly gone by D1 (c): the temp tree keeps each path, and image_findings(paths, root) already maps back by relpath to the root it is given.

R3A second index reader drifts from the first. ruff_staged already reads blobs and filters index modes. A copy in leak_check could diverge (a mode skipped in one, not the other); D2 decides where the reader lives. Closed 2026-11-08 by D1 (c) and D2 (a): only ruff_staged reads blobs, and the leak check skips symlinks and submodules by the same disk checks its full scan uses.

6. Decisions

IDQuestionOptionsOwner decision
D1How are the staged blobs read? (a) One git show :<path> per file, as ruff_staged does (b) one git cat-file --batch process for all staged files (c) one git checkout-index --prefix=<tmp>/ -z --stdin fed the staged list, writing the staged set into a temp tree under its own paths, and the existing scan() run on that tree (added 2026-11-08) (c), 2026-11-08. With --staged, leak_check writes the index into a temp tree and scans it; scan() and image_findings() are unchanged, so exiftool sees the staged path and extension. Tried on throwaway repos: the tree holds the staged bytes, not the disk's; a symlink is written as a symlink and a submodule as an empty directory, so scan()'s disk checks skip both; it follows GIT_INDEX_FILE, which is the temp index git hands the hook under commit -a and commit <path>. The repo has no .gitattributes or filters, so the tree holds the raw blobs. Cost is not what decides it: 30 files took about 80 ms by (a), 5 ms by (b).
D2Where does the index reader live? (a) In leak_check beside published_files, and ruff_staged uses it (b) each module keeps its own (c) a third module both import, e.g. coffeecv/git_index.py. Context from OPS-4's code review (2026-10-07): ruff_staged.staged_python_files reads index modes itself, and ruff_staged already imports leak_check (published_files), so a reader left in ruff_staged and imported by leak_check would make a circular import. (a) and (c) avoid it; (b) keeps the drift of R3. Reframed 2026-11-08 by D1 (c): leak_check needs no blob reader or mode filter of its own, so the options became (a) nothing moves (b) ruff_staged lints the temp tree too (c) a coffeecv/git_index.py with published_files and the temp-tree writer. (a) as reframed, 2026-11-08. Nothing moves: ruff_staged keeps its git show per file and its index-mode filter, since Ruff resolves its config and force-exclude from the real repo path, and changes only in its docstring. The one shared function, published_files(root, staged=True), stays in leak_check; the import goes one way, so there is no cycle. Closes R3.
D3Are the stale timing claims fixed here? (a) All of them, from the hook-time measurement this ticket already makes (b) only those on lines this ticket touches anyway (c) none, left for later docs work (a), 2026-11-08. coffeecv.config imports torch only inside its functions, and strip_metadata not at all, so python -m coffeecv.leak_check starts in about 0.33 s, not 1.7 s (measured 2026-11-08). Corrected: the hook's header ("both import torch through coffeecv.config", 1.7 s each), ruff_staged's docstring (1.7 s), the comment in image_findings() ("it pulls in torch") and this ticket's R2.
D4How is the change tested? — As proposed, 2026-11-08. leak_check.main(argv, root=REPO_ROOT), as ruff_staged.main. Tests on a temp repo, each seen failing first: an email staged and then removed on disk is refused; an email added on disk only, to a clean staged file, passes; a staged GPS photo whose disk copy is stripped is refused and named by its staged path; a staged symlink, submodule and deletion are skipped; a private pattern in a staged path is still found; and one case with GIT_INDEX_FILE on another index, standing in for commit -a and commit <path>. No test runs the real hook through git commit: its other two checks read REPO_ROOT.

7. Scope and acceptance

  • leak_check --staged reads each staged text file's blob from the index: an email staged and then removed on disk is refused; an email added on disk to a clean staged file is not.
  • A staged image is checked as staged: GPS in the staged blob is refused when the disk copy has none, and the finding names the staged path.
  • Staged symlinks and submodules are skipped by index mode; a staged deletion is not read.
  • The private-pattern check on file paths still runs on every staged path.
  • tests/test_leak_check.py covers both directions on a temp repo, each case seen failing before the change, and the D4 cases, including one on another index through GIT_INDEX_FILE.
  • leak_check's docstring, the hook's header comment and ruff_staged's docstring say the leak check reads the index; no "until OPS-5" is left.
  • No claim that the leak check or ruff_staged imports torch or takes 1.7 s to start is left in the hook, either module or this ticket (D3).
  • scripts/check.sh passes, and the hook's added time on a 30-file commit is measured and written in its header.

Out of scope

  • The full scan's working-tree read (scripts/check.sh), which is right for what it checks.
  • New leak rules or allow-list entries.
  • Wiring the hooks on the VM, whose clone has no core.hooksPath (OPS-4 P5).
