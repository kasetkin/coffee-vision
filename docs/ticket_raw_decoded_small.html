Owner request, 2026-11-09. “Open new ticket for DNG decoding”, after Claude read the photo's line in the logs of OPS-3's phone check.

1. Summary

Today a camera RAW upload is developed by rawpy at whatever size LibRaw reports, and nothing checks that the result is the photo's main image. The one phone DNG seen through the live site came out at 0.27 MP. After this ticket we know what LibRaw read from that file and why, and such a file is either decoded at its full size or refused saying why (D1), held by a test. The work: get the file; read its image directories and what LibRaw chose; find the cause; fix or refuse; a test with the file or one like it.

2. Background

  • The log line (the front's /var/log/coffee-cv-front/requests.jsonl, 2026-11-09 16:47 UTC, release 20261109T1637Z-c37f30e): ext .dng, format dng, bytes 5379377, canonicalized in 195 ms, width 454, height 602, bits 16, peak_mb 134, canonical_bytes 86834; then relayed, answered refused_ood. The four other photos of the same check (JPEG and HEIC) each took about 5 s to canonicalize; this one took 0.2 s.
  • The decode (coffeecv/canonical.py, decode): a RAW file is opened by rawpy.imread, checked against the RAW ceiling (16 MP, ML-19 D24) on raw.sizes, and developed with postprocess(output_bps=16, use_camera_wb=True, output_color=Rec2020, gamma=(1, 1)): no half_size, no thumbnail path. So a small image is what LibRaw itself took from the file.
  • The arithmetic: a 12 MP Bayer image at 16 bits is about 24 MB uncompressed, and lossless-JPEG DNGs of that size run 10–15 MB. 5.1 MB suggests a lossy main image (lossy DNG, or DNG 1.7's JPEG XL), or a file that really is small. Two hypotheses: (1) the file's main image uses a compression this LibRaw build does not decode, and LibRaw took a reduced-resolution directory instead; (2) the app that wrote it made a small DNG.
  • What is known to work: the dataset's six DNGs (dataset/segmenter_positives/, a Pixel 9 Pro) decode at full size; tests/test_front_check_service.py reads one at 3628 × 2732. The phone of 2026-11-09 sends Chrome's reduced browser string (“Android 10; K”), so its model is not in the logs.
  • No copy: the front never stores a photo (ADR 0033, OPS-3's “What does not change”), so the file must come from the owner's phone.

3. Before and after

Now

  • A RAW file is developed at the size LibRaw picks, checked only against a ceiling.
  • A file whose main image LibRaw cannot read may be classified from a small one, silently.

After

  • The cause of the 454 × 602 decode is known and written here.
  • Such a file is decoded at its full size, or refused with a 400 that says why (D1).
  • A test holds it, and the dataset's DNGs decode to the same pixels as before.

4. What does not change

  • One decode for training and serving. coffeecv.canonical makes both training's and the front's canonical photos (ADR 0033); a fix changes both, and is held to the dataset's DNGs (R1).
  • The RAW ceiling (16 MP, ML-19 D24) and the accepted formats (ADR 0034).

5. Risks

IDRiskEvidence and mitigation
R1A fix changes training's RAW photos too. The same code canonicalizes training's photos. Check that the dataset's six DNGs decode to the same canonical pixels before and after (CODING_STANDARDS.md, “A rewrite is checked against the original”).
R2Without the file, the cause stays a guess. The log line cannot say which directory LibRaw read. The owner sends the DNG, or another from the same phone and app; until then this ticket is needs-info.

6. Decisions

IDQuestionOptionsOwner decision
D1A RAW file whose main image cannot be decoded at full size? (a) Decode it fully (another LibRaw option or version) (b) Refuse it with a 400 that says why (c) Accept the small image Open, until the cause is known.
D2A floor on any photo's decoded pixels? (a) Yes, refuse a photo under N MP (b) No Open.

7. Scope and acceptance

  • The owner's DNG, or one like it, is read: its image directories, their sizes and compression, and the one LibRaw developed, written into this ticket.
  • The cause is known.
  • That file is decoded at its full size or refused saying why (D1), and a test holds it.
  • The dataset's DNGs decode to the same canonical pixels as before (R1).

Out of scope

  • The other RAW formats, unless the cause is shared.
  • OPS-3's logging, which found this.
