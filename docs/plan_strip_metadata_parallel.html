Implementation plan: strip photo metadata on several cores at once

The order of work for ticket ML-14. Three strands: the stripper without torch (P1); the serial run made safe, with failing rows, the resume check first, rows written as they come and a memory ceiling (P2, P3); then the pool (P4) and the measurements (P5). The serial work comes first because --jobs 1 is what the parallel run is checked against (D7), and P2's per-row writing is what P4's ordered results feed. No phase changes a manifest row's values; P5 is the owner's stop.

1. Phase order and why

P1 is a move with no behaviour change, checked by the import test and by every pixel digest staying the same. P2 and P3 change what a serial run does on an error, a mismatch, a Ctrl-C or a huge photo, and nothing about the rows of a run that has none of these. P4 adds the pool, checked row for row against P2's serial run. P5 measures and stops for the owner.

4. P2 — The serial run: failing rows, resume check first, rows as they come

StatusDone 2026-10-30, 684679d
Blocked byNone

Reshapes main into the steps P4 parallelises, still one photo at a time. The order of a run:

  1. List the photos (photos_under) and take the start time (D10).
  2. The resume check (D6): every photo whose key is in the manifest is hashed; any mismatch prints the photo, as today, and returns 1 before any photo is touched. The photos that pass are left out of the work list. Skipped under --dry-run, as today.
  3. Each photo in the work list goes through run_one(path, dry_run), a new module-level function (P4 submits it to workers) that calls strip_one and turns an Exception into a failing row for the photo: problems = [f"error: {type(e).__name__}: {e}"], its other fields as strip_one's first row has them, or the path and empty hashes if it failed before that (D5). BaseException is not caught.
  4. Each row as it comes, in photo order (D9, D10): its progress line, as today's; then, if it is a good row and there is a manifest and no --dry-run, it is appended and flushed. A small writer object holds the open file: it writes the header (with the start time) just before the first row of a new manifest, so a run with no good row writes no file.
  5. The report and the exit code, as today, from all the rows.

A Ctrl-C at --jobs 1 raises KeyboardInterrupt in strip_one; its finally removes the temporary file, and the rows written so far stay. The one row it can lose is the photo replaced on disk in the instant before its row is written, as today. The writer closes in a finally.

  1. run_one, the resume check before any work, the manifest writer, the start time; main rebuilt on them.
  2. Tests: a photo whose strip_one raises (mocked) gets a failing row, the photos after it are stripped and in the manifest, and the exit code is 1; a manifest photo with changed bytes gives exit code 1 with every other photo's bytes unchanged and no row added; an interruption (a mocked strip_one raising KeyboardInterrupt on the third photo) leaves the first two photos' rows in the manifest; a new manifest's header carries a start time taken before the first photo; a run whose only photo fails writes no manifest.
  3. Checks: the existing tests unchanged and green (the rows of a run without errors are what they were); the full suite green.

5. P3 — The memory ceiling

StatusDone 2026-10-30, 689d242
Blocked byP2

D13 (a). Before a photo is handed to run_one, the main process reads its dimensions from the header (Pillow's Image.open(...).size for JPEG and PNG, which reads no pixels; pillow_heif for HEIC, every top-level image; rawpy's sizes for RAW) and estimates its decode memory as width × height × a factor per format. Above the ceiling it gets a failing row, too big: about N GB to decode, budget M GB, and is never decoded; its original is untouched, it gets no manifest row, the exit code is 1. The ceiling is the memory available at the start (/proc/meminfo's MemAvailable, else os.sysconf) minus 1 GB, or --max-memory GB. P4's D12 default reads the same figure, so one helper returns it. A photo whose header cannot be read is not failed here: run_one meets the same error and makes it a failing row.

  1. The factors, measured: peak RSS above the imports of pixel_digest on a JPEG, a PNG, a HEIC with auxiliary images and a DNG, each in its own process, divided by its pixel count (for RAW, rawpy's output size). Written as constants with the measurement and its date in a comment, rounded up. The measurement of 2026-10-30 (ticket §2) gives about 10 bytes per pixel for a JPEG and a HEIC.
  2. estimate_decode_bytes(path), available_memory(), --max-memory, and the check in main before run_one. The report lists the too-big rows under its usual FAIL lines.
  3. Tests: with --max-memory 0.001 a fixture photo gets the too big row, keeps its bytes and gets no manifest row, and the exit code is 1; with the default ceiling the fixtures run as before. estimate_decode_bytes on each fixture format is within its factor of the pixel count.
  4. Checks: the full suite green.

6. P4 — The pool

StatusIn progress started 2026-10-30
Blocked byP1, P2, P3

D1, D3, D4, D7, D12. --jobs N, default min(os.cpu_count(), available_memory() // 1 GB), at least 1. At --jobs 1 nothing changes from P3 (D7). Above 1, a ProcessPoolExecutor(N, mp_context=spawn) as in find_duplicates, with an initializer that sets SIGINT to ignored in each worker. The main process submits run_one for every photo that passed the ceiling, in photo order, keeps the futures in that order, and takes each result in turn: the ceiling's failing rows take their place in the same order. Each result goes through P2's row step, so the progress lines and the manifest stay in photo order (D3, D9).

On a KeyboardInterrupt in the main process (D4): print that the run is stopping; shutdown(wait=False, cancel_futures=True); wait for the futures already running; then write, in photo order, every row whose future is done, skipping those cancelled, and exit 130 after the report. A second KeyboardInterrupt during that wait leaves at once: the workers are terminated, and their temporary files are beside their photos under a .-prefixed name that photos_under skips.

  1. --jobs, the pool, the ordered results, the Ctrl-C handling.
  2. Test: on a mixed set (the JPEG and HEIC fixtures with private tags, an already clean JPEG, and under @real_data the DNG and the iPhone HEIC the suite names, copied to a temporary folder), --jobs 1 and --jobs 3 give the same manifest rows, the same report, the same exit code and the same bytes on disk. Under --dry-run as well.
  3. Test: a truncated JPEG in the set gets a failing row from its spawned worker, and the other photos are stripped and in the manifest.
  4. Test: python -m coffeecv.strip_metadata in a subprocess on a dozen fixtures at --jobs 2, sent SIGINT after its first progress line: every photo whose bytes changed has its row, every row's sha256_after is its photo's bytes, no .-prefixed temporary file is left, and a rerun strips the rest and appends their rows.
  5. Checks: the full suite green, both tiers.

Explicitly not in this change

  • Everything in the ticket's "Out of scope": a long-lived exiftool per worker, admission by memory, a single decode of an RGB JPEG or PNG in pixel_digest, fewer copies in load_rgb_image.
  • Parallel hashing in the resume check: it reads files without decoding them, and stays serial in the main process.
