Built from a read of the code at acd949b, not from the ticket alone. Four things the ticket does not cover turned up. They are folded in below, and the ones that need a decision are Q1–Q2 (§2).

  1. The classifier fit has no "best metrics checkpoint". fit_frozen_head.fit_one_seed embeds the train, val and test patches and 8 views of every training patch, then fits one convex head at the fixed C; there are no epochs and nothing to select. Its hours go into the embeddings, which ADR 0025 keeps in memory only. Q1.
  2. DVC deletes a stage's outputs before it runs. A resume file declared as an output, or written to models/seg/<name>.pt, would be gone when dvc repro reruns the stage after a reboot. The resume state lives in outputs/ (gitignored, not a DVC output). P2.
  3. An exact resume needs three random streams. The fine-tune draws from torch's generator, its own numpy generator (batches, points) and the augmentation Compose's two generators (albumentations 2.0.8: random_generator and py_random, which seg_finetune.build_augment hides in a closure). All are saved and restored, with the optimizer and the cosine schedule. P2.
  4. The classifier's views are seeded per patch. HeadAugment.view seeds each view by (run seed, patch, view), so embeddings saved in chunks and resumed mid-split are the ones an uninterrupted run computes. That makes Q1 (a) exact without saving any random state. P3.

1. Phase order and why

P1 touches only data and records. P2 and P3 change training code but no number: a resumed toy run must equal an uninterrupted one byte for byte, and an uninterrupted run must equal what the code gives today. P4 is the owner's labelling, the longest step; P2 and P3 fit inside it. P5 is the first step that changes a number.

4. P2 — The fine-tune keeps its best checkpoint and resumes

StatusDone 2026-10-27: resume state each epoch; a run killed in epoch 2 and rerun gives the uninterrupted model, which is the code before's
Blocked byNone

After every epoch seg_finetune.train writes, atomically (a temporary file, then a rename), outputs/seg_finetune/<name>/resume.pt: the epoch, the decoder, the optimizer, the scheduler, the torch, numpy and augmentation random states, the best epoch's decoder and metrics, the history, and a fingerprint of the run. The fingerprint holds what the fine-tune stage in dvc.yaml lists, so a change DVC would rerun the stage for also stops a resume: the seed, the name, --lr, the threads, the label-set hash, the base weights' hash, the sha256 of seg_finetune.py, augment.py, sam_loader.py and the efficientvit tree, the albumentations version, and the params seg_ft, seg_prompt, seg_mask_select and augment, with seg_ft.augment expanded: its {use: colour}, compression and noise entries name augment's shared groups (ADR 0027), which hashing seg_ft alone would miss. The best epoch's decoder is in it from the moment it is best. Run again with the same arguments, the command finds the file, checks the fingerprint, rebuilds the photos and validation encodings (deterministic, minutes) and continues at the next epoch.

Each run has its own slot, outputs/seg_finetune/<name>/, and reads no other. A file in its own slot with another fingerprint is a leftover: it is deleted, with a log line naming what differs, and the run starts fresh (D8's rule). A run also deletes the other slots' leftovers when it starts, so nothing from one experiment stays on disk into the next (D8), except a toy run: a name ending _toy (the toy-scale proofs of P2 and P5) touches its own slot only, so a toy run made while a real run is interrupted cannot delete its hours. The slot goes once models/seg/<name>.pt and its card are written; the card records the epochs a run resumed at. The DVC stage's command is unchanged, so dvc repro -s after a reboot resumes. A reboot after the model is written and before DVC writes dvc.lock leaves the model but no resume state: then dvc commit the stage (after checking the card's chosen) instead of rerunning it.

  1. build_augment exposes its Compose's generators, so their state can be saved and restored in place.
  2. The resume state, written each epoch, read at start; the fingerprint check, the slots and the leftovers' deletion, _toy names kept to their own slot; the docstring.
  3. Tests on a toy model, with patience above the epochs so no run stops early: three epochs straight against one, a stop, and a resume give equal decoders, history and chosen epoch; a changed seed, label set, seg_ft key or shared augment group starts fresh and deletes the old state; a run deletes another name's leftovers and a _toy run does not; the slot is gone after the model is written.
  4. Checks: an uninterrupted toy run through the real entry point gives the same .pt as the code before P2 (CODING_STANDARDS, "A rewrite is checked against the original"); the same run killed during epoch 2 and rerun gives it too; scripts/check.sh.

5. P3 — The classifier fit resumes

StatusDone 2026-10-27: features saved and resumed; a --smoke killed after its first chunk and rerun gives the code before's model
Blocked byNone Q1 answered (ticket D8)

D8: fit_one_seed saves each split's embeddings, labels and metadata under the run's outputs/frozen_head/ directory when the split is done, and the training views in chunks as they are embedded, each file with the run's fingerprint. The fingerprint holds the seed, --smoke, the torch threads, the chunk size, the run's config (config_to_dict and head_augment's record), the backbone's weights hash, the crops' version in dvc.lock (merge_segpool's output), and the sha256 of the files a run's provenance check guards that a fit reads: coffeecv/, coffeecv_dino/, params.yaml, the classes file and labels/ml3/pool_exclude.csv. Not the git commit: Activity entries are committed during runs here, and each would throw away hours of embeddings. A rerun of the same command loads what matches and embeds the rest.

A chunk is a whole number of EMBED_BATCHes (32 views, 4 patches at 8 views), starting at a multiple of it, so a resumed run embeds every batch with the same views in it as an uninterrupted one: a batch made of other views can round differently on the CPU, and the resumed run would differ with nothing to show why. The chunk size is a module constant a test can lower, so a --smoke run spans several chunks.

Real runs and --smoke runs keep their files apart (outputs/frozen_head/ and its smoke/, as their run directories are now). The files go once the seed's run directory is written. A real run deletes every real run's files whose fingerprint is none of its seeds' before it embeds anything, so nothing from one experiment stays on disk into the next (D8); a --smoke run reads and deletes only smoke/, so a smoke made while exp279 is interrupted cannot delete its hours.

  1. The saved splits and view chunks, aligned to EMBED_BATCH, loaded on a rerun; the fingerprint; the clean-up at the run's end and of another run's leftovers at the start, smoke and real kept apart; the docstring.
  2. ADR 0025 amended: embeddings on disk until the run ends; nothing augmented stored as an image.
  3. Checks: --smoke with the chunk size lowered so its views span at least three chunks, straight through, and killed after the first chunk and rerun, give the same model.pt and metrics.json; a changed pool_exclude.csv or config key starts fresh; a --smoke leaves a real run's files alone; an uninterrupted --smoke gives what it gave before P3; scripts/check.sh.
